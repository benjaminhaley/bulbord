# Bulbord — Engineering Guide

This file is loaded automatically at the start of every Claude Code session in this repo. It is the source of truth for architecture and process decisions — read it before making structural changes, and update it whenever a decision below changes.

For product background, goals, and development path, see `readme.md`. For running notes/findings, see `log.md`.

## Product shape (MVP)
- Two tabs: Events, Camps.
- Invite-only: nothing is visible or usable — not even read-only browsing — until you've been invited by an existing member. There is no public/anonymous tier. See Login below for the mechanics; see the 2026-08-01 line in Status of these decisions for why this replaced the earlier public-read-access model.
- Logged-in: can suggest new events/camps, attempt bookings. Suggestions are saved as `pending` and only appear on the tabs once approved. Approval is modeled as a role, not a hardcoded person — Ben is the approver today, but the permission model must support automating or delegating approval (including to Claude) later without a schema change.
- Admin (Ben only): full data access via the in-app admin panel (see Introspectability below).
- Every account tracks who invited it (`users.invited_by_user_id`, nullable — null means a root/bootstrap account) — a basic social graph, visible today in the admin `/admin/users` view. There's no cap on how many people one member can invite, and no separate moderation queue for new members beyond the invite itself; revisit if that stops being appropriate at a larger scale.
- **Bulbord is the umbrella platform brand; each institution (a school, or other civic group) gets its own subdomain community** — e.g. `nettelhorst.bulbord.com` for Nettelhorst School, the first and (for now) only one (feedback #32, 2026-08-02). This is currently a domain/branding convention only, not a data-model change: there's no `institutions`/tenant table, and all data is still global/shared across the single Postgres database described in Application architecture below. Revisit if/when a second institution is actually onboarded. The bare platform domain (`bulbord.com`, no subdomain) serves a small static landing page (`web/src/landing/LandingPage.tsx`, branched on `window.location.hostname` in `web/src/main.tsx`) instead of the invite-gated app.

## Login
- Passkeys (WebAuthn) only — no password, no OAuth provider. Combined with the invite-only model above: the only way into the app is via another member's invite link (or, once, the root bootstrap secret — see below), and the only way to authenticate is a device passkey (Face ID / Touch ID / Windows Hello / Android biometric). Facebook OAuth was dropped entirely (2026-08-01), not deferred — this doesn't preclude adding an OAuth provider back later if a real need shows up; it would need its own credential table, since WebAuthn credentials aren't shaped like `(provider, provider_user_id)` pairs.
- Implementation: `users` (profile — `name`, `email`, `avatar_url`, `invited_by_user_id`, `profile_completed_at`) + `passkey_credentials` (one row per registered passkey — `credential_id`, `public_key`, `counter`, `device_type`, `backed_up`, `transports`; a user can have more than one, e.g. one per device) + `sessions` (opaque bearer token, sha256-hashed at rest) + `user_roles` (user_id + role, e.g. `admin`) — roles are data, not hardcoded checks, per the approver-role requirement above. Feature folder: `api/src/auth/` (`webauthn.ts` for the WebAuthn ceremonies, `service.ts` for session/profile/invite-lookup logic, `tokens.ts` for the shared HMAC signing helpers, `routes.ts` for the HTTP surface), mirrored by `web/src/auth/` (`webauthn.ts` client wrapper, `JoinGate.tsx` for the invite/registration/profile-setup UI, `AccountPage.tsx` for a signed-in member's own page).
- Session transport: bearer token (`Authorization: Bearer <token>`), not a cookie — unchanged from the original rationale (the web app and API are different top-level domains; Safari ITP would block a cross-site cookie; bearer tokens also travel cleanly into the Capacitor app's secure storage). Frontend stores the token in `localStorage` (`web/src/auth/token.ts`). Session TTL is still effectively unlimited (100-year expiry) for the same low-stakes-MVP reasons as before.
- **Invites**: no separate invite table or single-use codes. Every member's own `id` doubles as a permanent, reusable invite identity — `web/src/sharing/ShareButton.tsx` (see Sharing below) appends `?invite=<your user id>` to whatever URL it's already encoding when you're logged in. A non-member who opens that link sees a join screen naming the inviter (`GET /invites/:userId`, public, returns only `{name, avatarUrl}`) and can register a passkey to join, which sets their `invited_by_user_id`. Reusable by design (the same QR can invite multiple people over time, matching the existing in-person "shown at pickup" sharing model) — no expiry, no per-invite tracking, no cap. `web/src/auth/JoinGate.tsx` is the single place this is enforced on the frontend: it wraps the entire app and renders the join screen instead of any route until `user` is set, so there's no route that's reachable without it.
- **Root bootstrap**: the very first account can't come from an invite link (no member exists yet to generate one). `ROOT_INVITE_SECRET` (env var, timing-safe compared, same shape as the old `ADMIN_LOGIN_PASSWORD` stopgap) lets a registration happen with `invited_by_user_id = null` when the correct secret is supplied via `?rootSecret=<value>` instead of `?invite=`. Meant to be used once (or rarely, e.g. a second root-level account) and then left unset — unsetting it in Railway disables the path immediately (403) with no code change.
- **Sign-in link** (`?signInToken=<session token>`, added 2026-08-12 for App Store review — see Platform strategy's submission entry): `web/src/main.tsx` reads this param on boot, calls `setToken()` with it, and strips it from the visible URL immediately — lets a valid session be delivered as a link instead of requiring the WebAuthn ceremony. Same trust model as `?invite=`/`?rootSecret=` below (a query param carrying a real credential), not a new auth path or a backdoor — the token still has to be a real, valid session created the normal way (`createSession()`). Used for Apple's reviewer (a dedicated, always-onboarded "App Review" account, invited by Ben but kept separate from his own identity) and for capturing authenticated screenshots (`api/src/auth/update-2026-08-12-create-screenshot-session.ts` mints one for Ben's own account on demand). Not surfaced anywhere in the product UI — purely an operational tool.
- **WebAuthn ceremony**: `POST /auth/webauthn/register/options` resolves and validates the inviter (or root secret) up front, generates registration options (`residentKey: 'required'`, true discoverable passkey), and signs `{challenge, newUserId, resolvedInviterId, issuedAt}` into an opaque `challengeToken` (HMAC via `tokens.ts`'s `signJson`/`verifyJson`, ~5 min window) → `POST /auth/webauthn/register/verify` trusts the signature rather than re-validating client-supplied ids (no gap between the two calls), verifies the attestation, creates the user/credential/session, and returns `{token, user}` directly in the JSON response — no redirect, so unlike the old OAuth flow there's no one-time exchange code or callback page. Login is the mirror image (`POST /auth/webauthn/login/options` / `/verify`) using an empty `allowCredentials` list so the OS shows its own account picker across whichever passkeys it has for this RP ID. `WEBAUTHN_RP_ID`/`WEBAUTHN_RP_NAME`/`WEBAUTHN_ORIGIN` (comma-separated, so a native app's own origin can be added alongside the web origin) are the relying-party env vars. Since the Bulbord platform rename (2026-08-02): `WEBAUTHN_RP_ID` is deliberately the *parent* platform domain (`bulbord.com`), not the institution subdomain a member actually visits (`WEBAUTHN_ORIGIN=https://nettelhorst.bulbord.com`) — RP ID only needs to be a registrable-domain suffix of the origin, and scoping it to the parent means a member invited into a future second institution's subdomain could reuse an existing passkey rather than registering a new one. `WEBAUTHN_RP_NAME` stays the institution's name ("Nettelhorst"), not "Bulbord" — it's just the friendly label the OS prompt shows, and should match what the member actually recognizes from the join flow.
- **New-member flow**: register a passkey → land on a one-time "set up your profile" step (first/last name + email + role + photo, all required, `PATCH /auth/me`, photo via the existing uploads route with `folder: 'profiles'`) → for Family role, one or more kids/grade (see below) → a one-time "choose friends" step (see Connections below) → `profile_completed_at` (and, once friends is done, `friends_step_completed_at`) get set, which is what tells `JoinGate` the person is a fully onboarded member rather than mid-registration. Email is required starting 2026-08-02 (see Newsletter below, the reason it's collected) — enforced at the application layer only (`validateProfileUpdate` in `api/src/auth/service.ts`, mirroring how `feedback.title` is required with no DB constraint), since `users.email` predates this and stayed nullable/unindexed for accounts created before the requirement existed. WebAuthn's own `userName`/`displayName` are set to a generic placeholder at registration time (the real name isn't known yet) — a known minor limitation is that this placeholder is what a shared device's OS account-picker shows forever, since WebAuthn has no API to rename a credential after creation. **Photo required + required-fields explanation** (feedback #82, 2026-08-14): the photo went from optional to required — Nettelhorst Bulbord is invite-only, and a photo is part of how another member can tell a new account is really who they say they are. Enforced both client-side (`ProfileSetupScreen`'s `canSubmit`) and server-side (`validateProfileUpdate`'s `completingProfile` checks). Rather than a per-field error on a blocked submit attempt, the explanation ("Nettelhorst Bulbord is only for members of the Nettelhorst community — this information lets others verify that you are") is a static line shown directly under the Continue button whenever it's disabled (confirmed with Ben: "show under the continue button when it is greyed out and unclickable"), and hidden once every field is filled. **Kids/grade for Family** (feedback #81, 2026-08-14; count-dropdown revision same day): `user_children` (`user_id`, `grade` — `'pre-k' | 'k' | '1'..'8'`, no name/DOB — restricted like other kid data, see Data safety & classification) is a required step, Family role only ("select a parent" in the original feedback read as the existing Family option, confirmed with Ben) — at least one kid, `ProfileSetupScreen`'s kid list being just an array of grade `IonSelect`s (the array's own length is the "how many kids" count). A "Kids at Nettelhorst" count dropdown (1-5, never 0) drives that array's length directly, replacing an initial "+ Add a kid"/per-row-remove-button design per feedback ("pre-selected to one, don't allow a zero selection, but they can select up to five") — selecting Family pre-seeds one kid at the default grade immediately (`RolePicker`'s `onChange`), so there's no separate "add your first kid" step; changing the count trims or extends the array, preserving already-set grades. Full-replace on every `PATCH /auth/me` that includes `kids` (same posture as feedback_images), not an add/remove diff. Exists specifically to feed the friend-suggestion grade matching below — grade is never shown to other members directly.
- **Role field** (feedback #49, 2026-08-05): `users.role` (`'staff' | 'family' | 'other'`, plain text like every other status column) + `users.role_other` (free text, only meaningful when `role === 'other'`) — collected as a required step in `ProfileSetupScreen`, with a conditional free-text input when "Other" is picked. New signups only, confirmed with Ben — existing accounts stay `null` rather than being retroactively re-prompted, same posture as email's rollout. Surfaced on `/admin/users` next to the joined-date/invited-by line. Ben and Anna's own pre-existing accounts were backfilled to `'family'` by a one-off script (`api/src/auth/backfill-2026-08-05-existing-roles.ts`), since he asked to "call them both parents" directly rather than leave them unset. **Required-field marks** (feedback, 2026-08-06): every `ProfileSetupScreen` field except the photo is mandatory (already true both client-side via `canSubmit` and server-side via `validateProfileUpdate`'s `completingProfile` checks — see above) — now also marked visually with a small red `<RequiredMark />` (`*`) next to each label, since the mandatory-ness wasn't otherwise visible in the UI at all. **Autocomplete attributes** (feedback, 2026-08-06, from a screenshot where Safari's QuickType bar suggested only the saved email address for every field, including First name): First/Last name/Email `IonInput`s gained `autocomplete="given-name"`/`"family-name"`/`"email"` — Ionic's `IonInput` is documented to forward this prop straight to its underlying native `<input>` (necessary since that input lives in closed shadow DOM, unreachable any other way), which is what actually lets a browser distinguish which saved contact-info field to suggest per input rather than falling back to "whatever was used most recently" for all of them. **Role picker rewritten twice** (feedback, 2026-08-06): first pass shortened `IonSelectOption` text to just the role name and added a static bulleted explainer (bold role + plain description) below the field — reverted the same day per direct feedback ("the explanation text should only appear when you click to select, not on the main page"). There's no way to satisfy that with `IonSelect` at all — a plain `ion-select-option`'s display, in every interface mode (action-sheet, popover, alert), always flattens to one plain-text line, so secondary/explainer text can't be shown even inside `IonSelect`'s own picker, only outside it on the page. Replaced entirely with a custom `RolePicker` component: the field itself is a plain `IonItem button` showing the current value (or "Select one") with a chevron, and tapping it opens a real `IonModal` bottom sheet listing all three roles as two-line `IonItem`s (bold name + subtle gray description) — the explainer now only exists while the sheet is open, never on the main form. Still built entirely from standard Ionic primitives (`IonModal`/`IonRadioGroup`/`IonRadio`/`IonItem`/`IonLabel`), not a hand-rolled equivalent — just composed directly instead of reached for via `IonSelect`'s higher-level convenience wrapper, which structurally can't do this. **Truncation bug** (feedback, 2026-08-07): the initial version put the label+description as `IonRadio`'s own children (the rich-children-as-label pattern the newsletter `IonCheckbox` uses) — which silently clipped the Family option's longer description, since `ion-radio`'s internal label-text-wrapper is hard-coded `white-space: nowrap; overflow: hidden` in its shadow CSS with no exposed `part` to override it from outside. Fixed by moving to Ionic's standard list pattern instead — `IonLabel className="ion-text-wrap"` (with `<h2>`/`<p>` for the two lines) as the item's default content, `IonRadio slot="end"` alongside it — which wraps normally since it isn't relying on `ion-radio`'s own constrained label slot at all. Same feedback also simplified the Family description ("You are family of a kid at Nettelhorst," down from a longer parenthetical) and swapped every option's "the school" wording for "Nettelhorst" by name, matching how "Other"'s description already named it. **Testing gotcha this surfaced**: `IonModal`'s React wrapper portals its actual content straight to `document.body` (or `ion-app` if present) via `createPortal` rather than rendering it as a light-DOM descendant of wherever the component appears in JSX — the JSX location gets only an empty `<template>` marker. `keepContentsMounted` (set on this modal) is required for the content to exist at all before the sheet is first opened, but even then it's only reachable via `document.body.querySelector(...)`, never via RTL's own `container`/`canvasElement` — see `JoinGate.test.tsx`'s `roleRadioGroup()` helper and `ProfileSetupScreen.stories.tsx`'s `setRole()`, both new. Worth remembering alongside this file's other `IonModal` async-lifecycle gotcha (Testing section) if a future overlay component's content mysteriously isn't found by a query scoped to the render container.
- **Duplicate-account merge** (2026-08-05): Anna ended up with two active accounts (a second passkey registration created a new account instead of adding a credential to her existing one). `api/src/auth/backfill-2026-08-05-merge-duplicate-anna.ts` is the one-off pattern for this: reassign passkeys/sessions/roles directly (no uniqueness constraint), reassign event/camp interests only when the surviving account doesn't already have a conflicting row for that same event/camp (drop the old one if it does, per the unique `(user_id, event_id)` index), reassign comments/feedback/submitted-listing authorship directly, then soft-delete the losing account. Confirmed with Ben: keep the newer account, don't worry about perfectly preserving the older one.
- **Profile photo crop** (feedback #56, 2026-08-05, revised 2026-08-06): `web/src/uploads/CropModal.tsx` (`react-image-crop`, the only new runtime dependency this added) — a crop step before upload, wired into `ProfileSetupScreen`'s photo picker only (confirmed with Ben: profile photos are the one upload flow where exact framing matters; feedback/event/camp photos render at flexible aspect ratios already and don't get this treatment). `useImageUpload`'s `attach()` was widened to accept a `Blob` (not just `File`) so the cropped canvas output can be passed straight through without wrapping. Originally built on `react-easy-crop` — a fixed circular frame you pan/zoom the image within — reversed 2026-08-06 per direct feedback ("you expect to be able to highlight an area... pretty standard to have this kind of image cropping for a profile picture"): swapped for `react-image-crop`, a draggable/resizable selection box (8 real corner/edge handles) over the full, unmodified photo — the standard pattern (GitHub, Slack, etc. avatar uploaders all use this shape), native mouse/touch support, no separate zoom control needed since shrinking the box is the zoom. `aspect={1}` keeps the box always square (so the stored file stays square, matching `Avatar`'s circular CSS treatment of it elsewhere) while `circularCrop` renders the selection overlay itself as a circle, so it's visually obvious what the final avatar will look like while still freely draggable/resizable.
- **Native app passkey continuity** (Capacitor): see Platform strategy below.
- **De-emphasized passkey sign-in + About link on the join screen** (feedback #84/#85, 2026-08-14): "Sign In With Passkey" was a full-width outline `IonButton` competing visually with the primary Accept/Continue button — replaced with plain gray underlined text ("Sign In") at the same weight as the "Already on Nettelhorst Bulbord?" line above it (`JoinGate.tsx`'s shared `SignInLink`, used by both `InviteAcceptCard` and the no-invite dead-end state). Shrunk further the same day, per follow-up feedback that it was still too prominent at default paragraph size — `SignInLink` is `0.8125rem`, matching this screen's other small-print text. Separately, `BrandHeader` (shown on every logged-out state) gained a "Learn more" link, same gray/underlined treatment, to the real About page — reachable pre-auth via a narrow bypass in `JoinGate`: it renders `AboutPage` directly whenever `location.pathname === '/about'` and the visitor isn't yet a full member, rather than duplicating About's content into a second logged-out-only copy. Once a member, `/about` is reached the normal way, as one of the routes `JoinGate` gates access to.

## Connections (friends)
- **One-directional "add," no approval needed** (feedback #83, 2026-08-14): `user_connections` (`user_id` = the adder, `connected_user_id` = the one added, unique on the pair, toggled via `deletedAt` like `event_interests`) — adding is instant, mirrors the existing star/interest pattern rather than a request/accept flow. A mutual pair (both rows present) renders as "Friends"; one-directional renders as "Following" (from the adder's side) or "Added You" (from the other side — the prompt to add back). Feature folders: `api/src/connections/` (`service.ts` for the DB-touching CRUD/query functions, `logic.ts` for the pure, unit-tested mutual-state-derivation and suggestion-list ordering/dedup — split out the same way `events/comment-permissions.ts`/`camps/grouping.ts` keep the genuinely testable logic out of the DB plumbing, `template.ts` for the alert email's subject/HTML, `routes.ts` for the HTTP surface), mirrored by `web/src/connections/` (`api.ts` client, `ChooseFriendsScreen.tsx` for onboarding, `FriendsPage.tsx` for the ongoing Friends/Following/Added-You view).
- **Email alert on add** (confirmed with Ben: "alert the other person so they can friend back," delivered via email over an in-app-only notification since there's no notification inbox in this app): `addConnection()` sends a short transactional email (`connections/template.ts`) via Resend, reusing `newsletter/mailer.ts`'s client — that module's `sendNewsletterEmail` was generalized to `sendEmail(to, subject, html)` for this (feedback #83 is the second real caller, after the newsletter itself), rather than standing up a second Resend client. Only fires the first time a given pair's edge is actually created/reactivated (a repeat `POST /connections` on an already-active edge is a no-op, no repeat email) and is best-effort — a failed send (logged, not thrown) doesn't undo the add, same graceful-degrade posture as image enrichment/title-normalization elsewhere in this codebase.
- **Onboarding suggestions** (`GET /connections/suggestions`, `ChooseFriendsScreen.tsx`): in priority order — the inviter, then the inviter's own connections, then other Family-role members with a kid in the same grade as one of the viewer's kids (see Login's kids/grade bullet) — deduped, excluding the viewer and anyone already connected. `GET /connections/members?q=` (name search, any member, name/avatar only — same exposure as the existing invited-by social graph) covers everyone else, per Ben's "at the end, there should be a search that allows you to find anyone else." Adding a suggested person appends *their* own connections to the bottom of the list (`GET /connections/of/:userId`) — "as you add potential friends, suggest their friends at the bottom of the list."
- **Required step, optional picks** (confirmed with Ben): `users.friends_step_completed_at` (nullable timestamp, same shape as `profile_completed_at`) gates `JoinGate` into showing `ChooseFriendsScreen` once after profile setup, so it doesn't re-show on another device — but picking anyone during it is optional; Continue/Skip both just call `POST /connections/finish-onboarding` and proceed either way.
- **Friends page** (`/friends`, linked from Account): three sections — Friends (mutual), Following (you added, no reciprocation yet), Added You (they added you — an "Add back" button right there, reachable from the alert email's link too). `GET /connections` returns all three, derived by `connections/logic.ts`'s `deriveConnectionsState` from the two raw edge queries (`listOutgoingConnections`/an internal incoming-edges query) rather than a third denormalized "mutual" column.
- This pass is capture-and-display only — no other feature (e.g. event/camp social proof) reads the connection graph yet; revisit if a real need for that shows up.

## Feedback tab
- Third tab (alongside Events/Camps): a plain running list of title+description postings, newest first — a place for feature requests/notes while the app is being built. Feature folder: `api/src/feedback/`, `web/src/feedback/`.
- Deliberately unmoderated, unlike the events/camps suggestion queue above: `GET /feedback` (gated behind `requireAuth` like every route since the invite-only rework — see Product shape — not actually public despite this line's earlier wording) has no `pending`/`approved` status, and `POST /feedback` (any logged-in member) goes live immediately. Only Ben posts today, so this is a scope choice, not an oversight — revisit (add a `status` column + the same approver-role gate as events/camps) if feedback is ever opened up to a wider audience and unmoderated posts become a problem.
- Still follows the recoverability rule: `deleted_at` soft-delete column present (no delete route built yet), and every POST/PATCH writes an `events_log` entry (`feedback_created`/`feedback_updated`).
- Every item carries a small, permanent, subtle reference number (`#28`, shown next to the author/date line) so a specific piece of feedback can be referred to unambiguously in conversation instead of by title or UUID — `feedback.number`, backed by a dedicated Postgres sequence (`feedback_number_seq`) rather than the row's own primary key, assigned in creation order across all feedback ever posted (open and closed) and never reused, even if a row is later soft-deleted.
- **Author edit** (feedback #39, 2026-08-03): a post's own author — and only the author, no admin override, unlike event comments' delete-for-moderation carve-out — can edit its title/description/photos via `PATCH /feedback/:id`, gated by `canEditFeedback` (`api/src/feedback/permissions.ts`, a pure dependency-free function mirroring `events/comment-permissions.ts`'s unit-testable shape). The frontend shows a pencil icon only when the API's per-viewer `can_edit` field is true.
- **Multiple photos per post** (feedback #40, 2026-08-03): a post can now carry more than one photo. `feedback_images` (one row per photo, `position`-ordered — several rows inserted in one statement can share the same `created_at`, so position is the real sort key) replaced the single `feedback.image_url`/`thumbnail_url` columns; the migration that dropped those columns backfilled existing single-photo posts into the new table first. Editing photos is always a full replace, never a diff: the edit form resends the complete desired set (kept + newly attached), so `PATCH /feedback/:id` soft-deletes the old rows and inserts the new set fresh rather than reconciling an add/remove list. `web/src/feedback/useMultiImageUpload.ts` wraps the shared `useImageUpload` hook (also used by the profile-photo step) to manage an array instead of a single value, uploading multiple attached files in parallel.
- **Backlog** (feedback #52, 2026-08-05): a third state alongside open/completed, for an item that's good but deliberately deferred rather than done — `feedback.backloggedAt` (nullable timestamp, same shape as `completedAt`), toggled by an admin-only clock icon next to the checkmark (`POST /feedback/:id/backlog` / `/unbacklog`). Mutually exclusive with completing an item (an item is backlogged OR completed, not both — the backlog toggle only shows while `!completed_at`). Rendered as its own collapsed accordion section between Open and Closed. Applied immediately to #53 (play date) and #54 (babysitter), since both said in their own text they belonged there.
- **In Progress** (feedback #79, 2026-08-14): a fourth state, for an item Claude has already picked up but that's now blocked on something only Ben can do (pasting a DNS record, clicking through an App Store Connect screen, approving a Railway plan change) — distinct from Backlog, which is a deliberately deferred item nobody's actively waiting on. `feedback.inProgressAt` (nullable timestamp, same shape as `backloggedAt`), toggled by an admin-only hourglass icon next to the backlog clock icon (`POST /feedback/:id/start-progress` / `/stop-progress`). Mutually exclusive with Backlog specifically — `api/src/feedback/routes.ts`'s `setSideState` helper (parameterized over which of the two columns to write) clears the other column whenever one is set, so an item is never shown in both sections at once. Rendered as its own collapsed accordion section between Open and Backlog.

## Sharing
- One mechanism, not two: a persistent, always-visible share button (present on every page) opens a fullscreen modal with a QR code encoding whatever page the visitor is currently on — the app root, `/events`, or a specific event's detail page. Built for local/in-person sharing (shown at pickup, scanned phone-to-phone), so pointing at the current page (including a specific listing) is the intended behavior, not a gap. Generated client-side (`web/src/sharing/ShareButton.tsx`, `qrcode` package) — no third-party service ever sees the URL.
- Since 2026-08-01, this same URL also doubles as the app's only invite mechanism: it carries `?invite=<your user id>` whenever you're logged in (see Login above). A member sharing "the current page" and a member inviting someone new are the same action now — the destination page just doesn't render for a non-member until they've joined, at which point they land on whatever was originally shared.
- This supersedes an earlier draft that split "app-level" (invite-only, never a specific listing) from a separate not-yet-built "listing-level" share mechanism, and also the 2026-07-31 confirmation that the QR would never carry an invite. Revisit only if a real need emerges for a share surface that must NOT reflect the current page.
- **Native OS share sheet** (feedback #58, 2026-08-05): the modal also has a "Share via Text, Email, etc." button using `navigator.share({ url })` — opens the phone's real share sheet (Messages, Mail, whatever's installed), feature-detected (`typeof navigator.share === 'function'`) so it's simply absent on a browser without support (e.g. plain desktop Chrome) rather than a dead button. An "— or —" divider sits between the QR instruction and this button, shown/hidden together with it, to mark it as an alternative to scanning rather than a second unrelated action.
- **No raw URL as visible text** (feedback, 2026-08-05): the modal used to show the bare `https://...` link as plain text under the QR code — dropped entirely ("no reason for an HTTPS URL written out as plain text"). The link still exists (it's what the QR encodes, and it's in the QR `<img>`'s `alt` text for accessibility/testing), just never rendered as its own visible line. In its place, an instruction line reads "Have your friend scan this QR code to join Nettelhorst Bulbord" — "Nettelhorst Bulbord", not bare "Nettelhorst", matching the join screen's own app-name convention (see the 2026-08-03 Status-of-decisions entry on that).
- **Add to Calendar** (feedback #76, 2026-08-14): both event and camp detail pages ("the drill down section") get an "Add to Calendar" button — an `IonActionSheet` offering Google Calendar and Outlook.com (each opens a prefilled web composer in a new tab) and a downloaded `.ics` file (Apple Calendar, Outlook desktop, and anything else that imports one) — confirmed with Ben as the "standard platforms." Built as shared, generic infra (`web/src/calendar/AddToCalendarButton.tsx` + `calendarLinks.ts`), the same bar as `ShareButton`/`Avatar`/`dayLabel.ts`, since Camps can't import from `events/` (see Camps' "fresh, non-shared clone" bullet) — not a per-feature copy. No timezone-conversion logic anywhere in it: every date/time in this app is already a plain, timezone-less local value (see `api/src/db/schema.ts`'s `date`/`time` columns), so every calendar target gets a "floating" local time with no UTC/offset suffix — the same convention RFC 5545 itself uses for a timezone-less `DTSTART`, consistent with how the rest of this codebase never does timezone math client-side (`dayLabel.ts` parses dates the same way). A timed event/camp with no explicit end time gets a one-hour default block. A multi-day camp (`start_date !== end_date`) always becomes an all-day calendar block spanning the whole range regardless of `start_time`/`end_time` — a specific daily time window repeated across several days can't be represented as one calendar event without a recurrence rule, which this deliberately doesn't build; only a genuinely single-day camp's own `start_time`/`end_time` become a timed block. No dependency added — the ICS file and both calendar-service URLs are hand-built (~150 lines, unit-tested in `calendarLinks.test.ts`) rather than reaching for an npm package.

## Platform strategy
- **Native app as the primary surface** (feedback #61, 2026-08-07): Ben wants the iOS/Android apps to become how most members actually use Bulbord — he'll keep using the web version himself as a beta tester, but a home-screen app icon is what keeps a casual member from losing track of the site entirely. This reverses the "no native release until the web product is proven" posture below into "start the release process now," since App Store/Play Store review and account approval have long, largely fixed timelines that don't shorten by waiting.
- **WebView-shell architecture, not a bundled build** (confirmed with Ben, 2026-08-07): `web/capacitor.config.ts`'s `server.url` points the native shell at `https://nettelhorst.bulbord.com` live, instead of Capacitor's default of bundling `web/dist` into the binary. This is the actual mechanism behind "update as easily as the website" — a normal `railway up` web deploy reaches every installed app instantly, with zero store resubmission; only shell-level changes (native plugins, `capacitor.config.ts`, icons) ever need a new review cycle. `webDir: 'dist'` is still required by Capacitor's config type and by `cap sync`, but its contents are never actually loaded while `server.url` is set. Tradeoff: no offline access to a previously-loaded page (pure a network dependency, consistent with this file's existing "usable on a slow connection, not usable with none" performance target) — acceptable since nothing about this app is meant to work offline today.
- **Apple review risk (Guideline 4.2, minimum functionality)**: a pure WebView wrapper risks rejection as "not different enough from a mobile browser." Mitigated by real native device capability already built for other reasons — native passkey/WebAuthn sign-in via the OS credential manager (not a web fallback) and the native share sheet (`navigator.share`, feedback #58) — lead with these if a review flags it. See `store-listing-notes.md` (repo root) for the drafted App Store Connect / Play Console submission copy, privacy questionnaire answers, and this talking point.
- **When a web-only change needs a fresh App Store review, not just a deploy** (confirmed with Ben, 2026-08-13): because of the WebView-shell architecture above, the default is that *no* web/API change needs a new native build or review — that's the whole point of `server.url`. The trigger for deliberately cutting a new build and resubmitting isn't "the feature is big" or "the code changed a lot" — it's whether the feature crosses into territory the current App Store approval doesn't cover, specifically:
  - **Real-people matching/connection features** (Guideline 1.2, User-Generated Content) — e.g. the future babysitting finder connecting parents and babysitters. Apple requires the app to actually *implement* content filtering, a report-abuse mechanism, block functionality, and published contact info for this kind of feature — this is real product work to do before shipping, not just review paperwork.
  - **Any feature that collects, transmits, or can share personal information about a minor** (Guideline 5.1.4(b)) — triggers a requirement for a privacy policy that specifically addresses children's data and compliance with applicable children's privacy statutes. This applies the moment kids' names/ages/health info (already classified Restricted under Data safety & classification above) flows through a feature Apple hasn't reviewed — it is not limited to apps in the Kids Category.
  - **Any new payment-collection mechanism** — worth re-checking Guideline 3.1.3(d) (real-time person-to-person services, e.g. babysitting payments, may use non-IAP payment methods — this is favorable, and consistent with this app's existing processor-delegation plan under Data safety & classification) and 3.1.1 (In-App Purchase requirement for digital goods) against the specific mechanism being built, since the exemption depends on the details.
  - The general test, per Guideline 2.3.1(a) ("don't include any hidden, dormant, or undocumented features... all new features, functionality, and product changes must be described with specificity in the Notes for Review"): would a reviewer, reading the *current* Notes for Review, actually recognize what the app does today? If a new feature would require materially different review notes to describe honestly, resubmit — even though the WebView shell itself won't need to change — specifically so Apple signs off on the new capability (and the safety/privacy work it requires) before it's live to everyone, rather than it being discovered later via complaint or spot-check.
  - This list is illustrative, not exhaustive, and Apple's guidelines change over time — before shipping a feature that changes *who* the app connects, *what data about someone other than the account holder* it collects (especially about children), or *how money moves*, re-check the current guidelines rather than trusting this file's citations to still be accurate.
- **No physical Mac required for iOS builds**: iOS code signing doesn't actually need Xcode running on hardware anyone owns — `web/ios/App/fastlane/Fastfile` runs entirely on GitHub Actions' `macos-latest` runner (`.github/workflows/mobile-ios.yml`, `workflow_dispatch`-only, not part of every-push CI). Android needs no macOS at all — `web/android/fastlane/Fastfile` builds on a standard Linux runner (`.github/workflows/mobile-android.yml`) with Google Play App Signing holding the real release key, and only a locally-generated upload key (`keytool`, instructions in the workflow's own header comment) as a repo secret.
  - **iOS pipeline verified end-to-end 2026-08-12**: a real signed build (version 1) reached App Store Connect and is processing for TestFlight. Getting there surfaced several real gotchas worth knowing before touching this again: (1) `get_certificates`/`sigh`'s own "reuse a cert already installed locally" check always misses on a fresh CI runner (no persistent keychain between runs), which mints a brand-new Distribution certificate every single run — and Apple caps how many can be active at once, so a handful of retries exhausts the account's quota outright (`"reached the maximum number of available Distribution certificates"`, hit for real during this pass). Fixed by generating **one durable certificate once** (directly via the App Store Connect REST API, not through fastlane) and importing it fresh into each run's keychain instead — `IOS_DIST_CERT_P12_BASE64`/`IOS_DIST_CERT_PASSWORD` repo secrets, `DIST_CERT_ID` constant in the Fastfile. This is the same underlying problem `match` solves with a git-backed store, just without standing up a separate certs repo for a single-maintainer app. (2) Exporting that `.p12` with OpenSSL 3.x's default cipher/KDF (AES-256/PBKDF2) fails macOS Keychain import with a misleading `"MAC verification failed during PKCS12 import (wrong password?)"` **even given the correct password** — macOS's `SecKeychainItemImport` only understands the older SHA1/RC2/3DES format, so the `.p12` must be exported with `-legacy`. (3) `set_key_partition_list` (needed so `codesign` can use the imported key non-interactively) is **not a bundled fastlane action** despite widespread references to it that way — it's a raw `security set-key-partition-list` shell invocation, same as `match`'s own internals use. (4) The App Store Connect API flatly disallows creating a new **app record** via API (`POST /v1/apps` → 403, "Allowed operations are: GET_COLLECTION, GET_INSTANCE, UPDATE") — this is the one setup step that genuinely requires the App Store Connect website; everything else (bundle ID registration, capabilities, certificates, provisioning profiles) works fine via direct REST calls. (5) The Xcode project needs an explicit `update_code_signing_settings` call (manual signing, real team/cert/profile) before `build_app` — its default automatic-signing state has no team configured, since no one had ever opened it in real Xcode before this pipeline existed.
  - **iOS app actually submitted for App Store review 2026-08-12** (build 12, `com.bulbord.app`) — the icon (see Design system's app-icon note below), TestFlight internal testing, and the full submission itself were all done via direct App Store Connect REST API calls rather than the website, including the final `POST reviewSubmissions` + `PATCH {submitted: true}` that actually starts Apple's review clock. Same trust model as the existing `?invite=`/`?rootSecret=` query-param mechanisms, just delivering a valid session via URL instead of requiring the WebAuthn ceremony.

## Application architecture
- Single repo, single Postgres database, single Node/TypeScript API server. Don't split services or add databases without a strong, explicit reason.
- Frontend: Ionic React + Vite, TypeScript strict mode.
- Backend: Node.js API server (Fastify), TypeScript strict mode.
- ORM: Drizzle (schema-as-TypeScript, close to raw SQL) — chosen partly because its transparency makes it straightforward to build a generic DB browser directly off the schema.
- Hosting: Railway (project `bulbord`). The deciding criterion is API/introspection access for Claude, not dashboard ease-of-use for Ben — Railway ships a local MCP server, a hosted remote MCP server (mcp.railway.com), and an agent-oriented CLI, so I can deploy, inspect logs, and manage the database directly instead of working around a plain REST API. Railway also added Postgres PITR (Pro tier, ~7-day WAL-archive window), closing the backup gap that used to favor Render. Accepted trade-off: Railway has no free tier and a weaker 2025-2026 reliability record than Render — fine at this stage, worth revisiting if uptime becomes business-critical. Fly.io stays ruled out (deprecated unmanaged Postgres, heavier Dockerfile-based deploy). Live at `bulbord.com` (landing page) and `nettelhorst.bulbord.com` (the Nettelhorst institution's app) since the Bulbord platform rename (feedback #32, 2026-08-02) — WebAuthn's `WEBAUTHN_RP_ID`/`WEBAUTHN_ORIGIN` and CORS are already cut over to the new domains (see Login above), not pending.
  - Deploying: each service (`api`, `web`) is deployed independently via `railway up . --path-as-root --service <name> --environment production --ci` run from inside that service's own directory (`api/` or `web/`). The `--path-as-root` flag is required — this is a monorepo and Railway's builder (Railpack) can't identify the app if it's uploaded from the repo root instead of the service's subdirectory; omitting the flag produces a build failure with no useful error beyond "Railpack could not determine how to build the app." (The web service was renamed from `campy` to `web` on 2026-08-03, alongside the Railway project itself being renamed from `campy` to `bulbord` — both via the `railway api` CLI's raw GraphQL access, `projectUpdate`/`serviceUpdate` mutations, since neither has a dedicated CLI flag or MCP tool.)
  - One-off scripts against the production DB (seeding, corrections) run locally with `DATABASE_URL` overridden to the Postgres service's `DATABASE_PUBLIC_URL` (get it via `railway variables --service Postgres --environment production --kv`) — the default `DATABASE_URL` uses Railway's internal-network hostname (`postgres.railway.internal`), which only resolves from inside Railway, not from `railway run` on a local machine.
  - Ship-and-verify is part of finishing a change, not a separate step: commit, push to `origin/main`, `railway up` the affected service(s), then confirm the change is actually live (e.g. curl the served HTML/asset and check the built hash or content) before telling Ben to look at it. Never end a task on "committed locally" or "deployed" without having checked the live response.
- API conventions: REST modeled on Stripe's API design — plural resource-based URLs, standard HTTP verbs, one consistent error-object shape, cursor-based pagination. Chosen because it's a widely-known, well-documented reference standard rather than something invented per feature.
- Database naming: snake_case, plural table names, UUID primary keys, `created_at`/`updated_at`/`deleted_at` on every table, singular `_id` foreign key columns. Standard Rails-derived convention; pairs directly with Drizzle's schema style.
- File organization: feature-based (vertical-slice), not layer-based — code for `events`, `camps`, `auth`, `admin`, etc. is colocated (routes, db access, components, tests together) rather than spread across parallel `routes/`, `models/`, `components/` trees. Makes a whole dead feature visible as one unused folder instead of scattered orphaned files (see Code hygiene below).

## Local development
- The full stack runs locally with one command: `npm run dev` from the repo root (root `package.json`, `concurrently` running docker-compose, the API dev server, and the web dev server together). Tests always run against this local database, never against the Railway production database — the day-to-day test loop must not depend on cloud access or risk touching real data.
- Schema changes go through Drizzle Kit migrations checked into the repo. Never hand-edit the schema directly against any database — this keeps the schema, the admin table-browser, and the codebase from drifting apart.

## Data safety & classification
- Nothing is publicly queryable without an account anymore (see Product shape's invite-only model) — the distinction below is now about what's visible to *any* member versus what's restricted further, not public-vs-private.
- Member-visible (any invited member): service/business listings — camp and event details (name, schedule, price, location, description), and the basic invited-by social graph (name/photo only, see Login).
- Restricted (least-privilege even among members): anything more sensitive that's personal data about a specific person — babysitter profiles/contact info, booking details, kids' names/ages/health info. A user sees their own data and what's needed for an active transaction. Broader visibility for social proof (e.g. "who from school is going," per `readme.md`) is a deliberate feature but must expose attendance signals only, never raw contact/health/PII fields.
- Admin (Ben) can see all of the above via the in-app admin panel, for support/moderation.
- Secrets (DB URL, session secret, root invite secret, etc.) live in a gitignored `.env`; a checked-in `.env.example` documents every required variable. Never commit secrets.
- Payment info is never stored directly in our database — booking payments are delegated to a processor (e.g. Stripe) and we store only tokens/references, not raw card data. This is a hard rule to apply from the first line of booking code, not a retrofit.

## Data recoverability & Claude's production-database boundary
- Nothing is ever hard-deleted from application code: deletes set a `deleted_at` timestamp (soft-delete) rather than issuing SQL `DELETE`, so in-app mistakes are always reversible.
- Every mutation and deletion is also captured in `events_log` (actor, action, metadata, timestamp) — an audit trail independent of the row itself.
- Railway Postgres PITR (opt-in, ~7-day WAL-archive window) is the infra-level safety net underneath both of the above, for catastrophic cases (bad migration, bug) that soft-deletes don't cover.
- Local database: fully self-serve — migrate, seed, reset freely without asking.
- Railway production database: also self-serve — Claude runs schema migrations and manages data there directly, without pausing to ask first. The policy is recoverability, not a confirmation gate: soft-delete + audit log + PITR (above) must always be in place and trustworthy, and that's what's allowed to substitute for asking. Hard deletes from application code are still never issued, regardless.

## Events data model & sourcing
- `events`: title, description, start_date, start_time (nullable — null means no specific time, distinct from `all_day`), all_day boolean, address, location_name (nullable — a human-friendly place name, e.g. "Merlo Library", shown in place of the raw address in list contexts; falls back to the address when absent), latitude/longitude (nullable, populated opportunistically — not a live geocoding integration), source_url, source_id (real FK to `event_sources`, alongside `source_url` which stays the free-text per-occurrence dedup key), image_url/thumbnail_url (nullable, see Images & object storage below), status (`pending`/`approved`/`rejected` — the same pending-review/approver-role model as user-submitted suggestions, see Product shape above), submitted_by_user_id (nullable — null means system-sourced), approved_by_user_id, plus the standard created_at/updated_at/deleted_at.
- `event_sources`: id, name, url, type (`generic_search` / `website` / `facebook_group` / `open_data` / …), is_active, last_checked_at, notes (free text — e.g. what to scope a broad source down to, or why a lead was skipped) — lets specific sources (a park district page, a school PTA calendar, a neighborhood FB group) be added later without a schema change. Prefer a real queryable open-data API over hand-searching when one genuinely exists for a source (e.g. Chicago's CDOT block-party permit dataset on the Socrata-based city data portal, `type: 'open_data'`) — a one-off script can query it live and is safely rerunnable to pick up newly-published data, rather than hardcoding a point-in-time result.
- One reusable ingestion operation (not per-trigger code) takes candidate events, upserts them (deduped on title+start_date+source_url), and writes `events_log` entries. A manual sourcing pass, a future daily job, and future per-source scrapers all call this same path — automating it later changes what triggers it, not how it works. It also opportunistically enriches each newly-inserted event with an image (see below) before logging.
- Sourced events default to `pending`, same queue as user suggestions, until there's an admin UI to review them. Manually-vetted seed batches (reviewed live with Ben, no UI yet to do it another way) are the one exception, inserted as `approved` directly.
- **Member self-service event posting** (feedback #46, 2026-08-03): any logged-in member can post their own event via `POST /events` — deliberately bypasses the `pending` queue above and goes live as `approved` immediately, same unmoderated posture as the Feedback tab (see Feedback tab section) rather than the sourced-event suggestion model; confirmed explicitly with Ben rather than assumed. Only `title`, `address` ("Location" in the form), and `start_date` are required; description, time/all-day, source URL, and a single optional photo (uploaded via the generic `POST /uploads` route's new `'events'` folder) are all optional. The submitter can edit (`PATCH /events/:id`) or delete (`DELETE /events/:id`, soft-delete) their own event — creator-only, no admin override, same posture as feedback-post edits (feedback #39) — gated by `api/src/events/permissions.ts`'s `canEditEvent`, a pure dependency-free function unit-tested the same way `feedback/permissions.ts` and `events/comment-permissions.ts` are. Editing does **not** reset status back to `pending` — confirmed with Ben, a deliberate simplification since there's no pending step to return to. The API exposes a per-viewer `can_edit` field (same shape as feedback's) so the frontend only shows the edit-pencil/delete-trash icons to the actual submitter. A self-submitted event has no `source_url`, so it already falls into its own single-row partition in the next-occurrence-collapse dedup logic below (via the existing `coalesce(source_url, id)` fallback) rather than needing any special-casing. Building the edit/delete flow surfaced a real Ionic gotcha worth reusing: `IonRouterOutlet` keeps a popped page's React state alive (hidden via `.ion-page-hidden`, not unmounted) for the back-transition, so `EventsPage`'s original mount-once `useEffect` never saw an edit/delete made on the detail page — a member deleting an event and navigating back would still see it in the list. Fixed by switching `EventsPage`'s fetch to Ionic's `useIonViewWillEnter` lifecycle hook (fires on every entry, including the first), which is now this codebase's first use of that hook — reach for it instead of `useEffect(fn, [])` on any list/page whose data can be mutated from a page pushed on top of it. **Poster attribution + avatar placeholder** (feedback, 2026-08-03; superseded 2026-08-14 — see Images & object storage's NOT NULL entry below): every event response now carries a `submitted_by: {name, avatar_url} | null` field (`api/src/events/routes.ts`'s `submittedByExpr`, a scalar subquery on `submitted_by_user_id` mirroring `interestedCountExpr`'s shape — null for system-sourced events, since there's no submitter row to join). The frontend shows "Posted by {name}" on the event detail page, and — since a member-submitted event had no source page to enrich an image from — used to fall back to the submitter's own `Avatar` (photo or initials) in place of a thumbnail/hero image whenever the event had none of its own. That fallback is now unreachable in practice (`event.image_url` is never null since `events.image_url` became `NOT NULL`, always a real photo or a generated placeholder) but is still there defensively in `EventsPage.tsx`/`EventDetailPage.tsx` — harmless dead-in-practice code, not worth stripping just to chase the new invariant. The "Posted by {name}" text line is unaffected either way.
- **Hidden repeating-event reveal** (feedback #48, 2026-08-03): the next-occurrence-collapse below (one row shown per recurring series) used to suppress later occurrences with no indicator at all. `GET /events` now also returns `hidden_count` — the total occurrences currently suppressed across the whole upcoming window (a second lightweight query reusing the same `next_occurrence` CTE, counting `rn > 1`) — and accepts `include_hidden=true` to bypass the collapse entirely and return every occurrence. `web/src/events/EventsPage.tsx` shows a subtle "Show N hidden repeating events" row inside the New accordion section (see below) when `hidden_count > 0`; tapping it refetches with `include_hidden` and replaces the list. Revealed occurrences behave as ordinary independent event rows from then on (their own id, their own interest state) — this is a one-time reveal for the current page view, not a persisted per-user preference.
- **Accordion sections replaced the New/Starred/Dismissed tabs** (feedback #60, 2026-08-06; Dismissed folded back into the same accordion group 2026-08-14): `EventsPage.tsx` renders three `IonAccordion` sections ("Starred", "New", "Dismissed") inside one `IonAccordionGroup multiple` — same pattern Camps already uses, collapsed by default (Ionic's own default, confirmed against Camps' identical behavior). Dismissed events still render dimmed with a small "DISMISSED" label per row (unchanged), but the section itself is now a real accordion header (muted icon/label color, same square/chevron shape as Starred/New) rather than the earlier plain centered "Show N dismissed events" link that swapped itself for a flat list on tap — feedback, 2026-08-14: "should look just like the new and star sections... same kind of square drop down." Dismissed events are already present in the one `GET /events` fetch (no server-side suppression), so expanding the accordion is purely a client-side reveal, same as before — there's just no separate `dismissedRevealed` state anymore, since `IonAccordionGroup`'s own expand/collapse *is* the reveal now.
- Daily automated sourcing (not yet built): a scheduled trigger re-runs the ingestion operation against `event_sources` plus a generic-search fallback. Mechanism undecided — a Claude Code scheduled cloud routine or a Railway cron service are both viable; the schema and ingestion-script boundary work with either.
- Facebook-authenticated sourcing (not yet built, explicitly deferred): needs its own secrets handling (Railway env vars only, never the repo) and a look at Meta's ToS for automated login before building.
- **Source detail view** (`GET /event-sources/:id`, `web/src/events/SourceDetailPage.tsx`, linked from the plain list at `SourcesPage.tsx`): shows a source's notes, when its most recently-ingested event was added, a "likely stale" flag (no new event ingested in ~30 days — a signal about the ingestion pipeline going quiet, not a judgment about how far out the events themselves are dated), and its own upcoming events (next-first, past events excluded — a "what's coming up," not "full history," view). The event count shown is the approved+upcoming subset specifically — i.e. what a member would actually see on the Events tab right now — not a raw all-time count of everything ever ingested from that source.
- **Interest/attendance social proof**: `event_interests` (user_id, event_id, status: `interested`/`dismissed`, unique on (user_id, event_id), toggled via `deleted_at` rather than inserted/deleted per swipe) backs the Events tab's swipe-right-to-mark-interested / swipe-left-to-dismiss mechanism, which replaced an earlier star-to-favorite model on 2026-07-31. Each event also carries an `interested_count`/`interested_names` — shown as a teaser ("3 interested: You, Alice and Bob", truncated to fit) on both the events list and detail page, tap-through to the full list of interested members' names+avatars (`GET /events/:id/interested`) — attendance-signal social proof only per Data safety & classification above, names/avatars never contact info. The viewer's own name is substituted with "You" server-side.
- **Title simplification** (feedback, 2026-08-02): long, verbose scraped titles ("Toyota Movie Nights at Gallagher Way: Happy Gilmore") read poorly at large zoom/text sizes and duplicate what `location_name` already shows. `events/title-normalization.ts`'s `simplifyTitle()` calls Claude (model `claude-opus-5`, low effort — a deliberately cheap/fast call for a short rewrite task) to drop sponsor branding, drop location text redundant with `location_name`, and trim wordy qualifiers, while keeping a recurring series' brand name and the occurrence-specific differentiator (a movie title, a workshop topic). Called once per candidate inside `ingestEvents()` in `ingest.ts` — before the dedup lookup, not after, so a later re-ingestion of the same source page dedups against the already-simplified title instead of drifting into a duplicate row. Optional: with no `ANTHROPIC_API_KEY` set, or on any API failure, it returns the title unchanged rather than blocking ingestion — same graceful-degrade posture as image enrichment leaving `image_url` null. `events/backfill-2026-08-02-simplify-titles.ts` applied the same simplification once, retroactively, to the 54 events approved before this shipped — using an explicit hand-verified title mapping (not a live model call) so the result matched exactly what was reviewed with Ben before writing.

## Camps data model & sourcing

- **Deliberately fresh, non-shared clone of Events** (feedback #50, 2026-08-04): the Camps tab is built as its own vertical slice — `api/src/camps/` and `web/src/camps/` mirror the events feature's file-for-file shape (`permissions.ts`, `comment-permissions.ts`, `comments.ts`, `routes.ts`, `CommentsSection.tsx`, `InterestedBadge.tsx`, `format.ts`, `CampSourcesPage.tsx`/`CampSourceDetailPage.tsx`, member self-service posting with creator-only edit/delete going live as `approved` immediately) but with its own tables, own routes, and no imports from `events/` — confirmed explicitly with Ben, since camps and events are expected to diverge over time. Only truly generic shared infra is reused: `auth`, `uploads` (folder union widened to include `'camps'`), `dates.ts`, `Avatar`, and — since feedback #78 — `web/src/dayLabel.ts` and `web/src/calendar/` (see this file's Testing-adjacent day-labeling entry and Sharing-adjacent Add to Calendar entry below). No `camps/theme.ts` — that file exists on the events side only to stay byte-identical with the newsletter template, and camps has no newsletter counterpart.
- **Shared day-labeling rule** (feedback #78, 2026-08-14): Today/Tomorrow/"This &lt;Weekday&gt;" (a day within the current Sunday-Saturday calendar week) is computed by `web/src/dayLabel.ts`'s `dayLabel(dateStr, now, mode)` — genuinely shared by `events/format.ts` and `camps/format.ts` (a real import, not a second diverging copy), since both tabs need the identical rule despite Camps otherwise being a non-shared clone (see the bullet above). Replaces an earlier per-file "2-6 days out" heuristic that ignored calendar week boundaries entirely (it would call a Sunday two days after a Friday "This Sunday," even though that Sunday starts next week) — confirmed with Ben: the week is Sunday-Saturday. Two modes: `'summary'` (the default; a list row, where the row's own section/bucket header usually supplies more date context — e.g. Camps' school-break accordion header) shows just the word; `'detailed'` (an event/camp's own detail page, reached via its own URL/back-stack with no such surrounding context) shows the word AND the actual date together, e.g. "This Saturday, Aug 16" — confirmed with Ben, extending to Camps a request originally raised only about Events' detail page, specifically so there's one consistent function both tabs call for both modes rather than parallel logic. Mirrored byte-for-byte into `api/src/dayLabel.ts` (parity-checked by `scripts/check-format-parity.mjs`, same convention as `events/format.ts`/`theme.ts`) since `api/src/newsletter/format.ts`'s `formatWhen` needs the identical rule — it lives at `api/src/` rather than inside `api/src/newsletter/` specifically so its relative import path from `newsletter/format.ts` (`'../dayLabel'`) matches `events/format.ts`'s own relative path to the web-side file after the parity script's existing `.js`-extension normalization; it's a different file from the pre-existing, unrelated `api/src/dates.ts` Chicago-timezone helper, not a merge with it. `api/src/camps/preview-when.ts` (the camp share-link preview title, no parity requirement with anything — see that file's own header) also imports `dayLabel` directly rather than keeping a fourth duplicate copy, even though the rest of that file stays intentionally "close enough," not byte-identical.
- **Data sourcing quality checklist** (distilled 2026-08-05 from a full day of feedback rounds on the provider seed data below — apply this to any future camp research pass, hand-researched or eventually scraped, and to any other feature that hand-sources real-world listings): every round of feedback that day was about the same underlying failure mode — trusting an inference instead of checking the real, specific source — so treat these as standing rules, not one-off fixes:
  1. **Never trust a stated blanket policy as proof of real availability.** A provider saying "we run camp on every non-attendance day" is a policy claim, not a booking guarantee — check the actual registration/booking system (or the provider's own page-level disclaimers) for the specific dates in question. When the real system can't be queried programmatically (a JS-rendered SPA, a login-gated portal), say so explicitly and treat a human's direct check as ground truth rather than guessing. Three real mechanisms in `seed-2026-08-04-providers.ts`'s `ProviderSpec` exist because "assumed open" turned out wrong in three different shapes: `hasRecurringOffering: false` (nothing at all confirmed — Chicago Park District, BitSpace), `earliestConfirmedDate` (open, but not yet for the earliest dates — YMCA, Fit City Kids), `breakDateOverrides` (open, but not for a break's *full* date range — YMCA's Thanksgiving-week hours). Don't invent a fourth shape before checking whether one of these three already fits.
  2. **A price must be the provider's own genuinely published single-unit rate.** Never derive one by dividing a bulk/weekly/seasonal figure (a 10-pack ÷ 10, a season's total spending ÷ days) — that produced two real wrong numbers this session (Family Room, Chicago Park District) before being caught. If no real single-day rate is published anywhere, the honest answer is `null`/"not published," never a computed approximation.
  3. **"Estimated" means the price itself is uncertain — not merely "not individually re-announced for this exact date."** A provider's own clearly stated standing rate applied across every seeded date is still a confirmed price; reserve the "(estimated)" flag for when the actual dollar amount is in doubt (an early version of this file conflated the two, and mislabeled several real, clear prices as guesses).
  4. **A source's URL is the actual page a person would go to book from** — a live registration portal or a specific product/listing page, never a generic marketing or homepage. Applied retroactively to BitSpace and Chicago Park District once the pattern was named.
  5. **Use the provider's own most specific, correct listing** — the right location among several (Family Room has three; Broadway, not Southport, is correct), the right dedicated page among several (Fit City Kids has a generic `/camps/` page and a real `/schools-out-camp/` page — only the latter has real dates/pricing), not just "a page that mentions this provider."
  6. **Once a data-quality gap is found for one provider, proactively re-check every similarly-situated provider in the same pass** — don't wait to be told about each one individually. Several real gaps (BitSpace's "nothing open yet" disclaimer, in particular) were caught this way rather than by Ben flagging them directly.
  7. **Merge listings that are genuinely one continuous window** rather than fragmenting near-identical adjacent entries — Parent-Teacher Conference Day and Election Day, being consecutive dates, became one `school_breaks` row instead of two.
  8. **A closure only belongs in the calendar if it represents real camp-need** (kids off school, parents still working) — the five nationally-recognized paid public holidays were excluded on this reasoning, not included just because CPS happens to also be closed that day.
- **Schema** (`camps`, `camp_sources`, `camp_interests`, `camp_comments` — same shape as their `event*` equivalents otherwise): camps are **date ranges** (`start_date`/`end_date`, both required — `end_date` defaults to `start_date` at the application layer when a single-day camp omits it), not single dates like events, since a camp can span a whole school break. **`start_time`/`end_time`** (nullable `time` columns, added 2026-08-05 per feedback: "make sure that all camps list the exact time... more important than the description") reverses this file's earlier "camps aren't scheduled to the hour" call — exact hours are shown as their own bold line right under the date, on both the compact list row (`CampRow`) and the detail page, ahead of the description. Null (a provider with no fixed schedule, e.g. Family Room's flexible drop-in pass where the family picks their own drop-off/pick-up time, or a provider whose hours simply aren't confirmed) renders as "Time: not specified" rather than a fabricated time — same always-labeled honesty posture as price/age/distance below (`web/src/camps/format.ts`'s `timeLabel`). A member posting their own camp gets optional native `<input type="time">` fields in `CampForm.tsx`, same pattern as the existing date inputs. Extra fields beyond events: `price_per_day` (numeric, optional — always a single full-day number, shown in the compact list/preview line), `options` (**structured**, not free text — see "Structured Options/What-to-bring" below), `age_min`/`age_max` (integer years, optional), `distance_miles` (numeric, optional — haversine distance from Nettelhorst's fixed coordinates via `camps/geo.ts`, populated opportunistically whenever latitude/longitude are known, same "not a live lookup" posture as latitude/longitude themselves), `price_is_estimated` (boolean, default false — see Pricing honesty below), and `spots_available` (integer, optional — real-time availability isn't tracked, no live booking integration exists, so this is `null`/unknown for essentially every camp today; a member posting their own camp can set it, since they'd actually know).
- **Every field always shown, never silently hidden when unknown — except spots, a narrow exception** (feedback, 2026-08-04, revised 2026-08-05): a camp missing a value (no published price, no stated age range) still shows that field's line, explicitly labeled — "Price: not published", "Ages: not specified" — rather than omitting it, so the *set* of fields a member sees is always the same across every camp. `web/src/camps/format.ts`'s `priceLabel`/`ageRangeLabel`/`distanceLabel` each always return a labeled string (never `null`). `spotsLabel` is the one exception (feedback, 2026-08-05: "just remove spots unknown for now, very distracting") — it returns `null`, not a string, when `spots_available` is unknown, and `campDetailsLine()` filters `null`s out before joining, so the line reads "Price: $70/day · Ages: 5-13 · Distance: 1.3 mi" with no spots segment at all until a real number is known (a member posting their own camp, or a future provider update, can supply one). This is narrower than a full reversal of the always-shown rule: it's specific to spots being unknown for nearly every camp today, making the placeholder read as noise rather than useful honesty — price/age/distance keep the original "always show, even unknown" rule as the general default for any future field.
- **School-break accordion browsing** (`school_breaks` table: name, start_date, end_date, `split_weekly` boolean): the Camps tab's primary view groups camps by which school break(s) their date range overlaps — a camp only needs to overlap a break, not fully cover it (confirmed with Ben: a 3-day camp during a 2-week Christmas break still shows under "Winter Break"). Breaks flagged `split_weekly` (Summer Break is the only one today) are shown as one accordion section per week instead of one giant section, since camps run week-by-week over the summer; a camp spanning multiple weeks appears under every week it overlaps. This bucketing/overlap logic is computed in TypeScript (`api/src/camps/grouping.ts`'s `buildBreakBuckets`/`groupCampsByBreak`, unit-tested exhaustively), not SQL — unlike events' next-occurrence-collapse CTE, there's no pagination constraint forcing it into the database (school_breaks is a handful of rows, camps a few dozen at most), so it's a small, dependency-free, highly-testable pure function instead. `GET /camps/by-break` is the Camps tab's one primary fetch (no bare `GET /camps` list route). `web/src/camps/grouping.ts`'s `applyInterestUpdateAcrossBuckets` applies an interest-status change to every occurrence of a camp across all buckets at once, needed because a multi-week camp can appear in more than one bucket. Camps within each bucket are alphabetical by title (feedback, 2026-08-05) — `api/src/camps/routes.ts`'s `loadUpcomingCamps` orders its query `asc(camps.title)`, and `groupCampsByBreak`'s per-bucket filter preserves that relative order (bucket ordering itself stays chronological, independent of this). `api/src/camps/seed-2026-08-04-school-breaks.ts` seeded the real Nettelhorst/CPS 2026-27 calendar — 12 rows as of the latest pass: Summer Break, the three other multi-day breaks (Thanksgiving, Winter, Spring), one Parent-Teacher Conference day (Apr 12), a merged "Parent-Teacher Conference Day & Election Day" row (Nov 2-3 — those two were originally separate one-day rows, merged 2026-08-05 per feedback since they're consecutive dates; Election Day is observed in lieu of Veterans Day this year), and the six teacher Professional Development days (Sep 25, Nov 11, Jan 4, Jan 29, Feb 23, Apr 6 — added in a follow-up pass after Ben flagged their absence). Researched via WebSearch/WebFetch against cps.edu and cross-checked across independent sources, cited in each row's `notes`. **Deliberately excludes the five official paid public holidays** (Labor Day, Indigenous Peoples' Day, MLK Jr. Day, Presidents' Day, Memorial Day — feedback, 2026-08-04): this app exists to help find care on days kids are off school but parents still have to work (see readme.md), and on a nationally-recognized paid holiday most parents are off too, so there's no real camp-need to solve for there — Election Day is kept since it isn't a similarly universal paid holiday. Also excluded: the five staff-only PD days before the 2026-27 school year starts (Aug 17-21, already inside the seeded Summer Break range) and the one PD day after it ends (Jun 14, 2027, already ordinary summer).
- **Star/dismiss is inline, not tabbed** (feedback #59, 2026-08-05, superseding the original New/Starred/Dismissed segmented-tab view): every school-break bucket shows one list containing every camp regardless of interest state — starred camps float to the top of their bucket, dismissed camps are held out entirely rather than shown grayed inline, surfaced only via a per-bucket "Show N dismissed items" row (same one-time-reveal-per-page-view pattern as Events' `hidden_count`/"Show N hidden repeating events"). Swiping (right to star, left to dismiss, unchanged from the original ship) and a tappable star icon on each row are both live at once — the icon didn't replace the swipe gesture, it's a second way to do the same thing. `web/src/camps/CampsPage.tsx`'s `displayBuckets` partitions each bucket into `visibleCamps` (interested, then neutral, in existing alphabetical order) and `dismissedCamps`; `revealedBuckets` (a `Set<string>` of bucket ids) tracks which buckets have had their dismissed camps revealed for the current page view.
- **Provider seed data, hand-researched not scraped** (confirmed with Ben over building a camps `ingest.ts`/`camp_sources` scraping pipeline like events has): `api/src/camps/seed-2026-08-04-providers.ts` seeded real camp listings for six named local providers (Lake View YMCA, ClimbZone Chicago, Fit City Kids, BitSpace, Chicago Park District/Gill Park, Family Room Chicago) across every non-summer break above (down from an initial 102 candidate camps as each provider's *real* confirmed availability, not an assumed blanket policy, narrowed the candidate set — see below), within ~5 miles of Nettelhorst (a wider radius than events' ~1 mile, since camps are worth traveling further for) — reviewed live with Ben before running, same posture as events' original hand-vetted seed script. A 7th provider, **Unicoi Art Studio**, was added 2026-08-05 via a separate script — see the eleventh follow-up entry near the end of this section for detail. An 8th and 9th, **Ultimate Ninjas** (formerly "Windy City Ninjas" — the two merged; seeded under the real current name/site) and **Sky Zone Chicago Lincoln Park**, were added 2026-08-06 (feedback #57) the same standalone-script way — see `api/src/camps/backfill-2026-08-06-ninjas-and-skyzone.ts`.   - **A source's URL is the actual page you'd go to book from, not a generic marketing page** (confirmed with Ben, 2026-08-04): BitSpace's source points to their real registration portal (`education.bitspacechicago.com/day-off-camps`), not their marketing page (`bitspacechicago.com/day-off/`); Family Room's points directly at the specific product/shop page (see below); Chicago Park District's points at the actual ActiveCommunities registration search tool itself. Applied as a general rule for any future camp source.
  - **A provider's stated "we run camp on every non-attendance day" policy is not the same as its real registration system actually being open that far out** (the core lesson of this whole pass, confirmed with Ben across several rounds, 2026-08-04): every one of the five providers with such a stated policy turned out to have a real, checkable gap once Ben (or a follow-up check) looked at their *actual* registration page/system rather than trusting the policy statement alone —
    - **Chicago Park District**: makes no blanket "every non-attendance day" claim at all; real availability lives entirely in their live ActiveCommunities registration search (`anc.apm.activecommunities.com/chicagoparkdistrict/activity/search`) — a JS-rendered SPA this codebase's tooling can't query — and Ben checked it directly for Labor Day 2026-09-07 and found zero results.
    - **BitSpace**: its own `bitspacechicago.com/day-off/` page explicitly says "Keep an eye out for camp options for 2026-27 School Year!" — nothing at all is confirmed open yet for the seeded date range, a stronger finding than a partial-year gap, caught proactively (not by Ben) once the same scrutiny was applied to every recurring-policy provider rather than just the one Ben had flagged.
    - **Lake View YMCA**: Ben checked their real School Days Out page directly and confirmed registration is not yet open for Labor Day or the Sep 25 PD day — Oct 12 (Indigenous Peoples' Day) is the earliest currently-open date.
    - **Fit City Kids**: Ben pointed at their real dedicated page (`fitcitykids.com/schools-out-camp/` — an earlier pass had used the generic `/camps/` page instead) confirming no Labor Day session and a schedule that starts exactly Sep 25, 2026, plus a corrected $120/day full-day (8am-6pm = $85 day camp + $35 after-camp) rate.

## Newsletter
- A weekly email digest of that week's approved, upcoming events — feature folder `api/src/newsletter/` (no frontend component; email is the whole surface). Requested via feedback #25338333 (2026-08-01), which also drove making `users.email` required at signup (see Login above).
- **Sending**: Resend (`resend` npm package, `RESEND_API_KEY`/`RESEND_FROM_EMAIL` env vars) — chosen over Postmark/SES for this use case specifically because its free tier (3k transactional emails/mo, or a separate 1k-contacts/unlimited-sends broadcast tier) comfortably covers the current handful of members with no sandbox-approval delay (unlike SES) and no paid tier required from day one (unlike Postmark). Revisit if the member list grows enough that deliverability reputation or cost start to matter more than free-tier headroom.
- **Content window**: Monday–Sunday, computed by `getUpcomingWeekRange()` (`newsletter/week.ts`) against Chicago's calendar day (`todayInChicago()`, `api/src/dates.ts` — shared with the Events tab's own "today" cutoff in `events/routes.ts`). Sent Sunday night, so it covers the week starting the next day; run on any other day (e.g. a manual test send) it still resolves to "the next Monday through the Sunday after it," treating a Monday run as the start of that same week rather than skipping a week ahead.
- **Query**: `newsletter/query.ts`'s `getWeeklyEvents()` is a deliberate parallel implementation of `events/routes.ts`'s `GET /events` query — same next-occurrence-collapse and interest-count CTE techniques, scoped to an explicit date range instead of pagination, with no viewer-specific "You" substitution (one query result is reused across every recipient's email; the "You" swap happens per-recipient at render time in `newsletter/template.ts` instead). Kept separate rather than refactored into a shared function specifically to avoid risking a regression in the live, well-exercised `GET /events` endpoint for this lower-traffic feature's sake.
- **Template**: `newsletter/template.ts` renders table-based HTML with inline styles (standard for email-client compatibility), capped at the soonest 10 events (`query.ts`'s `MAX_NEWSLETTER_EVENTS`) so a busy week can't produce an unbounded email. The whole event row is one clickable link (not just the title, matching the in-app card's full-row tap target), and the header mirrors `InstitutionBanner`'s dark logo bar. Subject/heading read "This week near Nettelhorst" (`newsletterSubject()`, shared by the real send and the test-send dev tool below), and the closing CTA reads "See more" (feedback #36 — was "Open Nettelhorst").
- **Kept in sync with the app, not just duplicated** (feedback #36): `newsletter/format.ts` and `newsletter/theme.ts` are deliberately byte-identical to `web/src/events/format.ts` and `web/src/events/theme.ts` — there's still no real shared package between `web/` and `api/` (each deploys independently via `railway up --path-as-root`, which uploads only that service's own directory, so a runtime cross-package import wouldn't exist at deploy time), but `scripts/check-format-parity.mjs` (run in CI as its own job, and in the local pre-push hook) diffs the two copies and fails the build the moment they drift. This replaced an earlier, looser duplicate that had drifted to a different parameter shape and had invented its own unrelated green for the interested-count line instead of matching the app's actual `--ion-color-medium` gray. `web/src/main.tsx` sets that CSS variable from `theme.ts`'s `EVENT_CARD_SECONDARY_TEXT_COLOR` constant at startup (rather than relying on Ionic's coincidentally-same default), so the constant is a real, live source of truth on the web side too, not just a value the email happens to match.
- **Delivery mechanism**: `newsletter/send-weekly.ts` is a standalone script (same shape as `events/backfill-*.ts` — `import 'dotenv/config'`, no Fastify, `process.exit(0)` when done), triggered weekly by a dedicated Railway cron service pointed at the `api/` codebase with a custom start command. This is the same Railway-cron mechanism Events data model & sourcing above already flags as the (still undecided, for that feature) option for daily automated event sourcing — the newsletter is the first thing in this codebase to actually stand it up. Recipient sends happen in parallel (`Promise.allSettled`), so one bad address doesn't block everyone else's email; failures are logged, and one `events_log` entry (`actor: 'system:newsletter-cron'`, `action: 'newsletter_sent'`) summarizes each run (recipient/failure/event counts, week range).
- **Unsubscribe**: `users.newsletter_subscribed` (boolean, default true) + a no-login-required link (`GET /newsletter/unsubscribe?token=...`) signed with the same `signJson`/`verifyJson` HMAC helpers WebAuthn's challenge token uses (`api/src/auth/tokens.ts`), reusing `SESSION_SECRET` rather than a new signing secret. ## Images & object storage
- A single Railway object storage bucket (`uploads`, S3-compatible) holds every image in the app — feedback screenshots and event images alike. Feature folder: `api/src/uploads/` (`storage.ts` for upload/thumbnail/fetch, `routes.ts` for the HTTP surface), mirrored by `web/src/uploads/` (upload API client, `ImageLightbox`).
- Railway buckets are private only (no public-URL mode). Every image is served through a backend proxy route, `GET /uploads/*`, rather than presigned URLs — presigned URLs expire (max 90 days) which doesn't fit content displayed indefinitely in event/feedback lists. Object keys are content-addressed (uuid-based), so the proxy sets a long, immutable `Cache-Control` unconditionally.
- Every upload gets two variants: a full image (resized down if very large, original format preserved) and a JPEG thumbnail (400px wide) for compact list/card display. Both are generated server-side with `sharp` at upload time, not on read.
- `POST /uploads` (auth required) is the generic entry point for user-attached images — feedback screenshots today, via paste-from-clipboard or a file picker in `FeedbackPage.tsx`. Event images never go through this route; they're populated directly by calling `uploadImage()` from the ingestion pipeline (see below), since that path has no HTTP request to attach a file to.
- Event images are populated during ingestion by `api/src/events/image-enrichment.ts`, which fetches each new event's `source_url` and calls `api/src/uploads/extract-page-image.ts` to find a real image for the page, in priority order: `og:image`/`twitter:image` meta tags, a schema.org JSON-LD `image` (only from types like `Event`/`Article` — deliberately not `WebSite`/`Organization`, which usually carry a generic site logo instead), a WordPress featured image (`wp-post-image` class — a near-universal WordPress convention), the largest plain `<img>` within the page's `<article>`/`<main>` content (scoped there specifically so a sidebar/"related posts" widget image is never mistaken for the page's own image), then — last resort — the site's own header logo (a page with no dedicated image at all, e.g. a plain meeting notice, still gets the hosting org's branding rather than nothing). `CandidateEvent.imageUrl` (`api/src/events/ingest.ts`) lets a hand-vetted seed script supply a directly-verified image URL for a source extraction can't reach (e.g. a JS-rendered site), bypassing extraction entirely for that event. Runs with bounded concurrency across a batch rather than serially.
- **`events.image_url`/`thumbnail_url` are NOT NULL — every event and camp is guaranteed a real image** (feedback, 2026-08-14, reversing the 2026-07-31 decision below): if none of the real-extraction candidates above find anything (no `source_url`, an unreachable/JS-rendered page, dead link, or a download failure), `api/src/uploads/placeholder.ts`'s `generatePlaceholderImage()` — a deterministic solid-color card with the title's initial, one of 8 palette colors keyed by a hash of the title — is uploaded through the same pipeline as any other image (`uploadPlaceholderImage()`) and used instead. This is enforced by a real Postgres `NOT NULL` constraint on `events.image_url`/`thumbnail_url` and `camps.image_url`/`thumbnail_url` (migration `0025_smiling_sharon_carter.sql`), not just an app-level habit — every insert path computes a real value (found photo or generated placeholder) *before* the insert, so the constraint can never be violated by a forgotten call site; a missed one fails loudly at insert time instead of silently shipping an imageless card. `api/src/events/ingest.ts`'s `ingestEvents()` sets a placeholder at insert time (real image resolution is a separate async step — `enrichEventImages` — that UPDATEs it to a real photo afterward if one passes the quality gate, or leaves the placeholder in place if not); `POST`/`PATCH /events` and `POST`/`PATCH /camps` (`events/routes.ts`, `camps/routes.ts`) generate one whenever a member doesn't attach (or clears) their own photo. `api/src/events/backfill-2026-08-14-guarantee-image.ts` backfilled the one pre-existing event that predated this (a soft-deleted test row) before the migration could apply — `camps` already had zero nulls, since Camps' own sourcing pipeline had independently enforced "every camp needs a real photo" from the start (see Camps' Images bullet below). This reverses **only** the "leave it null, never fake an image" posture — the underlying extraction/quality-gate pipeline (og:image → JSON-LD → WordPress featured → best `<img>` → site logo, each downloaded and quality-checked before being trusted) is unchanged and still strongly preferred; a generated placeholder is the fallback of last resort, not a replacement for trying to find something real.
- `api/src/events/backfill-2026-07-31-event-images.ts` (historical — its `isNull(events.imageUrl)` query can never match anything now that the column is `NOT NULL`, so it's permanently a no-op as written) targeted events still missing a *real* photo at the time. There's currently no way to tell a generated placeholder apart from a real found photo on a given row (no `is_placeholder`-style flag, unlike camps' `price_is_estimated`) — add one before writing a future "upgrade placeholders to real photos" pass, rather than trying to infer it from the URL.
- **Image quality gate + try-next-candidate, applied to every sourced image** (2026-08-03): discovered when the Gallagher Way "Movie Night: X" events all landed on the same generic venue graphic or, worse, an unrelated site's tiny logo — `extractPageImageUrl` used to return only the single highest-priority hit (og:image, then JSON-LD, etc.) and image-enrichment.ts trusted it unconditionally, even when that hit turned out to be a 258x21 site-header badge. Two structural fixes, both general — not movie-specific: (1) `api/src/uploads/extract-page-image.ts`'s `extractPageImageCandidates()` now returns *every* candidate it finds, in the same priority order, instead of stopping at the first one; (2) `api/src/uploads/image-quality.ts`'s `isLowQualityImage()` downloads and checks each candidate's real pixel dimensions/aspect ratio (rejects anything under 200px on either side, or with an aspect ratio beyond 3:1 — loose enough to pass a genuinely small but real photo, like a ~220px-wide Wikipedia poster, while catching logo strips and banner crops). `image-enrichment.ts`'s `enrichEventImage()` walks the candidate list — override URL first, then every page-extracted candidate — downloading and quality-checking each until one passes, rather than accepting whatever was found first; if nothing in the whole list passes, `image_url` stays null, same "no fake/broken substitute" posture as the placeholder decision below. This is the general rule for any future image-sourcing work: never accept the first candidate found without checking it's actually usable, and always keep a next-best fallback to try rather than settling.
- **Subject-specific poster/cover lookup, preferred over page extraction when it applies** (2026-08-03): a further refinement of the rule above for the specific case where a recurring source's `source_url` can't distinguish one occurrence from another (several distinct events sharing one listing page) but the occurrences are individually identifiable, real-world subjects (a film, a book, a specific published work) — page-extraction candidates alone can't fix this, since every occurrence scrapes the same page. `api/src/events/movie-poster-lookup.ts`'s `lookupMoviePoster()` looks up a film's real official poster via Wikipedia's public, keyless API instead — no secret required, unlike the Claude-based helpers above. Two calls: the legacy search API (`action=query&list=search`) resolves a bare title to the correctly-disambiguated page (a bare "National Treasure" lookup hits the "national treasure" concept page, not the film; searching "National Treasure film" finds "National Treasure (film)"), then the REST `page/summary` endpoint — not the legacy `pageimages` API, which deliberately excludes non-free/fair-use images, and nearly every theatrical poster is one — returns that resolved page's real infobox image. Wired into `ingest.ts`: any candidate whose (already-simplified) title matches `Movie Night: <film>` supplies this as its `overrideImageUrl`, tried first by the quality-gated candidate list above (so even this lookup's result still gets quality-checked, not blindly trusted); any failure (no search hit, no thumbnail, network error) degrades to null and falls through to normal page extraction. `api/src/events/fix-2026-08-03-movie-night-posters.ts` applied real posters retroactively to the events already affected. Prefer a subject-specific keyless lookup like this over generic page scraping whenever a source's images can't be trusted to vary per occurrence — this file's `lookupMoviePoster` is the template if a similar per-subject case shows up for a different kind of recurring listing later.
- **Site-logo fallback silently finding nothing on a real page** (feedback, 2026-08-13): a Merlo Library event (`Back to School Clothing Swap`) shipped and shipped with no image at all. Root cause: `extract-page-image.ts`'s `siteLogo()` fallback — the last-resort tier, "the org's branding is a more meaningful image than no image at all" — blindly grabbed the *first* `<img>` in a page's `<header>` with no validation. On BiblioCommons' real event pages, that first image is `<img src="{{user_avatar}}">`, an unrendered personalization stub that always 404s, while a perfectly good CPL logo sat two images later in the same header, never tried. Fixed generically (a `TEMPLATE_PLACEHOLDER_PATTERN` matching any unrendered `{{...}}` stub, applied everywhere a `src` is read, not just in `siteLogo()`, since any extraction path could hit the same kind of stub on some other site) rather than special-cased to BiblioCommons. A second, independent bug compounded it: the real CPL logo is 500×120px, an aspect ratio the shared quality gate (built to reject "logo strips and banner crops") rejected outright — meaning a real site logo could almost never pass the same bar as a real content photo, defeating the point of having a logo fallback at all. `extractPageImageCandidates()` now returns typed candidates (`{url, isLogo}`), and `image-quality.ts`'s `isLowQualityImage()` takes a much looser size/aspect-ratio bar specifically for `isLogo` candidates — real photo candidates are unaffected. `api/src/uploads/extract-page-image.test.ts` commits the actual raw HTML fetched from the real page that broke as a fixture (`__fixtures__/bibliocommons-event-page.html`) rather than a hand-simplified mock, and runs it through the real extraction code end-to-end — verified this fails against the pre-fix code and passes against the fix, so a future change to the extraction logic gets checked against the real messy markup that broke, not just a synthetic snippet shaped to pass. Backfilled the 4 live events this affected via the existing rerunnable `backfill-2026-07-31-event-images.ts`. At the time this shipped, a hard "every event must have an image" invariant test was considered and rejected on the reasoning that some sourced events genuinely have no findable image anywhere and the 2026-07-31 "never fake an image" decision meant that was fine — **reversed the very next day** (feedback, 2026-08-14: "you're not allowed to create a camp or event without an image... a pretty basic database constraint") once Ben pushed back directly: a real `NOT NULL` constraint now makes exactly that invariant true (see Images & object storage below) — this real-page regression fixture and the invariant constraint are complementary, not alternatives: the fixture catches *this specific extraction bug* recurring, the constraint guarantees the *outcome* (a real image or a placeholder, never nothing) regardless of which extraction bug might exist. Worth remembering: when a "we can't make this a hard guarantee, some legitimate cases fail it" argument gets raised, check whether the legitimate-failure case can itself be given an acceptable fallback (a placeholder was resisted 2026-07-31 as "reads as broken," but at that time there was no real alternative on the table — the actual objection was to a *bad* placeholder, not to placeholders as a concept) rather than concluding no test/constraint is possible at all.
- Local dev shares the same production bucket (no separate per-environment bucket provisioned) — local uploads are namespaced under an `UPLOADS_KEY_PREFIX` (`dev/`) so they can never collide with real objects. Get bucket credentials with `railway bucket credentials --bucket uploads --environment production --json`.
- Observed once (2026-07-31): an object uploaded to the production bucket from a local one-off script was immediately visible to a direct SDK read (same credentials) but 404'd through the deployed API's `/uploads/*` proxy for several minutes — a propagation gap between whatever storage-backend edge the local write landed on and the one the deployed API reads from. A restart of the API service didn't fix it. Workaround: upload through the deployed API itself (e.g. `POST /uploads`) rather than a local script when a one-off fix needs the image servable immediately — writes and reads through the same running server were consistent instantly. If this recurs, it may be worth asking Railway support about it.

## Testing (must run headless — no manual QA step required)
- Unit/component: Vitest + React Testing Library (`web/`), Vitest (`api/`) — both stood up for real 2026-08-01, alongside the passkey/invite rework. Ionic's web components don't map to standard ARIA roles in jsdom (`getByRole('button', ...)` won't find an `<ion-button>`/`<ion-fab-button>`); tests click the underlying custom element directly instead (see `web/src/sharing/ShareButton.test.tsx` for the pattern). `web/src/test-setup.ts` stubs `window.matchMedia` (jsdom doesn't implement it, and Ionic's overlay components query it on present()) and auto-cleans up between tests. A second, independent regression was hiding behind the first: once the server could boot, the spec itself failed — `ProfileSetupScreen`'s "I am..." role field became required 2026-08-05 (feedback #49, added after this spec was written) and the spec's `fillProfileAndContinue` helper never selected one, so Continue was permanently disabled. - Coverage is enforced but targeted: near-100% required on business logic (bookings, auth, data mutations); light coverage is acceptable on trivial UI glue. Don't chase a blanket coverage percentage for its own sake — that produces padding, not protection. ## Code hygiene (anti-sprawl)
- Knip (`knip.json` in `api/`, default config in `web/`) runs in CI on every push (`npm run knip` in both), flagging unused exports, unused files, and unused dependencies automatically — dead-code detection isn't a manual, remember-to-do-it process. Set up 2026-08-02, alongside fixing the two real hits it found on first run (an unnecessarily-exported type in each package). Its default oxc-parser "raw transfer" parse mode allocates a fixed ~6GB arena buffer per file and can `RangeError` under tight memory limits (observed in a constrained sandbox, not a real concern on a normal dev machine or CI runner) — both `knip` scripts set `KNIP_DISABLE_RAW_TRANSFER=1` to sidestep it unconditionally rather than relying on the environment having enough headroom.
- oxlint (`web/`) and `tsc`'s `noUnusedLocals`/`noUnusedParameters` (both packages) enforce unused-imports/unused-vars rules at write time, so cruft doesn't accumulate between cleanup passes.
- Feature-based file organization (see Application architecture) makes a whole dead feature visible as one unused folder rather than scattered orphaned files spread across shared layers.
- Run the `/simplify` skill as a standard step before merging non-trivial work — a deliberate pass reviewing the changed code for reuse, redundancy, and unnecessary complexity, not an occasional nice-to-have.
