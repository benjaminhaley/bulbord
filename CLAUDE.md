# Bulbord — Engineering Guide

This file is loaded automatically at the start of every Claude Code session in this repo. It is the source of truth for architecture and process decisions — read it before making structural changes, and update it whenever a decision below changes.

For product background, goals, and development path, see `readme.md`. For running notes/findings, see `log.md`.

## Product shape (MVP)
- Two tabs: Events, Camps.
- Invite-only: nothing is visible or usable — not even read-only browsing — until you've been invited by an existing member. There is no public/anonymous tier. See Login below for the mechanics; see the 2026-08-01 line in Status of these decisions for why this replaced the earlier public-read-access model.
- Logged-in: can suggest new events/camps, attempt bookings. Suggestions are saved as `pending` and only appear on the tabs once approved. Approval is modeled as a role, not a hardcoded person — Ben is the approver today, but the permission model must support automating or delegating approval (including to Claude) later without a schema change.
- Admin (Ben only): full data access via the in-app admin panel (see Introspectability below).
- Every account tracks who invited it (`users.invited_by_user_id`, nullable — null means a root/bootstrap account) — a basic social graph, visible today in the admin `/admin/users` view. There's no cap on how many people one member can invite, and no separate moderation queue for new members beyond the invite itself; revisit if that stops being appropriate at a larger scale.
- **Bulbord is the umbrella platform brand; each institution (a school, or other civic group) gets its own subdomain community** — e.g. `nettelhorst.bulbord.com` for Nettelhorst School, the first and (for now) only one (feedback #32, 2026-08-02). This is currently a domain/branding convention only, not a data-model change: there's no `institutions`/tenant table, and all data is still global/shared across the single Postgres database described in Application architecture below. Revisit if/when a second institution is actually onboarded. The bare platform domain (`bulbord.com`, no subdomain) serves a small static landing page (`web/src/landing/LandingPage.tsx`, branched on `window.location.hostname` in `web/src/main.tsx`) instead of the invite-gated app.

## Login
- Passkeys (WebAuthn) only — no password, no OAuth provider. Combined with the invite-only model above: the only way into the app is via another member's invite link (or, once, the root bootstrap secret — see below), and the only way to authenticate is a device passkey (Face ID / Touch ID / Windows Hello / Android biometric). Facebook OAuth was dropped entirely (2026-08-01), not deferred — this doesn't preclude adding an OAuth provider back later if a real need shows up; it would need its own credential table, since WebAuthn credentials aren't shaped like `(provider, provider_user_id)` pairs.
- Implementation: `users` (profile — `name`, `email`, `avatar_url`, `invited_by_user_id`, `profile_completed_at`) + `passkey_credentials` (one row per registered passkey — `credential_id`, `public_key`, `counter`, `device_type`, `backed_up`, `transports`; a user can have more than one, e.g. one per device) + `sessions` (opaque bearer token, sha256-hashed at rest) + `user_roles` (user_id + role, e.g. `admin`) — roles are data, not hardcoded checks, per the approver-role requirement above. Feature folder: `api/src/auth/` (`webauthn.ts` for the WebAuthn ceremonies, `service.ts` for session/profile/invite-lookup logic, `tokens.ts` for the shared HMAC signing helpers, `routes.ts` for the HTTP surface), mirrored by `web/src/auth/` (`webauthn.ts` client wrapper, `JoinGate.tsx` for the invite/registration/profile-setup UI, `AccountPage.tsx` for a signed-in member's own page).
- Session transport: bearer token (`Authorization: Bearer <token>`), not a cookie — unchanged from the original rationale (the web app and API are different top-level domains; Safari ITP would block a cross-site cookie; bearer tokens also travel cleanly into the Capacitor app's secure storage). Frontend stores the token in `localStorage` (`web/src/auth/token.ts`). Session TTL is still effectively unlimited (100-year expiry) for the same low-stakes-MVP reasons as before.
- **Invites**: no separate invite table or single-use codes. Every member's own `id` doubles as a permanent, reusable invite identity — `web/src/sharing/ShareButton.tsx` (see Sharing below) appends `?invite=<your user id>` to whatever URL it's already encoding when you're logged in. A non-member who opens that link sees a join screen naming the inviter (`GET /invites/:userId`, public, returns only `{name, avatarUrl}`) and can register a passkey to join, which sets their `invited_by_user_id`. Reusable by design (the same QR can invite multiple people over time, matching the existing in-person "shown at pickup" sharing model) — no expiry, no per-invite tracking, no cap. `web/src/auth/JoinGate.tsx` is the single place this is enforced on the frontend: it wraps the entire app and renders the join screen instead of any route until `user` is set, so there's no route that's reachable without it.
- **Root bootstrap**: the very first account can't come from an invite link (no member exists yet to generate one). `ROOT_INVITE_SECRET` (env var, timing-safe compared, same shape as the old `ADMIN_LOGIN_PASSWORD` stopgap) lets a registration happen with `invited_by_user_id = null` when the correct secret is supplied via `?rootSecret=<value>` instead of `?invite=`. Meant to be used once (or rarely, e.g. a second root-level account) and then left unset — unsetting it in Railway disables the path immediately (403) with no code change.
- **WebAuthn ceremony**: `POST /auth/webauthn/register/options` resolves and validates the inviter (or root secret) up front, generates registration options (`residentKey: 'required'`, true discoverable passkey), and signs `{challenge, newUserId, resolvedInviterId, issuedAt}` into an opaque `challengeToken` (HMAC via `tokens.ts`'s `signJson`/`verifyJson`, ~5 min window) → `POST /auth/webauthn/register/verify` trusts the signature rather than re-validating client-supplied ids (no gap between the two calls), verifies the attestation, creates the user/credential/session, and returns `{token, user}` directly in the JSON response — no redirect, so unlike the old OAuth flow there's no one-time exchange code or callback page. Login is the mirror image (`POST /auth/webauthn/login/options` / `/verify`) using an empty `allowCredentials` list so the OS shows its own account picker across whichever passkeys it has for this RP ID. `WEBAUTHN_RP_ID`/`WEBAUTHN_RP_NAME`/`WEBAUTHN_ORIGIN` (comma-separated, so a native app's own origin can be added alongside the web origin) are the relying-party env vars. Since the Bulbord platform rename (2026-08-02): `WEBAUTHN_RP_ID` is deliberately the *parent* platform domain (`bulbord.com`), not the institution subdomain a member actually visits (`WEBAUTHN_ORIGIN=https://nettelhorst.bulbord.com`) — RP ID only needs to be a registrable-domain suffix of the origin, and scoping it to the parent means a member invited into a future second institution's subdomain could reuse an existing passkey rather than registering a new one. `WEBAUTHN_RP_NAME` stays the institution's name ("Nettelhorst"), not "Bulbord" — it's just the friendly label the OS prompt shows, and should match what the member actually recognizes from the join flow.
- **New-member flow**: register a passkey → land on a one-time "set up your profile" step (first/last name + email, all required, + optional photo, `PATCH /auth/me`, photo via the existing uploads route with `folder: 'profiles'`) → `profile_completed_at` gets set, which is what tells `JoinGate` the person is a fully onboarded member rather than mid-registration. Email is required starting 2026-08-02 (see Newsletter below, the reason it's collected) — enforced at the application layer only (`validateProfileUpdate` in `api/src/auth/service.ts`, mirroring how `feedback.title` is required with no DB constraint), since `users.email` predates this and stayed nullable/unindexed for accounts created before the requirement existed. WebAuthn's own `userName`/`displayName` are set to a generic placeholder at registration time (the real name isn't known yet) — a known minor limitation is that this placeholder is what a shared device's OS account-picker shows forever, since WebAuthn has no API to rename a credential after creation.
- **Native app passkey continuity** (Capacitor): see Platform strategy below.

## Feedback tab
- Third tab (alongside Events/Camps): a plain running list of title+description postings, newest first — a place for feature requests/notes while the app is being built. Feature folder: `api/src/feedback/`, `web/src/feedback/`.
- Deliberately unmoderated, unlike the events/camps suggestion queue above: `GET /feedback` (gated behind `requireAuth` like every route since the invite-only rework — see Product shape — not actually public despite this line's earlier wording) has no `pending`/`approved` status, and `POST /feedback` (any logged-in member) goes live immediately. Only Ben posts today, so this is a scope choice, not an oversight — revisit (add a `status` column + the same approver-role gate as events/camps) if feedback is ever opened up to a wider audience and unmoderated posts become a problem.
- Still follows the recoverability rule: `deleted_at` soft-delete column present (no delete route built yet), and every POST/PATCH writes an `events_log` entry (`feedback_created`/`feedback_updated`).
- Every item carries a small, permanent, subtle reference number (`#28`, shown next to the author/date line) so a specific piece of feedback can be referred to unambiguously in conversation instead of by title or UUID — `feedback.number`, backed by a dedicated Postgres sequence (`feedback_number_seq`) rather than the row's own primary key, assigned in creation order across all feedback ever posted (open and closed) and never reused, even if a row is later soft-deleted.
- **Author edit** (feedback #39, 2026-08-03): a post's own author — and only the author, no admin override, unlike event comments' delete-for-moderation carve-out — can edit its title/description/photos via `PATCH /feedback/:id`, gated by `canEditFeedback` (`api/src/feedback/permissions.ts`, a pure dependency-free function mirroring `events/comment-permissions.ts`'s unit-testable shape). The frontend shows a pencil icon only when the API's per-viewer `can_edit` field is true.
- **Multiple photos per post** (feedback #40, 2026-08-03): a post can now carry more than one photo. `feedback_images` (one row per photo, `position`-ordered — several rows inserted in one statement can share the same `created_at`, so position is the real sort key) replaced the single `feedback.image_url`/`thumbnail_url` columns; the migration that dropped those columns backfilled existing single-photo posts into the new table first. Editing photos is always a full replace, never a diff: the edit form resends the complete desired set (kept + newly attached), so `PATCH /feedback/:id` soft-deletes the old rows and inserts the new set fresh rather than reconciling an add/remove list. `web/src/feedback/useMultiImageUpload.ts` wraps the shared `useImageUpload` hook (also used by the profile-photo step) to manage an array instead of a single value, uploading multiple attached files in parallel.

## Sharing
- One mechanism, not two: a persistent, always-visible share button (present on every page) opens a fullscreen modal with a QR code encoding whatever page the visitor is currently on — the app root, `/events`, or a specific event's detail page. Built for local/in-person sharing (shown at pickup, scanned phone-to-phone), so pointing at the current page (including a specific listing) is the intended behavior, not a gap. Generated client-side (`web/src/sharing/ShareButton.tsx`, `qrcode` package) — no third-party service ever sees the URL.
- Since 2026-08-01, this same URL also doubles as the app's only invite mechanism: it carries `?invite=<your user id>` whenever you're logged in (see Login above). A member sharing "the current page" and a member inviting someone new are the same action now — the destination page just doesn't render for a non-member until they've joined, at which point they land on whatever was originally shared.
- This supersedes an earlier draft that split "app-level" (invite-only, never a specific listing) from a separate not-yet-built "listing-level" share mechanism, and also the 2026-07-31 confirmation that the QR would never carry an invite. Revisit only if a real need emerges for a share surface that must NOT reflect the current page.

## Platform strategy
- Build a standard responsive mobile-web app first, but the Capacitor wrapper itself now exists (added 2026-08-01, ahead of a real native release) specifically so passkeys created on the web keep working once real iOS/Android builds ship — see below. No native *release* (App Store/Play Store) until the web product is proven.
- Native port path: Capacitor wraps the built web app into iOS/Android binaries with no rewrite. `web/capacitor.config.ts` (`appId: com.bulbord.app` — the native app container is branded at the platform level, Bulbord, not per-institution), native projects scaffolded at `web/ios/` and `web/android/` (checked into the repo, standard Capacitor convention — only their own build-artifact subfolders are gitignored). This sandbox has no Xcode or Android SDK, so neither has been built or run on a device yet; everything below is scaffolded and ready for whenever that tooling is available.
  - **Passkey continuity across the native wrap**: a passkey is tied to the domain (RP ID `bulbord.com` — see Login above), not to a specific browser or app, but the native app has to prove it's allowed to act as the institution subdomain it serves (`nettelhorst.bulbord.com`). `web/public/.well-known/apple-app-site-association` and `assetlinks.json` are in place (served automatically — they live in `public/`, which Vite copies verbatim into `dist/`) but both currently hold placeholder values (`REPLACE_WITH_APPLE_TEAM_ID`, `REPLACE_WITH_SIGNING_CERT_SHA256_FINGERPRINT`) that only exist once real signing is set up. On iOS, `ios/App/App/App.entitlements` already declares `webcredentials:nettelhorst.bulbord.com` and is wired into the Xcode project's `CODE_SIGN_ENTITLEMENTS` build setting — WKWebView supports passkeys directly once that's correctly signed, no extra plugin needed. On Android, WebView has **no** native WebAuthn support at all, so `@capgo/capacitor-passkey` is installed and bridges `navigator.credentials.create/get` to the native Credential Manager API; `web/src/main.tsx` installs its shim only when `Capacitor.isNativePlatform()` is true (confirmed locally: installing it unconditionally broke registration in a plain browser — the plugin's web implementation isn't a transparent passthrough). `npx cap sync` auto-wires the Android manifest's `asset_statements` metadata from `capacitor.config.ts`'s `plugins.CapacitorPasskey.domains`.
  - **Remaining manual steps, once real Xcode/Android Studio access exists**: open `ios/App/App.xcodeproj` (no separate `.xcworkspace` — no CocoaPods dependency), pick a signing team, and replace the AASA file's Team ID placeholder; generate a real Android signing certificate and replace `assetlinks.json`'s fingerprint placeholder (`keytool -list -v -keystore ~/.android/debug.keystore` for a debug build); add the resulting Android app-origin string (`android:apk-key-hash:...`) to `WEBAUTHN_ORIGIN` alongside the web origin, since Android passkey assertions report that origin format instead of the HTTPS one.
- Design for one viewport class: vertical phone. Desktop/tablet layout is not a design goal — don't spend effort on it.
- Performance target: usable on a slow/unreliable connection (phone at a park, not a desk). Cache last-fetched events/camps client-side so the app isn't blank on a slow request.

## Design system
- Ionic component library (React bindings), forced into Material Design mode on every platform (iOS, Android, web) — do NOT use Ionic's default per-platform adaptive styling. The goal is visually identical interfaces everywhere, not a native-feeling-per-OS look.
- Use Ionic's built-in components (tab bar, lists, forms, modals, cards) rather than custom-built equivalents. Don't hand-roll UI primitives Ionic already provides — that's how design drifts into haphazard territory.

## Application architecture
- Single repo, single Postgres database, single Node/TypeScript API server. Don't split services or add databases without a strong, explicit reason.
- Frontend: Ionic React + Vite, TypeScript strict mode.
- Backend: Node.js API server (Fastify), TypeScript strict mode.
- ORM: Drizzle (schema-as-TypeScript, close to raw SQL) — chosen partly because its transparency makes it straightforward to build a generic DB browser directly off the schema.
- Hosting: Railway (project `bulbord`). The deciding criterion is API/introspection access for Claude, not dashboard ease-of-use for Ben — Railway ships a local MCP server, a hosted remote MCP server (mcp.railway.com), and an agent-oriented CLI, so I can deploy, inspect logs, and manage the database directly instead of working around a plain REST API. Railway also added Postgres PITR (Pro tier, ~7-day WAL-archive window), closing the backup gap that used to favor Render. Accepted trade-off: Railway has no free tier and a weaker 2025-2026 reliability record than Render — fine at this stage, worth revisiting if uptime becomes business-critical. Fly.io stays ruled out (deprecated unmanaged Postgres, heavier Dockerfile-based deploy). Live at `bulbord.com` (landing page) and `nettelhorst.bulbord.com` (the Nettelhorst institution's app) since the Bulbord platform rename (feedback #32, 2026-08-02) — WebAuthn's `WEBAUTHN_RP_ID`/`WEBAUTHN_ORIGIN` and CORS are already cut over to the new domains (see Login above), not pending.
  - Deploying: each service (`api`, `web`) is deployed independently via `railway up . --path-as-root --service <name> --environment production --ci` run from inside that service's own directory (`api/` or `web/`). The `--path-as-root` flag is required — this is a monorepo and Railway's builder (Railpack) can't identify the app if it's uploaded from the repo root instead of the service's subdirectory; omitting the flag produces a build failure with no useful error beyond "Railpack could not determine how to build the app." (The web service was renamed from `campy` to `web` on 2026-08-03, alongside the Railway project itself being renamed from `campy` to `bulbord` — both via the `railway api` CLI's raw GraphQL access, `projectUpdate`/`serviceUpdate` mutations, since neither has a dedicated CLI flag or MCP tool.)
  - One-off scripts against the production DB (seeding, corrections) run locally with `DATABASE_URL` overridden to the Postgres service's `DATABASE_PUBLIC_URL` (get it via `railway variables --service Postgres --environment production --kv`) — the default `DATABASE_URL` uses Railway's internal-network hostname (`postgres.railway.internal`), which only resolves from inside Railway, not from `railway run` on a local machine.
  - Ship-and-verify is part of finishing a change, not a separate step: commit, push to `origin/main`, `railway up` the affected service(s), then confirm the change is actually live (e.g. curl the served HTML/asset and check the built hash or content) before telling Ben to look at it. Never end a task on "committed locally" or "deployed" without having checked the live response.
- API conventions: REST modeled on Stripe's API design — plural resource-based URLs, standard HTTP verbs, one consistent error-object shape, cursor-based pagination. Chosen because it's a widely-known, well-documented reference standard rather than something invented per feature.
- Database naming: snake_case, plural table names, UUID primary keys, `created_at`/`updated_at`/`deleted_at` on every table, singular `_id` foreign key columns. Standard Rails-derived convention; pairs directly with Drizzle's schema style.
- File organization: feature-based (vertical-slice), not layer-based — code for `events`, `camps`, `auth`, `admin`, etc. is colocated (routes, db access, components, tests together) rather than spread across parallel `routes/`, `models/`, `components/` trees. Makes a whole dead feature visible as one unused folder instead of scattered orphaned files (see Code hygiene below).

## Local development
- The full stack runs locally with one command: `npm run dev` from the repo root (root `package.json`, `concurrently` running docker-compose, the API dev server, and the web dev server together). Tests always run against this local database, never against the Railway production database — the day-to-day test loop must not depend on cloud access or risk touching real data.
- Schema changes go through Drizzle Kit migrations checked into the repo. Never hand-edit the schema directly against any database — this keeps the schema, the admin table-browser, and the codebase from drifting apart.

## Data safety & classification
- Nothing is publicly queryable without an account anymore (see Product shape's invite-only model) — the distinction below is now about what's visible to *any* member versus what's restricted further, not public-vs-private.
- Member-visible (any invited member): service/business listings — camp and event details (name, schedule, price, location, description), and the basic invited-by social graph (name/photo only, see Login).
- Restricted (least-privilege even among members): anything more sensitive that's personal data about a specific person — babysitter profiles/contact info, booking details, kids' names/ages/health info. A user sees their own data and what's needed for an active transaction. Broader visibility for social proof (e.g. "who from school is going," per `readme.md`) is a deliberate feature but must expose attendance signals only, never raw contact/health/PII fields.
- Admin (Ben) can see all of the above via the in-app admin panel, for support/moderation.
- Secrets (DB URL, session secret, root invite secret, etc.) live in a gitignored `.env`; a checked-in `.env.example` documents every required variable. Never commit secrets.
- Payment info is never stored directly in our database — booking payments are delegated to a processor (e.g. Stripe) and we store only tokens/references, not raw card data. This is a hard rule to apply from the first line of booking code, not a retrofit.

## Data recoverability & Claude's production-database boundary
- Nothing is ever hard-deleted from application code: deletes set a `deleted_at` timestamp (soft-delete) rather than issuing SQL `DELETE`, so in-app mistakes are always reversible.
- Every mutation and deletion is also captured in `events_log` (actor, action, metadata, timestamp) — an audit trail independent of the row itself.
- Railway Postgres PITR (opt-in, ~7-day WAL-archive window) is the infra-level safety net underneath both of the above, for catastrophic cases (bad migration, bug) that soft-deletes don't cover.
- Local database: fully self-serve — migrate, seed, reset freely without asking.
- Railway production database: also self-serve — Claude runs schema migrations and manages data there directly, without pausing to ask first. The policy is recoverability, not a confirmation gate: soft-delete + audit log + PITR (above) must always be in place and trustworthy, and that's what's allowed to substitute for asking. Hard deletes from application code are still never issued, regardless.

## Events data model & sourcing
- `events`: title, description, start_date, start_time (nullable — null means no specific time, distinct from `all_day`), all_day boolean, address, location_name (nullable — a human-friendly place name, e.g. "Merlo Library", shown in place of the raw address in list contexts; falls back to the address when absent), latitude/longitude (nullable, populated opportunistically — not a live geocoding integration), source_url, source_id (real FK to `event_sources`, alongside `source_url` which stays the free-text per-occurrence dedup key), image_url/thumbnail_url (nullable, see Images & object storage below), status (`pending`/`approved`/`rejected` — the same pending-review/approver-role model as user-submitted suggestions, see Product shape above), submitted_by_user_id (nullable — null means system-sourced), approved_by_user_id, plus the standard created_at/updated_at/deleted_at.
- `event_sources`: id, name, url, type (`generic_search` / `website` / `facebook_group` / `open_data` / …), is_active, last_checked_at, notes (free text — e.g. what to scope a broad source down to, or why a lead was skipped) — lets specific sources (a park district page, a school PTA calendar, a neighborhood FB group) be added later without a schema change. Prefer a real queryable open-data API over hand-searching when one genuinely exists for a source (e.g. Chicago's CDOT block-party permit dataset on the Socrata-based city data portal, `type: 'open_data'`) — a one-off script can query it live and is safely rerunnable to pick up newly-published data, rather than hardcoding a point-in-time result.
- One reusable ingestion operation (not per-trigger code) takes candidate events, upserts them (deduped on title+start_date+source_url), and writes `events_log` entries. A manual sourcing pass, a future daily job, and future per-source scrapers all call this same path — automating it later changes what triggers it, not how it works. It also opportunistically enriches each newly-inserted event with an image (see below) before logging.
- Sourced events default to `pending`, same queue as user suggestions, until there's an admin UI to review them. Manually-vetted seed batches (reviewed live with Ben, no UI yet to do it another way) are the one exception, inserted as `approved` directly.
- **Member self-service event posting** (feedback #46, 2026-08-03): any logged-in member can post their own event via `POST /events` — deliberately bypasses the `pending` queue above and goes live as `approved` immediately, same unmoderated posture as the Feedback tab (see Feedback tab section) rather than the sourced-event suggestion model; confirmed explicitly with Ben rather than assumed. Only `title`, `address` ("Location" in the form), and `start_date` are required; description, time/all-day, source URL, and a single optional photo (uploaded via the generic `POST /uploads` route's new `'events'` folder) are all optional. The submitter can edit (`PATCH /events/:id`) or delete (`DELETE /events/:id`, soft-delete) their own event — creator-only, no admin override, same posture as feedback-post edits (feedback #39) — gated by `api/src/events/permissions.ts`'s `canEditEvent`, a pure dependency-free function unit-tested the same way `feedback/permissions.ts` and `events/comment-permissions.ts` are. Editing does **not** reset status back to `pending` — confirmed with Ben, a deliberate simplification since there's no pending step to return to. The API exposes a per-viewer `can_edit` field (same shape as feedback's) so the frontend only shows the edit-pencil/delete-trash icons to the actual submitter. A self-submitted event has no `source_url`, so it already falls into its own single-row partition in the next-occurrence-collapse dedup logic below (via the existing `coalesce(source_url, id)` fallback) rather than needing any special-casing. Building the edit/delete flow surfaced a real Ionic gotcha worth reusing: `IonRouterOutlet` keeps a popped page's React state alive (hidden via `.ion-page-hidden`, not unmounted) for the back-transition, so `EventsPage`'s original mount-once `useEffect` never saw an edit/delete made on the detail page — a member deleting an event and navigating back would still see it in the list. Fixed by switching `EventsPage`'s fetch to Ionic's `useIonViewWillEnter` lifecycle hook (fires on every entry, including the first), which is now this codebase's first use of that hook — reach for it instead of `useEffect(fn, [])` on any list/page whose data can be mutated from a page pushed on top of it. **Poster attribution + avatar placeholder** (feedback, 2026-08-03): every event response now carries a `submitted_by: {name, avatar_url} | null` field (`api/src/events/routes.ts`'s `submittedByExpr`, a scalar subquery on `submitted_by_user_id` mirroring `interestedCountExpr`'s shape — null for system-sourced events, since there's no submitter row to join). The frontend shows "Posted by {name}" on the event detail page, and — since a member-submitted event has no source page to enrich an image from (see Images & object storage below) — falls back to the submitter's own `Avatar` (photo or initials) in place of a thumbnail/hero image wherever the event has none of its own. This is deliberately scoped to self-submitted events only: system-sourced events with no image still show nothing, per the 2026-07-31 decision below that a generic placeholder "reads as broken, not as no image yet" — a submitter's real photo doesn't have that problem, so the exception is narrow and intentional.
- **Hidden repeating-event reveal** (feedback #48, 2026-08-03): the next-occurrence-collapse below (one row shown per recurring series) used to suppress later occurrences with no indicator at all. `GET /events` now also returns `hidden_count` — the total occurrences currently suppressed across the whole upcoming window (a second lightweight query reusing the same `next_occurrence` CTE, counting `rn > 1`) — and accepts `include_hidden=true` to bypass the collapse entirely and return every occurrence. `web/src/events/EventsPage.tsx` shows a subtle "Show N hidden repeating events" row at the bottom of the New view when `hidden_count > 0`; tapping it refetches with `include_hidden` and replaces the list. Revealed occurrences behave as ordinary independent event rows from then on (their own id, their own interest state) — this is a one-time reveal for the current page view, not a persisted per-user preference.
- Daily automated sourcing (not yet built): a scheduled trigger re-runs the ingestion operation against `event_sources` plus a generic-search fallback. Mechanism undecided — a Claude Code scheduled cloud routine or a Railway cron service are both viable; the schema and ingestion-script boundary work with either.
- Facebook-authenticated sourcing (not yet built, explicitly deferred): needs its own secrets handling (Railway env vars only, never the repo) and a look at Meta's ToS for automated login before building.
- **Source detail view** (`GET /event-sources/:id`, `web/src/events/SourceDetailPage.tsx`, linked from the plain list at `SourcesPage.tsx`): shows a source's notes, when its most recently-ingested event was added, a "likely stale" flag (no new event ingested in ~30 days — a signal about the ingestion pipeline going quiet, not a judgment about how far out the events themselves are dated), and its own upcoming events (next-first, past events excluded — a "what's coming up," not "full history," view). ## Camps data model & sourcing

- **Deliberately fresh, non-shared clone of Events** (feedback #50, 2026-08-04): the Camps tab is built as its own vertical slice — `api/src/camps/` and `web/src/camps/` mirror the events feature's file-for-file shape (`permissions.ts`, `comment-permissions.ts`, `comments.ts`, `routes.ts`, `CommentsSection.tsx`, `InterestedBadge.tsx`, `format.ts`, `CampSourcesPage.tsx`/`CampSourceDetailPage.tsx`, member self-service posting with creator-only edit/delete going live as `approved` immediately) but with its own tables, own routes, and no imports from `events/` — confirmed explicitly with Ben, since camps and events are expected to diverge over time. Only truly generic shared infra is reused: `auth`, `uploads` (folder union widened to include `'camps'`), `dates.ts`, `Avatar`. No `camps/theme.ts` — that file exists on the events side only to stay byte-identical with the newsletter template, and camps has no newsletter counterpart.
- **Data sourcing quality checklist** (distilled 2026-08-05 from a full day of feedback rounds on the provider seed data below — apply this to any future camp research pass, hand-researched or eventually scraped, and to any other feature that hand-sources real-world listings): every round of feedback that day was about the same underlying failure mode — trusting an inference instead of checking the real, specific source — so treat these as standing rules, not one-off fixes:
  1. **Never trust a stated blanket policy as proof of real availability.** A provider saying "we run camp on every non-attendance day" is a policy claim, not a booking guarantee — check the actual registration/booking system (or the provider's own page-level disclaimers) for the specific dates in question. When the real system can't be queried programmatically (a JS-rendered SPA, a login-gated portal), say so explicitly and treat a human's direct check as ground truth rather than guessing. Three real mechanisms in `seed-2026-08-04-providers.ts`'s `ProviderSpec` exist because "assumed open" turned out wrong in three different shapes: `hasRecurringOffering: false` (nothing at all confirmed — Chicago Park District, BitSpace), `earliestConfirmedDate` (open, but not yet for the earliest dates — YMCA, Fit City Kids), `breakDateOverrides` (open, but not for a break's *full* date range — YMCA's Thanksgiving-week hours). Don't invent a fourth shape before checking whether one of these three already fits.
  2. **A price must be the provider's own genuinely published single-unit rate.** Never derive one by dividing a bulk/weekly/seasonal figure (a 10-pack ÷ 10, a season's total spending ÷ days) — that produced two real wrong numbers this session (Family Room, Chicago Park District) before being caught. If no real single-day rate is published anywhere, the honest answer is `null`/"not published," never a computed approximation.
  3. **"Estimated" means the price itself is uncertain — not merely "not individually re-announced for this exact date."** A provider's own clearly stated standing rate applied across every seeded date is still a confirmed price; reserve the "(estimated)" flag for when the actual dollar amount is in doubt (an early version of this file conflated the two, and mislabeled several real, clear prices as guesses).
  4. **A source's URL is the actual page a person would go to book from** — a live registration portal or a specific product/listing page, never a generic marketing or homepage. Applied retroactively to BitSpace and Chicago Park District once the pattern was named.
  5. **Use the provider's own most specific, correct listing** — the right location among several (Family Room has three; Broadway, not Southport, is correct), the right dedicated page among several (Fit City Kids has a generic `/camps/` page and a real `/schools-out-camp/` page — only the latter has real dates/pricing), not just "a page that mentions this provider."
  6. **Once a data-quality gap is found for one provider, proactively re-check every similarly-situated provider in the same pass** — don't wait to be told about each one individually. Several real gaps (BitSpace's "nothing open yet" disclaimer, in particular) were caught this way rather than by Ben flagging them directly.
  7. **Merge listings that are genuinely one continuous window** rather than fragmenting near-identical adjacent entries — Parent-Teacher Conference Day and Election Day, being consecutive dates, became one `school_breaks` row instead of two.
  8. **A closure only belongs in the calendar if it represents real camp-need** (kids off school, parents still working) — the five nationally-recognized paid public holidays were excluded on this reasoning, not included just because CPS happens to also be closed that day.
- **Schema** (`camps`, `camp_sources`, `camp_interests`, `camp_comments` — same shape as their `event*` equivalents otherwise): camps are **date ranges** (`start_date`/`end_date`, both required — `end_date` defaults to `start_date` at the application layer when a single-day camp omits it), not single dates like events, since a camp can span a whole school break. **`start_time`/`end_time`** (nullable `time` columns, added 2026-08-05 per feedback: "make sure that all camps list the exact time... more important than the description") reverses this file's earlier "camps aren't scheduled to the hour" call — exact hours are shown as their own bold line right under the date, on both the compact list row (`CampRow`) and the detail page, ahead of the description. Null (a provider with no fixed schedule, e.g. Family Room's flexible drop-in pass where the family picks their own drop-off/pick-up time, or a provider whose hours simply aren't confirmed) renders as "Time: not specified" rather than a fabricated time — same always-labeled honesty posture as price/age/distance below (`web/src/camps/format.ts`'s `timeLabel`). A member posting their own camp gets optional native `<input type="time">` fields in `CampForm.tsx`, same pattern as the existing date inputs. Extra fields beyond events: `price_per_day` (numeric, optional — always a single full-day number, shown in the compact list/preview line), `options` (**structured**, not free text — see "Structured Options/What-to-bring" below), `age_min`/`age_max` (integer years, optional), `distance_miles` (numeric, optional — haversine distance from Nettelhorst's fixed coordinates via `camps/geo.ts`, populated opportunistically whenever latitude/longitude are known, same "not a live lookup" posture as latitude/longitude themselves), `price_is_estimated` (boolean, default false — see Pricing honesty below), and `spots_available` (integer, optional — real-time availability isn't tracked, no live booking integration exists, so this is `null`/unknown for essentially every camp today; a member posting their own camp can set it, since they'd actually know).
- **Every field always shown, never silently hidden when unknown — except spots, a narrow exception** (feedback, 2026-08-04, revised 2026-08-05): a camp missing a value (no published price, no stated age range) still shows that field's line, explicitly labeled — "Price: not published", "Ages: not specified" — rather than omitting it, so the *set* of fields a member sees is always the same across every camp. `web/src/camps/format.ts`'s `priceLabel`/`ageRangeLabel`/`distanceLabel` each always return a labeled string (never `null`). `spotsLabel` is the one exception (feedback, 2026-08-05: "just remove spots unknown for now, very distracting") — it returns `null`, not a string, when `spots_available` is unknown, and `campDetailsLine()` filters `null`s out before joining, so the line reads "Price: $70/day · Ages: 5-13 · Distance: 1.3 mi" with no spots segment at all until a real number is known (a member posting their own camp, or a future provider update, can supply one). This is narrower than a full reversal of the always-shown rule: it's specific to spots being unknown for nearly every camp today, making the placeholder read as noise rather than useful honesty — price/age/distance keep the original "always show, even unknown" rule as the general default for any future field.
- **School-break accordion browsing** (`school_breaks` table: name, start_date, end_date, `split_weekly` boolean): the Camps tab's primary view groups camps by which school break(s) their date range overlaps — a camp only needs to overlap a break, not fully cover it (confirmed with Ben: a 3-day camp during a 2-week Christmas break still shows under "Winter Break"). Breaks flagged `split_weekly` (Summer Break is the only one today) are shown as one accordion section per week instead of one giant section, since camps run week-by-week over the summer; a camp spanning multiple weeks appears under every week it overlaps. This bucketing/overlap logic is computed in TypeScript (`api/src/camps/grouping.ts`'s `buildBreakBuckets`/`groupCampsByBreak`, unit-tested exhaustively), not SQL — unlike events' next-occurrence-collapse CTE, there's no pagination constraint forcing it into the database (school_breaks is a handful of rows, camps a few dozen at most), so it's a small, dependency-free, highly-testable pure function instead. `GET /camps/by-break` is the Camps tab's one primary fetch (no bare `GET /camps` list route — the frontend derives Starred/Dismissed flat views by flattening+deduping across buckets client-side, `web/src/camps/grouping.ts`'s `flattenAndDedupeCamps`/`applyInterestUpdateAcrossBuckets`, needed because a multi-week camp can appear in more than one bucket at once). Camps within each bucket are alphabetical by title (feedback, 2026-08-05) — `api/src/camps/routes.ts`'s `loadUpcomingCamps` orders its query `asc(camps.title)`, and `groupCampsByBreak`'s per-bucket filter preserves that relative order (bucket ordering itself stays chronological, independent of this). `api/src/camps/seed-2026-08-04-school-breaks.ts` seeded the real Nettelhorst/CPS 2026-27 calendar — 12 rows as of the latest pass: Summer Break, the three other multi-day breaks (Thanksgiving, Winter, Spring), one Parent-Teacher Conference day (Apr 12), a merged "Parent-Teacher Conference Day & Election Day" row (Nov 2-3 — those two were originally separate one-day rows, merged 2026-08-05 per feedback since they're consecutive dates; Election Day is observed in lieu of Veterans Day this year), and the six teacher Professional Development days (Sep 25, Nov 11, Jan 4, Jan 29, Feb 23, Apr 6 — added in a follow-up pass after Ben flagged their absence). Also excluded: the five staff-only PD days before the 2026-27 school year starts (Aug 17-21, already inside the seeded Summer Break range) and the one PD day after it ends (Jun 14, 2027, already ordinary summer).

## Newsletter
- A weekly email digest of that week's approved, upcoming events — feature folder `api/src/newsletter/` (no frontend component; email is the whole surface). Requested via feedback #25338333 (2026-08-01), which also drove making `users.email` required at signup (see Login above).
- **Sending**: Resend (`resend` npm package, `RESEND_API_KEY`/`RESEND_FROM_EMAIL` env vars) — chosen over Postmark/SES for this use case specifically because its free tier (3k transactional emails/mo, or a separate 1k-contacts/unlimited-sends broadcast tier) comfortably covers the current handful of members with no sandbox-approval delay (unlike SES) and no paid tier required from day one (unlike Postmark). Revisit if the member list grows enough that deliverability reputation or cost start to matter more than free-tier headroom.
- **Content window**: Monday–Sunday, computed by `getUpcomingWeekRange()` (`newsletter/week.ts`) against Chicago's calendar day (`todayInChicago()`, `api/src/dates.ts` — shared with the Events tab's own "today" cutoff in `events/routes.ts`). Sent Sunday night, so it covers the week starting the next day; run on any other day (e.g. a manual test send) it still resolves to "the next Monday through the Sunday after it," treating a Monday run as the start of that same week rather than skipping a week ahead.
- **Query**: `newsletter/query.ts`'s `getWeeklyEvents()` is a deliberate parallel implementation of `events/routes.ts`'s `GET /events` query — same next-occurrence-collapse and interest-count CTE techniques, scoped to an explicit date range instead of pagination, with no viewer-specific "You" substitution (one query result is reused across every recipient's email; the "You" swap happens per-recipient at render time in `newsletter/template.ts` instead). Kept separate rather than refactored into a shared function specifically to avoid risking a regression in the live, well-exercised `GET /events` endpoint for this lower-traffic feature's sake.
- **Template**: `newsletter/template.ts` renders table-based HTML with inline styles (standard for email-client compatibility), capped at the soonest 10 events (`query.ts`'s `MAX_NEWSLETTER_EVENTS`) so a busy week can't produce an unbounded email. The whole event row is one clickable link (not just the title, matching the in-app card's full-row tap target), and the header mirrors `InstitutionBanner`'s dark logo bar. Subject/heading read "This week near Nettelhorst" (`newsletterSubject()`, shared by the real send and the test-send dev tool below), and the closing CTA reads "See more" (feedback #36 — was "Open Nettelhorst").
- **Kept in sync with the app, not just duplicated** (feedback #36): `newsletter/format.ts` and `newsletter/theme.ts` are deliberately byte-identical to `web/src/events/format.ts` and `web/src/events/theme.ts` — there's still no real shared package between `web/` and `api/` (each deploys independently via `railway up --path-as-root`, which uploads only that service's own directory, so a runtime cross-package import wouldn't exist at deploy time), but `scripts/check-format-parity.mjs` (run in CI as its own job, and in the local pre-push hook) diffs the two copies and fails the build the moment they drift. This replaced an earlier, looser duplicate that had drifted to a different parameter shape and had invented its own unrelated green for the interested-count line instead of matching the app's actual `--ion-color-medium` gray. `web/src/main.tsx` sets that CSS variable from `theme.ts`'s `EVENT_CARD_SECONDARY_TEXT_COLOR` constant at startup (rather than relying on Ionic's coincidentally-same default), so the constant is a real, live source of truth on the web side too, not just a value the email happens to match.
- **Delivery mechanism**: `newsletter/send-weekly.ts` is a standalone script (same shape as `events/backfill-*.ts` — `import 'dotenv/config'`, no Fastify, `process.exit(0)` when done), triggered weekly by a dedicated Railway cron service pointed at the `api/` codebase with a custom start command. This is the same Railway-cron mechanism Events data model & sourcing above already flags as the (still undecided, for that feature) option for daily automated event sourcing — the newsletter is the first thing in this codebase to actually stand it up. Recipient sends happen in parallel (`Promise.allSettled`), so one bad address doesn't block everyone else's email; failures are logged, and one `events_log` entry (`actor: 'system:newsletter-cron'`, `action: 'newsletter_sent'`) summarizes each run (recipient/failure/event counts, week range).

Unlike the WebAuthn challenge token, this one has no expiry — an unsubscribe link should stay valid indefinitely. Logic lives in `newsletter/service.ts` (not `routes.ts`), since the standalone send script also needs `createUnsubscribeToken()` and a non-HTTP caller reaching into the HTTP-routes file would invert the auth feature's own routes/service split.

## Images & object storage
- A single Railway object storage bucket (`uploads`, S3-compatible) holds every image in the app — feedback screenshots and event images alike. Feature folder: `api/src/uploads/` (`storage.ts` for upload/thumbnail/fetch, `routes.ts` for the HTTP surface), mirrored by `web/src/uploads/` (upload API client, `ImageLightbox`).
- Railway buckets are private only (no public-URL mode). Every image is served through a backend proxy route, `GET /uploads/*`, rather than presigned URLs — presigned URLs expire (max 90 days) which doesn't fit content displayed indefinitely in event/feedback lists. Object keys are content-addressed (uuid-based), so the proxy sets a long, immutable `Cache-Control` unconditionally.
- Every upload gets two variants: a full image (resized down if very large, original format preserved) and a JPEG thumbnail (400px wide) for compact list/card display. Both are generated server-side with `sharp` at upload time, not on read.
- `POST /uploads` (auth required) is the generic entry point for user-attached images — feedback screenshots today, via paste-from-clipboard or a file picker in `FeedbackPage.tsx`. Event images never go through this route; they're populated directly by calling `uploadImage()` from the ingestion pipeline (see below), since that path has no HTTP request to attach a file to.
- Event images are populated during ingestion by `api/src/events/image-enrichment.ts`, which fetches each new event's `source_url` and calls `api/src/uploads/extract-page-image.ts` to find a real image for the page, in priority order: `og:image`/`twitter:image` meta tags, a schema.org JSON-LD `image` (only from types like `Event`/`Article` — deliberately not `WebSite`/`Organization`, which usually carry a generic site logo instead), a WordPress featured image (`wp-post-image` class — a near-universal WordPress convention), the largest plain `<img>` within the page's `<article>`/`<main>` content (scoped there specifically so a sidebar/"related posts" widget image is never mistaken for the page's own image), then — last resort — the site's own header logo (a page with no dedicated image at all, e.g. a plain meeting notice, still gets the hosting org's branding rather than nothing). If none of that finds anything (no source_url, an unreachable/JS-rendered page, dead link, or a download failure), `image_url`/`thumbnail_url` are left null rather than showing anything fake — a generated placeholder (solid color + initial) was tried initially but dropped per 2026-07-31 feedback: it reads as broken, not as "no image yet." `CandidateEvent.imageUrl` (`api/src/events/ingest.ts`) lets a hand-vetted seed script supply a directly-verified image URL for a source extraction can't reach (e.g. a JS-rendered site), bypassing extraction entirely for that event. Runs with bounded concurrency across a batch rather than serially. `api/src/events/backfill-2026-07-31-event-images.ts` is a script (rerunnable — it only targets events still missing an image) that retries real-image extraction for any event that predates enrichment or that it couldn't find one for at the time.
- **Image quality gate + try-next-candidate, applied to every sourced image** (2026-08-03): discovered when the Gallagher Way "Movie Night: X" events all landed on the same generic venue graphic or, worse, an unrelated site's tiny logo — `extractPageImageUrl` used to return only the single highest-priority hit (og:image, then JSON-LD, etc.) and image-enrichment.ts trusted it unconditionally, even when that hit turned out to be a 258x21 site-header badge. Two structural fixes, both general — not movie-specific: (1) `api/src/uploads/extract-page-image.ts`'s `extractPageImageCandidates()` now returns *every* candidate it finds, in the same priority order, instead of stopping at the first one; (2) `api/src/uploads/image-quality.ts`'s `isLowQualityImage()` downloads and checks each candidate's real pixel dimensions/aspect ratio (rejects anything under 200px on either side, or with an aspect ratio beyond 3:1 — loose enough to pass a genuinely small but real photo, like a ~220px-wide Wikipedia poster, while catching logo strips and banner crops). `image-enrichment.ts`'s `enrichEventImage()` walks the candidate list — override URL first, then every page-extracted candidate — downloading and quality-checking each until one passes, rather than accepting whatever was found first; if nothing in the whole list passes, `image_url` stays null, same "no fake/broken substitute" posture as the placeholder decision below. This is the general rule for any future image-sourcing work: never accept the first candidate found without checking it's actually usable, and always keep a next-best fallback to try rather than settling.
- **Subject-specific poster/cover lookup, preferred over page extraction when it applies** (2026-08-03): a further refinement of the rule above for the specific case where a recurring source's `source_url` can't distinguish one occurrence from another (several distinct events sharing one listing page) but the occurrences are individually identifiable, real-world subjects (a film, a book, a specific published work) — page-extraction candidates alone can't fix this, since every occurrence scrapes the same page. `api/src/events/movie-poster-lookup.ts`'s `lookupMoviePoster()` looks up a film's real official poster via Wikipedia's public, keyless API instead — no secret required, unlike the Claude-based helpers above. Two calls: the legacy search API (`action=query&list=search`) resolves a bare title to the correctly-disambiguated page (a bare "National Treasure" lookup hits the "national treasure" concept page, not the film; searching "National Treasure film" finds "National Treasure (film)"), then the REST `page/summary` endpoint — not the legacy `pageimages` API, which deliberately excludes non-free/fair-use images, and nearly every theatrical poster is one — returns that resolved page's real infobox image. Wired into `ingest.ts`: any candidate whose (already-simplified) title matches `Movie Night: <film>` supplies this as its `overrideImageUrl`, tried first by the quality-gated candidate list above (so even this lookup's result still gets quality-checked, not blindly trusted); any failure (no search hit, no thumbnail, network error) degrades to null and falls through to normal page extraction. `api/src/events/fix-2026-08-03-movie-night-posters.ts` applied real posters retroactively to the events already affected. Prefer a subject-specific keyless lookup like this over generic page scraping whenever a source's images can't be trusted to vary per occurrence — this file's `lookupMoviePoster` is the template if a similar per-subject case shows up for a different kind of recurring listing later.
- Local dev shares the same production bucket (no separate per-environment bucket provisioned) — local uploads are namespaced under an `UPLOADS_KEY_PREFIX` (`dev/`) so they can never collide with real objects. Get bucket credentials with `railway bucket credentials --bucket uploads --environment production --json`.
- Observed once (2026-07-31): an object uploaded to the production bucket from a local one-off script was immediately visible to a direct SDK read (same credentials) but 404'd through the deployed API's `/uploads/*` proxy for several minutes — a propagation gap between whatever storage-backend edge the local write landed on and the one the deployed API reads from. A restart of the API service didn't fix it. Workaround: upload through the deployed API itself (e.g. `POST /uploads`) rather than a local script when a one-off fix needs the image servable immediately — writes and reads through the same running server were consistent instantly. If this recurs, it may be worth asking Railway support about it.

The CI `web` job installs Playwright's Chromium (`npx playwright install --with-deps chromium`) before `npm test` for exactly this reason — it didn't need a real browser before this.
- Types: TypeScript strict mode everywhere — treat `tsc` errors as test failures.
- Every push runs lint + typecheck + unit (api and web, in parallel) + e2e in CI (`.github/workflows/ci.yml`); this must pass before merge. A local pre-push hook (`scripts/pre-push.sh`, installed via `ln -sf ../../scripts/pre-push.sh .git/hooks/pre-push` — hooks aren't version-controlled by git itself, so this is a one-time step per clone) runs the fast subset (lint + typecheck only) plus `scripts/check-format-parity.mjs` (see Newsletter's "kept in sync" note above) — also its own CI job, since it needs the whole repo checked out rather than either package's own working directory.
- Coverage is enforced but targeted: near-100% required on business logic (bookings, auth, data mutations); light coverage is acceptable on trivial UI glue. Don't chase a blanket coverage percentage for its own sake — that produces padding, not protection. The auth rewrite's unit tests cover the challenge-token signing/verification and invite/root-secret resolution logic specifically, since those are the actual security boundary; CI/tests for pre-existing untested code elsewhere in the app are a separate, not-yet-done follow-up, not part of this pass.

## Code hygiene (anti-sprawl)
- Knip (`knip.json` in `api/`, default config in `web/`) runs in CI on every push (`npm run knip` in both), flagging unused exports, unused files, and unused dependencies automatically — dead-code detection isn't a manual, remember-to-do-it process. Set up 2026-08-02, alongside fixing the two real hits it found on first run (an unnecessarily-exported type in each package). Its default oxc-parser "raw transfer" parse mode allocates a fixed ~6GB arena buffer per file and can `RangeError` under tight memory limits (observed in a constrained sandbox, not a real concern on a normal dev machine or CI runner) — both `knip` scripts set `KNIP_DISABLE_RAW_TRANSFER=1` to sidestep it unconditionally rather than relying on the environment having enough headroom.
- oxlint (`web/`) and `tsc`'s `noUnusedLocals`/`noUnusedParameters` (both packages) enforce unused-imports/unused-vars rules at write time, so cruft doesn't accumulate between cleanup passes.
- Feature-based file organization (see Application architecture) makes a whole dead feature visible as one unused folder rather than scattered orphaned files spread across shared layers.
- Run the `/simplify` skill as a standard step before merging non-trivial work — a deliberate pass reviewing the changed code for reuse, redundancy, and unnecessary complexity, not an occasional nice-to-have.
