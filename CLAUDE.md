# Campy — Engineering Guide

This file is loaded automatically at the start of every Claude Code session in this repo. It is the source of truth for architecture and process decisions — read it before making structural changes, and update it whenever a decision below changes.

For product background, goals, and development path, see `readme.md`. For running notes/findings, see `log.md`.

## Product shape (MVP)
- Two tabs: Events, Camps.
- Public/anonymous: read-only access to both tabs.
- Logged-in: can suggest new events/camps, attempt bookings. Suggestions are saved as `pending` and only appear on the public tabs once approved. Approval is modeled as a role, not a hardcoded person — Ben is the approver today, but the permission model must support automating or delegating approval (including to Claude) later without a schema change.
- Admin (Ben only): full data access via the in-app admin panel (see Introspectability below).
- Login: Facebook OAuth only for MVP. The auth layer must support adding more providers (Google, Apple) later without rearchitecture — Apple requires offering "Sign in with Apple" if we ever ship third-party social login inside an iOS App Store app.
  - Implementation: `users` (profile) + `auth_identities` (provider + provider_user_id, so Google/Apple slot in as new rows later) + `sessions` (opaque token, sha256-hashed at rest) + `user_roles` (user_id + role, e.g. `admin`) — roles are data, not hardcoded checks, per the approver-role requirement above. Feature folder: `api/src/auth/`.
  - Session transport: bearer token (`Authorization: Bearer <token>`), not a cookie. The web app (`campcampy.com`) and API (`api-production-a551.up.railway.app`) are different top-level domains, and a cross-site cookie would get blocked by Safari's Intelligent Tracking Prevention — a real risk given the target audience is parents on iPhones. Bearer tokens sidestep that entirely and also travel cleanly into the future Capacitor app (token in secure storage instead of a cookie jar). Frontend stores the token in `localStorage` for now (`web/src/auth/token.ts`).
  - Session TTL: effectively unlimited (100-year expiry, since the column is NOT NULL — not a true nullable "never expires"), applies to every session regardless of provider. Deliberately long — favors staying logged in over re-auth friction, since the app is low-stakes right now (no payments, no sensitive data live yet). The only way a session ends is explicit logout (sets `deletedAt`) or the device clearing `localStorage` (private browsing, manual clear, or — on iOS Safari specifically — its tracking-protection storage purge after a long stretch of no visits). Revisit this once bookings/payments/PII are real — an indefinitely-lived bearer token is a real liability if one is ever copied off the device (shared computer, logs, browser history).
  - OAuth handshake: `GET /auth/facebook` redirects to Facebook with a signed, timestamped `state` param (HMAC'd with `SESSION_SECRET`, no server-side storage needed pre-login) → `GET /auth/facebook/callback` exchanges the code, upserts the user, creates a session, and redirects to `${WEB_URL}/auth/callback?code=<one-time code>` → frontend calls `POST /auth/exchange` to trade that code for the real session token. The one-time code (`login_codes` table, 2-minute TTL, single-use) exists so the actual session token never rides in a URL/browser history — only a dead-in-two-minutes code does.
  - Temporary stopgap (2026-07-30): Facebook login is blocked on Meta account recovery for Ben's developer account, so `POST /auth/password-login` (checked against the `ADMIN_LOGIN_PASSWORD` env var, timing-safe compare) exists as a fallback — it finds-or-creates a fixed `auth_identities(provider='password', providerUserId='admin-bootstrap')` user and grants it the `admin` role directly, since only Ben has the password. Surfaced on the Account page below the (currently unusable) Facebook button. **Remove this route and its frontend UI once Facebook login is confirmed working** — unsetting `ADMIN_LOGIN_PASSWORD` in Railway disables it immediately (503) without a code change, but the code itself should still come out once it's no longer needed.

## Feedback tab
- Third tab (alongside Events/Camps): a plain running list of title+description postings, newest first — a place for feature requests/notes while the app is being built. Feature folder: `api/src/feedback/`, `web/src/feedback/`.
- Deliberately unmoderated, unlike the events/camps suggestion queue above: `GET /feedback` is public with no `pending`/`approved` status, and `POST /feedback` (any logged-in user, via `requireAuth`) goes live immediately. Only Ben posts today, so this is a scope choice, not an oversight — revisit (add a `status` column + the same approver-role gate as events/camps) if feedback is ever opened up to a wider audience and unmoderated public posts become a problem.
- Still follows the recoverability rule: `deleted_at` soft-delete column present (no delete route built yet), and every POST writes an `events_log` entry (`feedback_created`).

## Sharing
- One mechanism, not two: a persistent, always-visible share button (present on every page) opens a fullscreen modal with a QR code encoding whatever page the visitor is currently on — the app root, `/events`, or a specific event's detail page. Built for local/in-person sharing (shown at pickup, scanned phone-to-phone), so pointing at the current page (including a specific listing) is the intended behavior, not a gap. Generated client-side (`web/src/sharing/ShareButton.tsx`, `qrcode` package) — no third-party service ever sees the URL.
- This supersedes an earlier draft that split "app-level" (invite-only, never a specific listing) from a separate not-yet-built "listing-level" share mechanism. Revisit only if a real need emerges for a share surface that must NOT reflect the current page (e.g. a remote/non-in-person invite link).

## Platform strategy
- Build a standard responsive mobile-web app first. No native app development until the web product is proven.
- Native port path: Capacitor wraps the built web app into iOS/Android binaries with no rewrite. Native device APIs (push, camera, etc.) get added later via Capacitor plugins, only when actually needed.
- Design for one viewport class: vertical phone. Desktop/tablet layout is not a design goal — don't spend effort on it.
- Performance target: usable on a slow/unreliable connection (phone at a park, not a desk). Cache last-fetched events/camps client-side so the app isn't blank on a slow request.

## Design system
- Ionic component library (React bindings), forced into Material Design mode on every platform (iOS, Android, web) — do NOT use Ionic's default per-platform adaptive styling. The goal is visually identical interfaces everywhere, not a native-feeling-per-OS look.
- Use Ionic's built-in components (tab bar, lists, forms, modals, cards) rather than custom-built equivalents. Don't hand-roll UI primitives Ionic already provides — that's how design drifts into haphazard territory.

## Application architecture
- Single repo, single Postgres database, single Node/TypeScript API server. Don't split services or add databases without a strong, explicit reason.
- Frontend: Ionic React + Vite, TypeScript strict mode.
- Backend: Node.js API server (Fastify), TypeScript strict mode.
- ORM: Drizzle (schema-as-TypeScript, close to raw SQL) — chosen partly because its transparency makes it straightforward to build a generic DB browser directly off the schema.
- Hosting: Railway. The deciding criterion is API/introspection access for Claude, not dashboard ease-of-use for Ben — Railway ships a local MCP server, a hosted remote MCP server (mcp.railway.com), and an agent-oriented CLI, so I can deploy, inspect logs, and manage the database directly instead of working around a plain REST API. Railway also added Postgres PITR (Pro tier, ~7-day WAL-archive window), closing the backup gap that used to favor Render. Accepted trade-off: Railway has no free tier and a weaker 2025-2026 reliability record than Render — fine at this stage, worth revisiting if uptime becomes business-critical. Fly.io stays ruled out (deprecated unmanaged Postgres, heavier Dockerfile-based deploy). Live at campcampy.com.
  - Deploying: each service (`api`, `campy`) is deployed independently via `railway up . --path-as-root --service <name> --environment production --ci` run from inside that service's own directory (`api/` or `web/`). The `--path-as-root` flag is required — this is a monorepo and Railway's builder (Railpack) can't identify the app if it's uploaded from the repo root instead of the service's subdirectory; omitting the flag produces a build failure with no useful error beyond "Railpack could not determine how to build the app."
  - One-off scripts against the production DB (seeding, corrections) run locally with `DATABASE_URL` overridden to the Postgres service's `DATABASE_PUBLIC_URL` (get it via `railway variables --service Postgres --environment production --kv`) — the default `DATABASE_URL` uses Railway's internal-network hostname (`postgres.railway.internal`), which only resolves from inside Railway, not from `railway run` on a local machine.
  - Ship-and-verify is part of finishing a change, not a separate step: commit, push to `origin/main`, `railway up` the affected service(s), then confirm the change is actually live (e.g. curl the served HTML/asset and check the built hash or content) before telling Ben to look at it. Never end a task on "committed locally" or "deployed" without having checked the live response.
- API conventions: REST modeled on Stripe's API design — plural resource-based URLs, standard HTTP verbs, one consistent error-object shape, cursor-based pagination. Chosen because it's a widely-known, well-documented reference standard rather than something invented per feature.
- Database naming: snake_case, plural table names, UUID primary keys, `created_at`/`updated_at`/`deleted_at` on every table, singular `_id` foreign key columns. Standard Rails-derived convention; pairs directly with Drizzle's schema style.
- File organization: feature-based (vertical-slice), not layer-based — code for `events`, `camps`, `auth`, `admin`, etc. is colocated (routes, db access, components, tests together) rather than spread across parallel `routes/`, `models/`, `components/` trees. Makes a whole dead feature visible as one unused folder instead of scattered orphaned files (see Code hygiene below).

## Local development
- The full stack runs locally with one command (Postgres via docker-compose + the API/frontend dev servers). Tests always run against this local database, never against the Railway production database — the day-to-day test loop must not depend on cloud access or risk touching real data.
- Schema changes go through Drizzle Kit migrations checked into the repo. Never hand-edit the schema directly against any database — this keeps the schema, the admin table-browser, and the codebase from drifting apart.

## Data safety & classification
- Public (no login): service/business listings only — camp and event details (name, schedule, price, location, description). No personal data about any individual is ever publicly queryable.
- Private (login required): anything that is personal data about a person — user accounts, babysitter profiles/contact info, booking details, kids' names/ages/health info. Standard PII least-privilege applies: a user sees their own data and what's needed for an active transaction. Broader visibility for social proof (e.g. "who from school is going," per `readme.md`) is a deliberate feature but must expose attendance signals only, never raw contact/health/PII fields.
- Admin (Ben) can see all of the above via the in-app admin panel, for support/moderation.
- Secrets (DB URL, Facebook app secret, session secret, etc.) live in a gitignored `.env`; a checked-in `.env.example` documents every required variable. Never commit secrets.
- Payment info is never stored directly in our database — booking payments are delegated to a processor (e.g. Stripe) and we store only tokens/references, not raw card data. This is a hard rule to apply from the first line of booking code, not a retrofit.

## Data recoverability & Claude's production-database boundary
- Nothing is ever hard-deleted from application code: deletes set a `deleted_at` timestamp (soft-delete) rather than issuing SQL `DELETE`, so in-app mistakes are always reversible.
- Every mutation and deletion is also captured in `events_log` (actor, action, metadata, timestamp) — an audit trail independent of the row itself.
- Railway Postgres PITR (opt-in, ~7-day WAL-archive window) is the infra-level safety net underneath both of the above, for catastrophic cases (bad migration, bug) that soft-deletes don't cover.
- Local database: fully self-serve — migrate, seed, reset freely without asking.
- Railway production database: also self-serve — Claude runs schema migrations and manages data there directly, without pausing to ask first. The policy is recoverability, not a confirmation gate: soft-delete + audit log + PITR (above) must always be in place and trustworthy, and that's what's allowed to substitute for asking. Hard deletes from application code are still never issued, regardless.

## Events data model & sourcing
- `events`: title, description, start_date, start_time (nullable — null means no specific time, distinct from `all_day`), all_day boolean, address, latitude/longitude (nullable, populated opportunistically — not a live geocoding integration), source_url, image_url/thumbnail_url (nullable, see Images & object storage below), status (`pending`/`approved`/`rejected` — the same pending-review/approver-role model as user-submitted suggestions, see Product shape above), source_id, submitted_by_user_id (nullable — null means system-sourced), approved_by_user_id, plus the standard created_at/updated_at/deleted_at.
- `event_sources`: id, name, url, type (`generic_search` / `website` / `facebook_group` / …), is_active, last_checked_at, notes — lets specific sources (a park district page, a school PTA calendar, a neighborhood FB group) be added later without a schema change.
- One reusable ingestion operation (not per-trigger code) takes candidate events, upserts them (deduped on title+start_date+source_url), and writes `events_log` entries. A manual sourcing pass, a future daily job, and future per-source scrapers all call this same path — automating it later changes what triggers it, not how it works. It also opportunistically enriches each newly-inserted event with an image (see below) before logging.
- Sourced events default to `pending`, same queue as user suggestions, until there's an admin UI to review them. Manually-vetted seed batches (reviewed live with Ben, no UI yet to do it another way) are the one exception, inserted as `approved` directly.
- Daily automated sourcing (not yet built): a scheduled trigger re-runs the ingestion operation against `event_sources` plus a generic-search fallback. Mechanism undecided — a Claude Code scheduled cloud routine or a Railway cron service are both viable; the schema and ingestion-script boundary work with either.
- Facebook-authenticated sourcing (not yet built, explicitly deferred): needs its own secrets handling (Railway env vars only, never the repo) and a look at Meta's ToS for automated login before building.

## Images & object storage
- A single Railway object storage bucket (`uploads`, S3-compatible) holds every image in the app — feedback screenshots and event images alike. Feature folder: `api/src/uploads/` (`storage.ts` for upload/thumbnail/fetch, `routes.ts` for the HTTP surface), mirrored by `web/src/uploads/` (upload API client, `ImageLightbox`).
- Railway buckets are private only (no public-URL mode). Every image is served through a backend proxy route, `GET /uploads/*`, rather than presigned URLs — presigned URLs expire (max 90 days) which doesn't fit content displayed indefinitely in event/feedback lists. Object keys are content-addressed (uuid-based), so the proxy sets a long, immutable `Cache-Control` unconditionally.
- Every upload gets two variants: a full image (resized down if very large, original format preserved) and a JPEG thumbnail (400px wide) for compact list/card display. Both are generated server-side with `sharp` at upload time, not on read.
- `POST /uploads` (auth required) is the generic entry point for user-attached images — feedback screenshots today, via paste-from-clipboard or a file picker in `FeedbackPage.tsx`. Event images never go through this route; they're populated directly by calling `uploadImage()` from the ingestion pipeline (see below), since that path has no HTTP request to attach a file to.
- Event images are populated during ingestion by `api/src/events/image-enrichment.ts`, which fetches each new event's `source_url` and calls `api/src/uploads/extract-page-image.ts` to find a real image for the page, in priority order: `og:image`/`twitter:image` meta tags, a schema.org JSON-LD `image` (only from types like `Event`/`Article` — deliberately not `WebSite`/`Organization`, which usually carry a generic site logo instead), a WordPress featured image (`wp-post-image` class — a near-universal WordPress convention), the largest plain `<img>` within the page's `<article>`/`<main>` content (scoped there specifically so a sidebar/"related posts" widget image is never mistaken for the page's own image), then — last resort — the site's own header logo (a page with no dedicated image at all, e.g. a plain meeting notice, still gets the hosting org's branding rather than nothing). Every event gets an image, guaranteed — if none of that finds anything (no source_url, unreachable page, dead link, or a download failure), it falls back to a generated placeholder (`api/src/uploads/placeholder.ts`: a solid color + the event's initial, deterministic per title) rather than leaving `image_url` null. Runs with bounded concurrency across a batch rather than serially. `api/src/events/backfill-2026-07-31-event-images.ts` is a script (rerunnable — it only targets events still missing an image) that fills in any event that predates this or that enrichment couldn't find a real image for at the time.
- Local dev shares the same production bucket (no separate per-environment bucket provisioned) — local uploads are namespaced under an `UPLOADS_KEY_PREFIX` (`dev/`) so they can never collide with real objects. Get bucket credentials with `railway bucket credentials --bucket uploads --environment production --json`.

## Testing (must run headless — no manual QA step required)
- Unit/component: Vitest + React Testing Library.
- E2E: Playwright, headless, using its built-in mobile-viewport device emulation profiles. Reporters written to disk (JSON/HTML) so failures are inspectable without a live browser or user involvement.
- Types: TypeScript strict mode everywhere — treat `tsc` errors as test failures.
- Every push runs lint + typecheck + unit + e2e in CI (GitHub Actions); this must pass before merge. A local pre-push hook runs the fast subset.
- Coverage is enforced but targeted: near-100% required on business logic (bookings, auth, data mutations); light coverage is acceptable on trivial UI glue. Don't chase a blanket coverage percentage for its own sake — that produces padding, not protection.

## Introspectability
- No separate admin tool (no pgAdmin/Supabase Studio/etc. as the primary interface). All DB browsing, logs, and analytics live in an in-app `/admin` section gated to Ben's account specifically (not just "logged in").
- Logs are structured domain events, not verbose request/polling logs: a single `events_log` table (actor, action, metadata JSON, timestamp) capturing discrete events like "user created," "camp submitted," "booking attempted."
- Exception: production error/crash monitoring (stack traces, alerting) uses an external tool (Sentry or similar) rather than being built in-house. This is a rare-use ops tool, not a daily-use surface, so duplicating it isn't worth the effort — it doesn't violate the "everything on the site" rule, which is about the tools Ben uses day to day.

## Code hygiene (anti-sprawl)
- Knip runs in CI on every push, flagging unused exports, unused files, and unused dependencies automatically — dead-code detection isn't a manual, remember-to-do-it process.
- ESLint enforces unused-imports/unused-vars rules at write time, so cruft doesn't accumulate between cleanup passes.
- Feature-based file organization (see Application architecture) makes a whole dead feature visible as one unused folder rather than scattered orphaned files spread across shared layers.
- Run the `/simplify` skill as a standard step before merging non-trivial work — a deliberate pass reviewing the changed code for reuse, redundancy, and unnecessary complexity, not an occasional nice-to-have.
