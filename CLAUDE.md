# Bulbord — Engineering Guide

This file is loaded automatically at the start of every Claude Code session in this repo. It is the source of truth for architecture and process decisions — read it before making structural changes, and update it whenever a decision below changes.

For product background, goals, and development path, see `readme.md`. For running notes/findings, see `log.md`. For the full decision history, incident postmortems, and round-by-round feedback iteration behind the rules below, see `CLAUDE_HISTORY.md` — this file states what's true now; that one explains how each decision was reached.

## Product shape (MVP)
- Two tabs: Events, Camps (plus Feedback and Sports & Clubs — see their own sections below).
- Invite-only: nothing is visible or usable — not even read-only browsing — until you've been invited by an existing member. There is no public/anonymous tier. See Login below for the mechanics; see `CLAUDE_HISTORY.md`'s decision log (2026-08-01) for why this replaced the earlier public-read-access model.
- Logged-in: can suggest new events/camps, attempt bookings. Member self-service posts (events, camps) go live as `approved` immediately, not through a `pending` queue — see Events/Camps sections below. Approval more generally is modeled as a role, not a hardcoded person — Ben is the approver today, but the permission model must support automating or delegating approval (including to Claude) later without a schema change.
- Admin (Ben only): full data access via the in-app admin panel (see Introspectability below).
- Every account tracks who invited it (`users.invited_by_user_id`, nullable — null means a root/bootstrap account) — a basic social graph, visible today in the admin `/admin/users` view. There's no cap on how many people one member can invite, and no separate moderation queue for new members beyond the invite itself; revisit if that stops being appropriate at a larger scale.
- **Bulbord is the umbrella platform brand; each institution (a school, or other civic group) gets its own subdomain community** — e.g. `nettelhorst.bulbord.com` for Nettelhorst School, the first and (for now) only one. This is currently a domain/branding convention only, not a data-model change: there's no `institutions`/tenant table, and all data is still global/shared across the single Postgres database described in Application architecture below. Revisit if/when a second institution is actually onboarded. The bare platform domain (`bulbord.com`, no subdomain) serves a small static landing page (`web/src/landing/LandingPage.tsx`, branched on `window.location.hostname` in `web/src/main.tsx`) instead of the invite-gated app.

## Login
- Passkeys (WebAuthn) only — no password, no OAuth provider. Facebook OAuth was dropped entirely (2026-08-01), not deferred.
- Implementation: `users` (`name`, `email`, `avatar_url`, `invited_by_user_id`, `profile_completed_at`, `role`, `role_other`, `friends_step_completed_at`) + `passkey_credentials` (one row per registered passkey) + `sessions` (opaque bearer token, sha256-hashed at rest) + `user_roles` (user_id + role, e.g. `admin`) — roles are data, not hardcoded checks. Feature folder: `api/src/auth/` (`webauthn.ts`, `service.ts`, `tokens.ts`, `routes.ts`), mirrored by `web/src/auth/` (`webauthn.ts`, `JoinGate.tsx`, `AccountPage.tsx`).
- Session transport: bearer token (`Authorization: Bearer <token>`), not a cookie — the web app and API are different top-level domains and bearer tokens travel cleanly into the Capacitor app's secure storage. Frontend stores it in `localStorage` (`web/src/auth/token.ts`). Session TTL is effectively unlimited (100-year expiry).
- **Invites**: no separate invite table. Every member's own `id` doubles as a permanent, reusable invite identity — `web/src/sharing/ShareButton.tsx` appends `?invite=<your user id>` to whatever URL it's already encoding when you're logged in. A non-member who opens that link sees a join screen naming the inviter (`GET /invites/:userId`, public, returns only `{name, avatarUrl}`) and can register a passkey to join, which sets their `invited_by_user_id`. Reusable, no expiry, no cap. `web/src/auth/JoinGate.tsx` wraps the entire app and gates every route until `user` is set.
- **Root bootstrap**: `ROOT_INVITE_SECRET` (env var, timing-safe compared) lets a registration happen with `invited_by_user_id = null` when the correct secret is supplied via `?rootSecret=<value>`. Unsetting it in Railway disables the path immediately (403), no code change.
- **Sign-in link** (`?signInToken=<session token>`): `web/src/main.tsx` reads this param on boot, calls `setToken()`, strips it from the visible URL. Same trust model as `?invite=`/`?rootSecret=` (a query param carrying a real credential, not a new auth path) — the token has to be a real session created the normal way (`createSession()`). Used for the dedicated "App Review" account (Apple's reviewer) and for minting authenticated screenshot sessions (`api/src/auth/update-2026-08-12-create-screenshot-session.ts`). Not surfaced anywhere in the product UI.
- **WebAuthn ceremony**: `POST /auth/webauthn/register/options` resolves/validates the inviter (or root secret), generates registration options (`residentKey: 'required'`), signs `{challenge, newUserId, resolvedInviterId, issuedAt}` into an opaque `challengeToken` (HMAC via `tokens.ts`'s `signJson`/`verifyJson`, ~5 min window) → `POST /auth/webauthn/register/verify` trusts the signature, verifies the attestation, creates the user/credential/session, returns `{token, user}` directly (no redirect). Login is the mirror (`POST /auth/webauthn/login/options` / `/verify`), empty `allowCredentials` list so the OS shows its own account picker. Env vars: `WEBAUTHN_RP_ID`/`WEBAUTHN_RP_NAME`/`WEBAUTHN_ORIGIN` (comma-separated). `WEBAUTHN_RP_ID` is deliberately the *parent* platform domain (`bulbord.com`), not the institution subdomain (`WEBAUTHN_ORIGIN=https://nettelhorst.bulbord.com`) — scoping it to the parent lets a member invited into a future second institution reuse an existing passkey. `WEBAUTHN_RP_NAME` stays the institution's name ("Nettelhorst"), not "Bulbord".
- **New-member flow**: register a passkey → `web/src/auth/ProfileSetupWizard.tsx` (Name → Email → Role → Kids [Family only] → Photo → Newsletter → a local completion screen), one screen per field/group, real `IonProgressBar` + "N/6" label recomputed off `visibleSteps(role)`. `ProfileSetupScreen` (the older single-page form) is unchanged and now only used by `EditProfilePage.tsx`. Shared field-option constants/validation between the two live in `web/src/auth/profileForm.tsx` (`ROLE_OPTIONS`, `GRADE_OPTIONS`, `KID_COUNT_OPTIONS`, `REQUIRED_FIELDS_EXPLANATION`, `capitalizeWords`, `isNameValid`/`isEmailValid`/`isRoleValid`/`isKidsValid`/`isPhotoValid`) so the two screens can't silently drift. After profile setup: `ChooseFriendsScreen` (see Connections below) → `profile_completed_at` / `friends_step_completed_at` set — that's what tells `JoinGate` a person is fully onboarded. Email required at signup (app-layer validation only, `validateProfileUpdate` in `api/src/auth/service.ts` — `users.email` predates this and stays nullable for older accounts). Photo required (client + server enforced) — the explanation ("Nettelhorst Bulbord is only for members of the Nettelhorst community — this information lets others verify that you are") is a static line under the Continue button whenever it's disabled, not a per-field error.
- `users.role`: `'staff' | 'family' | 'other'` + `users.role_other` free text (only meaningful when `role === 'other'`). Required for new signups only — existing accounts stay `null`. Surfaced on `/admin/users`.
- `user_children` (`user_id`, `grade` — `'pre-k' | 'k' | '1'..'8'`, no name/DOB): required step, Family role only, at least one kid. Driven by a "Kids at Nettelhorst" count dropdown (1-5, never 0) that directly sets the length of `ProfileSetupScreen`'s kid-grade-select array; selecting Family pre-seeds one kid at the default grade. Full-replace on every `PATCH /auth/me` that includes `kids`. Feeds the friend-suggestion grade matching below — grade is never shown to other members directly.
- `RolePicker`: a custom `IonModal` bottom sheet (`IonRadioGroup`/`IonRadio`/`IonItem`/`IonLabel`, standard list pattern — not `IonSelect`, which can't show secondary explainer text in any interface mode, and not rich-children-as-label on `IonRadio`, whose shadow CSS silently truncates a longer description).
- **Edit Profile**: `/account/edit` (`EditProfilePage.tsx`) reuses `ProfileSetupScreen` via `initialValues`/`submitLabel`/`onSaved` props. `GET /auth/me` returns `role`/`roleOther`/`newsletterSubscribed`/`kids` for prefill.
- **Duplicate-account merge pattern**: `api/src/auth/backfill-2026-08-05-merge-duplicate-anna.ts` is the reusable shape for reassigning passkeys/sessions/roles/interests/comments/authorship to a surviving account and soft-deleting the losing one.
- **Profile photo crop**: `web/src/uploads/CropModal.tsx` (`react-image-crop`) — a draggable/resizable square selection box (`aspect={1}`, `circularCrop` overlay) over the full photo, wired into `ProfileSetupScreen`'s/the wizard's photo step only. `useImageUpload`'s `attach()` accepts a `Blob`. WebKit gotcha: read the loaded image's size via `getBoundingClientRect()` (not bare `.width`/`.height`, which WebKit can report in natural-pixel space before layout flushes), and retry on the next animation frame if it reads 0×0 — see `CLAUDE_HISTORY.md` for the onboarding-blocking bug this fixes.
- **De-emphasized passkey sign-in + About link**: "Sign In" is plain gray underlined text (`SignInLink` in `JoinGate.tsx`, `0.8125rem`), not a full-width button. `BrandHeader` (every logged-out state) has a "Learn more" link to the real `/about`, reachable pre-auth via a narrow `JoinGate` bypass. `JoinGate` checks for a pending `invite`/`rootSecret` param unconditionally at the top of the function, before any route-specific pre-auth bypass runs — see `CLAUDE_HISTORY.md` for the real invite that was silently swallowed before this was structural.
- **Native app passkey continuity** (Capacitor): see Platform strategy below.

## Connections (friends)
- `user_connections` (`user_id` = requester, `connected_user_id` = recipient, unique on the pair, toggled via `deletedAt`): `status` (`'pending' | 'accepted'`) starts `'pending'` and flips to `'accepted'` via `POST /connections/:id/accept` or is soft-deleted via `/decline` (allows a fresh request later). One row represents the whole relationship regardless of direction — "Friends" is the union of a viewer's accepted rows either direction. Sending a request to someone who already sent *you* one accepts theirs instead of a second row (`requestConnection()`'s reverse-pending check). Feature folders: `api/src/connections/` (`service.ts` DB CRUD, `logic.ts` pure friends/suggestion derivation, `template.ts` alert email, `routes.ts`), `web/src/connections/` (`api.ts`, `ChooseFriendsScreen.tsx` onboarding, `FriendsPage.tsx` ongoing view).
- Notifications: `notifyConnectionRequested()` (in-app `friend_added` + email) on request; `friend_request_accepted` (in-app only, no email) fires when a request is accepted, telling the original requester.
- **Onboarding suggestions** (`GET /connections/suggestions`, `ChooseFriendsScreen.tsx`): priority order — inviter, inviter's own *accepted* connections, other Family-role members with a kid in the same grade — deduped, excluding anyone already connected (pending or accepted). Falls back to everyone else alphabetically once tiers are exhausted, up to `SUGGESTIONS_LIMIT` (200). `GET /connections/members?q=` narrows by name search (always queries the full table). Adding a suggested person appends *their* own accepted connections to the list bottom (`GET /connections/of/:userId`). `ChooseFriendsScreen preview` mode shows a fixed `DEMO_SUGGESTIONS` list with a `reason` subtitle per row (one per real tier) instead of the live endpoint.
- `users.friends_step_completed_at` (nullable timestamp) gates `JoinGate` into showing `ChooseFriendsScreen` once after profile setup. Continue/Skip both call `POST /connections/finish-onboarding`; picking anyone during it is optional. Adding sends a real request, not an instant add.
- **Friends page** (`/friends`): three sections — Friends (accepted either direction), Requests Sent (pending, sent by viewer, no action), Friend Requests (pending, received — real Accept/Decline). `GET /connections` returns all three via `connections/logic.ts`'s `deriveConnectionsState`.
- `users.isServiceAccount` (boolean) excludes an account from every discovery surface (suggestions, search) via a shared `NOT_SERVICE_ACCOUNT` condition — still fully visible in admin `/admin/users`.
- **Repeatable admin test tools**: `POST /admin/connections/test-send` (test alert email) and Dev Tools' "Create a test friend request" (`POST /admin/connections/test-request`) — creates a real disposable `isServiceAccount` member and runs it through the real `requestConnection()` path.
- Capture-and-display only — no other feature reads the connection graph yet.

## Notifications
- **Unified notification center**: one `notifications` table (`user_id` recipient, `type` — `friend_added`/`feedback_reply`/`event_comment`/`camp_comment`/`friend_request_accepted`/`pipeline_review_ready`, `actor_user_id`, precomputed `message`/`target_path`, `dismissed_at`). Every trigger funnels through `api/src/notifications/service.ts`'s `createNotification()` — no separate "seen" watermark to drift out of sync.
- **One avatar badge**: `InstitutionBanner`'s avatar shows a single `BadgeDot` (bottom-right, numbered once `count > 1`) driven by `GET /auth/me`'s `unseenNotificationCount`. No per-feature dots anymore (`BadgeDot` — `web/src/app/BadgeDot.tsx` — has no `corner`/`color` props; one call site).
- **`/notifications`**, reached by tapping the avatar: `web/src/notifications/NotificationsPage.tsx` lists every notification newest-first — undismissed rows get a small filled dot + light background tint. Tapping a row's content navigates to `target_path` and dismisses it; a separate X dismisses without navigating. A header "Mark all as read" button fires dismiss for every unread row in parallel. Dismissed notifications stay visible (normal weight, no X) — dismissing only clears the unread count, not a delete.
- **Per-type email settings** (`/account/notification-settings`): Email is the only toggleable channel — `users.notifyFriendAddedEmail`, `notifyFeedbackReplyEmail`, `notifyContentCommentEmail`, `newsletterSubscribed`. `GET`/`PATCH /notifications/settings`.
- **Event/camp comment notifications**: `api/src/notifications/content-comment.ts`'s `notifyContentComment()`, shared by `events/comments.ts` and `camps/comments.ts`'s `POST .../comments` handlers. No self-notify (skipped when the event/camp has no `submitted_by_user_id`, or the commenter is the creator).
- **Admin-only data-freshness nudge** shares the same one red bell badge, no separate color/corner (`InstitutionBanner.tsx`'s `showNotificationBadge = unseenNotificationCount > 0 || showStaleAlert`). Synthesized as a client-side-only row (`describeFreshnessAlert()`, id `data-freshness-alert`) at the top of the notifications list — not a real `notifications` row, since it's live computed state; it stops appearing once the underlying data refreshes, or can be dismissed via a `localStorage` fingerprint (`freshnessSignature()`) that re-triggers if the flagged data changes. Routes to `/admin/dev-tools` with a `location.hash` anchor + a brief highlight ring.
- Repeatable test tool: Dev Tools' "Create a test friend follow" exercises the whole pipeline (in-app notification, unread badge, email) end-to-end.

## Feedback tab
- Third tab: a plain running list of title+description postings, newest first. Feature folder: `api/src/feedback/`, `web/src/feedback/`.
- Deliberately unmoderated (unlike events/camps): `GET /feedback` is gated behind `requireAuth` but has no `pending`/`approved` status; `POST /feedback` (any logged-in member) goes live immediately.
- Soft-delete (`deleted_at`) + `events_log` entries (`feedback_created`/`_updated`/`_deleted`) on every mutation.
- `DELETE /feedback/:id`: author-only (no admin override), soft-deletes.
- `feedback.number`: permanent reference number backed by a dedicated Postgres sequence (`feedback_number_seq`), assigned in creation order across all feedback ever posted, never reused even if soft-deleted.
- **Author edit**: `PATCH /feedback/:id`, gated by `canEditFeedback` (`api/src/feedback/permissions.ts`, a pure dependency-free function). The frontend shows the pencil icon only when the API's per-viewer `can_edit` field is true.
- **Multiple photos per post**: `feedback_images` (one row per photo, `position`-ordered) replaced single `image_url`/`thumbnail_url` columns. Editing photos is always a full replace, never a diff. `web/src/feedback/useMultiImageUpload.ts` wraps the shared `useImageUpload` hook to manage an array.
- **Backlog / In Progress**: `feedback.backloggedAt` / `feedback.inProgressAt` (nullable timestamps), mutually exclusive with each other and with `completedAt`, toggled by admin-only icons (`POST /feedback/:id/{backlog,unbacklog,start-progress,stop-progress}`). `api/src/feedback/routes.ts`'s `setSideState` helper clears the other column whenever one is set. Rendered as collapsed accordion sections (Open / In Progress / Backlog / Closed).
- Compose-time photo previews (`FeedbackPage.tsx`'s `PhotoPicker`) are clickable, opening the same `ImageLightbox` a posted photo does.
- **Overflow menu**: a post's actions (Edit, Delete, Mark done, Backlog/In Progress toggles) live behind one ellipsis button opening a real `IonActionSheet`, mounted unconditionally outside any `editing`/`!editing` branch (not conditionally, which loses the dismiss lifecycle and can pop the menu back open — see `CLAUDE_HISTORY.md`).
- `POST /feedback/:id/complete` just completes, no note step involved.
- **Replies**: `feedback_comments` (same shape as `event_comments`/`camp_comments`); `api/src/feedback/comments.ts` (GET/POST/PATCH/DELETE `/feedback/:id/comments`), `comment-permissions.ts`'s `canEditFeedbackComment`/`canDeleteFeedbackComment` (author-only edit, author-or-admin delete). `FeedbackDetailPage.tsx` (`/feedback/:id`) mirrors `EventDetailPage.tsx`'s shape. Ordered oldest-at-top, newest-at-bottom (`GET /feedback/:id/comments` orders `asc(createdAt)`).
- **Reply photo attachments**: `feedback_comment_images` (same shape as `feedback_images`). `CommentsSection.tsx`'s composer/edit-form reuse `FeedbackForm.tsx`'s exported `PhotoPicker`/`makePasteHandler` and `useMultiImageUpload` (which gained a `reset()` method since a comment composer stays mounted after posting).
- **Reply notification**: `api/src/feedback/notifications.ts`'s `notifyFeedbackReply()` — email (`feedbackReplyHtml()` template, capped at `EMAIL_MAX_WIDTH` 480px, embeds the reply's own photos) gated by `users.notifyFeedbackReplyEmail`, plus an in-app row in the unified `notifications` table. No self-notify. Called best-effort (not awaited into the response).

## Sharing
- One mechanism, not two: a persistent, always-visible share button (present on every page) opens a fullscreen modal with a QR code encoding whatever page the visitor is currently on. Generated client-side (`web/src/sharing/ShareButton.tsx`, `qrcode` package) — no third-party service ever sees the URL.
- This same URL doubles as the app's only invite mechanism: it carries `?invite=<your user id>` whenever you're logged in (see Login above).
- **Native OS share sheet**: the modal also has a "Share via Text, Email, etc." button using `navigator.share({ url })`, feature-detected (`typeof navigator.share === 'function'`).
- No raw URL is shown as visible text in the modal — the link exists only in the QR encoding and the image's `alt` text.
- **Add to Calendar**: both event and camp detail pages get an "Add to Calendar" button — an `IonActionSheet` offering Google Calendar, Outlook.com, and a downloaded `.ics` file. Shared, generic infra (`web/src/calendar/AddToCalendarButton.tsx` + `calendarLinks.ts`) since Camps can't import from `events/`. No timezone-conversion logic — every date/time in this app is a plain, timezone-less local value, so every calendar target gets a "floating" local time. A multi-day camp (`start_date !== end_date`) always becomes an all-day block spanning the whole range; only a genuinely single-day camp's own `start_time`/`end_time` become a timed block. Hand-built ICS/URLs (~150 lines, unit-tested), no npm dependency.

## Platform strategy
- **Native app as the primary intended surface** going forward — Ben continues using the web version as a beta tester.
- **WebView-shell architecture, not a bundled build**: `web/capacitor.config.ts`'s `server.url` points the native shell at `https://nettelhorst.bulbord.com` live, instead of bundling `web/dist` into the binary — a normal `railway up` web deploy reaches every installed app instantly, no store resubmission. `webDir: 'dist'` is required by Capacitor's config type but unused while `server.url` is set. Tradeoff: no offline access. Only shell-level changes (native plugins, `capacitor.config.ts`, icons) need a new review cycle.
- **Apple review risk** (Guideline 4.2, minimum functionality): mitigated by real native capability built for other reasons — native passkey/WebAuthn via the OS credential manager, native share sheet (`navigator.share`).
- **When a web-only change needs a fresh App Store review, not just a deploy** — the trigger isn't feature size, it's whether the feature crosses into territory the current approval doesn't cover: real-people matching/connection features (Guideline 1.2 — requires actually implementing content filtering, report-abuse, block, published contact info); any feature that collects/transmits/shares personal info about a minor (Guideline 5.1.4(b) — triggers a children's-data privacy-policy requirement); any new payment-collection mechanism (re-check 3.1.3(d)'s person-to-person exemption and 3.1.1's IAP requirement against the specific mechanism). General test (2.3.1(a)): would a reviewer reading the current Notes for Review recognize what the app does today? Re-check Apple's current guidelines before shipping such a feature — don't trust these citations to stay accurate.
- **No physical Mac required for iOS builds**: `web/ios/App/fastlane/Fastfile` runs on GitHub Actions' `macos-latest` runner (`.github/workflows/mobile-ios.yml`, `workflow_dispatch`-only). Android needs no macOS at all (`web/android/fastlane/Fastfile`, standard Linux runner, `.github/workflows/mobile-android.yml`), Google Play App Signing holding the real release key, a locally-generated upload key as a repo secret.
- **iOS signing/build pipeline** (see `CLAUDE_HISTORY.md` for the full incident trail — cert-quota exhaustion, `.p12` legacy-export requirement, `set_key_partition_list` being a raw shell call not a fastlane action, app records needing the website not the API): a durable Distribution certificate (`IOS_DIST_CERT_P12_BASE64`/`IOS_DIST_CERT_PASSWORD` repo secrets, `DIST_CERT_ID` in the Fastfile) generated once via direct App Store Connect REST API calls, imported fresh into each CI run's keychain. `increment_build_number(build_number: ENV['GITHUB_RUN_NUMBER'])` gives each build a monotonic number. `TARGETED_DEVICE_FAMILY` restricted to `"1"` (iPhone-only — this app was never designed for iPad).
- **Sign-in for App Review**: since the app is passkey-only with no traditional password, a dedicated always-onboarded "App Review" account (invited by Ben, kept separate from his own identity) has its `?signInToken=` embedded directly in the App Store review notes — see Login above.
- **Universal Links**: `web/public/.well-known/apple-app-site-association` (real Team ID `792L57KZP4`), `App.entitlements`' `webcredentials`/`applinks` blocks, and an `@capacitor/app` `appUrlOpen` listener (`web/src/main.tsx`) so an incoming Universal Link navigates the app's own WebView. AASA must be served with `Content-Type: application/json` (`web/server.mjs`, a custom server using `sirv` as a library rather than `sirv-cli`'s extension-based MIME lookup, which can't match an extensionless file).
- **Passkey continuity**: `capacitor.config.ts`'s `plugins.CapacitorPasskey.domains` must match the real `WEBAUTHN_RP_ID` (`bulbord.com`), not the institution subdomain — the plugin generates native entitlements/`asset_statements` straight from this config on every `cap sync`. On Android, WebView has no native WebAuthn support, so `@capgo/capacitor-passkey` bridges `navigator.credentials.create/get` to the native Credential Manager API; `web/src/main.tsx` installs the shim only when `Capacitor.isNativePlatform()` is true (installing it unconditionally breaks registration in a plain browser).
- **Checking review status**: App Store Connect API credentials (`ASC_KEY_ID`/`ASC_ISSUER_ID`/`ASC_KEY_CONTENT`) live as Railway env vars on the `api` service (production) — get via `railway variables --service api --environment production --kv`, mint a JWT via `api/src/ops/generate-asc-jwt.ts` (expires ~20 min). App ID `6800520018`, bundle ID `com.bulbord.app`. As of the last check, the iOS build's status needs re-verifying in App Store Connect's Resolution Center directly — see `CLAUDE_HISTORY.md`'s most recent status-check entry.
- **Google Play's mandatory closed-testing window is the long pole**: any new Play Console developer account must run 14 continuous days of closed testing with 20+ opted-in testers before production publishing unlocks, independent of build quality — recruit testers and get a first build up early.
- **Store branding**: app name/icon is "Bulbord" (matching `com.bulbord.app`), not "Nettelhorst" — so the listing doesn't need to change when a second institution joins.
- **Apple Developer Program: Individual, not Organization** — uses Ben's personal Apple ID (~24-48hr approval), avoiding Organization's D-U-N-S/legal-entity verification delay.
- Native port: Capacitor wraps the built web app with no rewrite. `web/ios/`, `web/android/` scaffolded and checked in (only build-artifact subfolders gitignored). iOS: `App.entitlements` declares `webcredentials:nettelhorst.bulbord.com`, wired into `CODE_SIGN_ENTITLEMENTS` — WKWebView supports passkeys directly once correctly signed.
- Design for one viewport class: vertical phone. Desktop/tablet layout is not a design goal.
- Performance target: usable on a slow/unreliable connection — cache last-fetched events/camps client-side.

## Design system
- Ionic component library (React bindings), forced into Material Design mode on every platform (iOS, Android, web) — do NOT use Ionic's default per-platform adaptive styling. The goal is visually identical interfaces everywhere.
- Use Ionic's built-in components (tab bar, lists, forms, modals, cards) rather than custom-built equivalents. Don't hand-roll UI primitives Ionic already provides.
- **Style guide**: `STYLE_GUIDE.md` (repo root) is the current-state style reference — Material Design 3, the spacing/type-scale token layer (`web/src/theme/tokens.css`, `theme/layout.ts`), and durable written conventions (time formatting, always-labeled-unless-self-evident fields, no redundant display, bulleted-list content, icon alignment). A living visual version is in Storybook under "Style Guide". This file keeps historical rationale (see `CLAUDE_HISTORY.md`); `STYLE_GUIDE.md` is the present-tense reference to follow.
- **App icon**: a full-bleed red/gold triangulated stained-glass mosaic (SVG-generated), deliberately avoiding any cross motif. Source is `web/ios/App/App/Assets.xcassets/AppIcon.appiconset/AppIcon-512@2x.png` — Android's per-density launcher icons (`web/android/app/src/main/res/mipmap-*`) are generated from the same source and must be regenerated together if it ever changes.

## Application architecture
- Single repo, single Postgres database, single Node/TypeScript API server. Don't split services or add databases without a strong, explicit reason.
- Frontend: Ionic React + Vite, TypeScript strict mode.
- Backend: Node.js API server (Fastify), TypeScript strict mode.
- ORM: Drizzle (schema-as-TypeScript, close to raw SQL).
- Hosting: Railway (project `bulbord`) — API/introspection access for Claude is the deciding criterion, not dashboard ease-of-use. Live at `bulbord.com` (landing page) and `nettelhorst.bulbord.com` (the Nettelhorst institution's app).
  - Deploying: each service (`api`, `web`) is deployed independently via `railway up . --path-as-root --service <name> --environment production --ci` run from inside that service's own directory. The `--path-as-root` flag is required (monorepo).
  - One-off scripts against the production DB run locally with `DATABASE_URL` overridden to the Postgres service's `DATABASE_PUBLIC_URL` (get via `railway variables --service Postgres --environment production --kv`) — the default `DATABASE_URL` only resolves from inside Railway.
  - Ship-and-verify is part of finishing a change: commit, push to `origin/main`, `railway up` the affected service(s), then confirm the change is actually live before reporting done. Never end a task on "committed locally" or "deployed" without checking the live response.
  - `railway up` can hang indefinitely during a Railway-side outage with zero build logs — check status.railway.com before assuming something is wrong locally; killing and retrying is safe (check `list-deployments` first, since a killed local process doesn't necessarily kill the server-side deploy).
- API conventions: REST modeled on Stripe's API design — plural resource-based URLs, standard HTTP verbs, one consistent error-object shape, cursor-based pagination.
- Database naming: snake_case, plural table names, UUID primary keys, `created_at`/`updated_at`/`deleted_at` on every table, singular `_id` foreign key columns.
- File organization: feature-based (vertical-slice) — code for `events`, `camps`, `auth`, `admin`, etc. is colocated (routes, db access, components, tests together) rather than spread across parallel `routes/`, `models/`, `components/` trees.

## Local development
- The full stack runs locally with one command: `npm run dev` from the repo root (root `package.json`, `concurrently` running docker-compose, the API dev server, and the web dev server together). Tests always run against this local database, never against the Railway production database.
- Schema changes go through Drizzle Kit migrations checked into the repo. Never hand-edit the schema directly against any database.

## Data safety & classification
- Nothing is publicly queryable without an account (see Product shape's invite-only model).
- Member-visible (any invited member): service/business listings (camp/event details) and the basic invited-by social graph (name/photo only).
- Restricted (least-privilege even among members): babysitter profiles/contact info, booking details, kids' names/ages/health info. A user sees their own data and what's needed for an active transaction. Broader visibility for social proof must expose attendance signals only, never raw contact/health/PII fields.
- Admin (Ben) can see all of the above via the in-app admin panel, for support/moderation.
- Secrets live in a gitignored `.env`; a checked-in `.env.example` documents every required variable. Never commit secrets.
- Payment info is never stored directly in our database — booking payments are delegated to a processor (e.g. Stripe) and we store only tokens/references, not raw card data.

## Data recoverability & Claude's production-database boundary
- Nothing is ever hard-deleted from application code: deletes set a `deleted_at` timestamp (soft-delete) rather than issuing SQL `DELETE`.
- Every mutation and deletion is also captured in `events_log` (actor, action, metadata, timestamp) — an audit trail independent of the row itself.
- Railway Postgres PITR (opt-in, ~7-day WAL-archive window) is the infra-level safety net underneath both of the above.
- Local database: fully self-serve — migrate, seed, reset freely without asking.
- Railway production database: also self-serve — Claude runs schema migrations and manages data there directly, without pausing to ask first. The policy is recoverability (soft-delete + audit log + PITR), not a confirmation gate. Hard deletes from application code are still never issued, regardless.

A manual sourcing pass, the weekly cron, and per-source scrapers all call this same path.
- **Automated extraction (page-scraping via `resourcing.ts`, inbound email via `email-ingest.ts`) inserts directly as `status: 'approved'`** — there's no `pending` review step for sourced events, matching how member self-service posting already goes live immediately. Required: `title`, `address`, `start_date`; description/time/source URL/photo optional. Actions — Approve / Reject / Edit / Retry (`retryPipelineChecks()`, a bounded "just try again" rerun of the failing checks); Edit re-runs checks in place and never itself changes publish state, except that fixing the last failing check on a held-back `pending` item auto-publishes it. Weekly digest email (Wednesday ~7am Chicago, via `event-sourcing-cron`) + a `pipeline_review_ready` notification, scoped to the latest run only. Admin sampling knobs: `maxSources`/`maxCandidates` on `resourceActiveEventSources()`. **Each candidate row renders through `EventPostView` (`web/src/events/EventPostView.tsx`)** — the same shared component (`EventBody` plus the Add to Calendar/View source buttons) `EventDetailPage.tsx` itself renders, inside a plain `div` rather than `IonItem`/`IonLabel` (feedback #171, 2026-09-17 — `IonLabel`'s own Material Design typography was overriding the post's real body styles, and the two buttons had never been added to this page's rendering at all).
- **Retry-with-a-note + a shared retry-strategies library** (feedback #165, 2026-09-14): both Pipeline Review's Retry and the member-facing photo/Describe-It extraction review screen (`AddEventModal.tsx`, a "Retry" button next to Post opening a small modal) accept an optional free-text note, threaded straight into that retry's own extraction/check call. Every note is also persisted into `pipeline_retry_notes` (`api/src/events/retry-strategies.ts`) and logged to `events_log` — the most recent 15, across every event, are shown to every future retry (not just the one the note was written for) as a "past retry strategies" block appended to the relevant system prompt, so the same kind of problem doesn't need to be re-explained from scratch. Only fetched on an actual retry, never a first attempt (no added DB cost on the common path). **Pipeline Review's Retry button stays available even once every check already passes** (feedback #169 follow-up, 2026-09-16) — a note-guided image retry is a genuinely useful ask on a row that's otherwise clean (e.g. "look up the official poster"), and the note is now actually threaded into the image search itself (`findBroaderImageSearchPages`'s `admin_note`, tried before Commons whenever a note is given), not just corrected text fields — `retryPipelineChecks()` re-searches the image whenever it's currently failing OR a note was given, not only the former. **The broader-search tool call doesn't just trust the model's own final summary** (feedback #169 follow-up, 2026-09-17): a real incident showed the model can complete several genuinely good `web_search` calls, then hit the tool's own server-side rate limit mid-turn and give up with a bare `[]`, discarding every real result it had already found — `findBroaderImageSearchPages()` now falls back to pulling real URLs directly out of the raw `web_search_tool_result` blocks whenever the model's own final text comes back empty, so a completed search is never silently thrown away. ## Camps data model & sourcing
- **Deliberately fresh, non-shared clone of Events**: `api/src/camps/` and `web/src/camps/` mirror Events' file-for-file shape (`permissions.ts`, `comment-permissions.ts`, `comments.ts`, `routes.ts`, `CommentsSection.tsx`, `InterestedBadge.tsx`, `format.ts`, `CampSourcesPage.tsx`/`CampSourceDetailPage.tsx`, member self-service posting with creator-or-admin delete) but with its own tables/routes, no imports from `events/`. Only genuinely generic shared infra is reused: `auth`, `uploads`, `dates.ts`, `Avatar`, `web/src/dayLabel.ts`, `web/src/calendar/`.
- **Shared day-labeling rule**: `web/src/dayLabel.ts`'s `dayLabel(dateStr, now, mode)` computes Today/Tomorrow/"This &lt;Weekday&gt;" (within the current Sunday-Saturday week) — genuinely shared by `events/format.ts` and `camps/format.ts`. Two modes: `'summary'` (word only, used where a bucket header already supplies date context) and `'detailed'` (word + actual date, used on a standalone detail page). Mirrored byte-for-byte into `api/src/dayLabel.ts` (parity-checked by `scripts/check-format-parity.mjs`) since `api/src/newsletter/format.ts` needs the identical rule.
- **Data sourcing quality checklist** — apply mechanically to any future camp/event research pass, hand-researched or scraped (full incident detail behind each rule is in `CLAUDE_HISTORY.md`): (1) never trust a stated blanket policy as proof of real availability — check the actual booking system; (2) a price must be the provider's own genuinely published single-unit rate, never derived by dividing a bulk/weekly figure; (3) "estimated" means the price itself is uncertain, not just "not individually re-announced for this date"; (4) a source's URL must be the actual page you'd book from, never a marketing/homepage; (5) use the provider's own most specific, correct listing; (6) proactively re-check every similarly-situated provider once a data-quality gap is found for one; (7) merge listings that are genuinely one continuous window rather than fragmenting adjacent entries; (8) a closure only belongs in the calendar if it represents real camp-need (kids off school, parents still working) — nationally-recognized paid public holidays are excluded; (9) always file even a genuinely one-time event under its real, stable host organization's own page (a chamber of commerce, library branch, parish, neighborhood association), not a generic search/one-off source; (10) check whether a real umbrella aggregator already covers a category (verified for Chicago: `chicagoparent.com/calendar`, `chicagokids.com/calendar`) before hand-tracking individual venues.
- **Schema**: `camps` (`start_date`/`end_date` date ranges — a camp can span a school break; `end_date` defaults to `start_date`), `start_time`/`end_time` (nullable `time` columns — null renders "Time: not specified"), `price_per_day`, `options` (jsonb, `CampOptionLine[]`: `label`/`start_time`/`end_time`/`price`/`age_min`/`age_max`/`note`), `options_note` (free text, member self-service fallback only), `prep_items` (jsonb, `CampPrepLine[]`: `label`/`detail`), `prep_note` (free text, member self-service fallback only), `age_min`/`age_max`, `distance_miles` (haversine from Nettelhorst's fixed coordinates, `camps/geo.ts`), `price_is_estimated` (seed-only), `spots_available`, `booking_status` (`'open'|'full'|'waitlist'|'not_opened'`, nullable, seed-only), `image_url`/`thumbnail_url` (`NOT NULL`) — plus `camp_sources`, `camp_interests`, `camp_comments`.
- **Every field always shown, explicitly labeled even when unknown** (e.g. "Ages: not specified") — narrow exception: `spotsLabel` returns `null` (omitted entirely) when spots are unknown, since that's true for nearly every camp today and read as distracting noise inline.
- **School-break accordion browsing**: `school_breaks` table (`name`, `start_date`, `end_date`, `split_weekly` boolean). `GET /camps/by-break` groups camps by which break(s) their date range *overlaps* (not fully covers), computed in TypeScript (`api/src/camps/grouping.ts`'s `buildBreakBuckets`/`groupCampsByBreak`, unit-tested — not SQL, since the dataset is small). `split_weekly=true` (Summer Break) shows one accordion section per week. Sort within a bucket: viewer's own starred camp first, then most broadly interested, then booking-open, then alphabetical — `camps/format.ts`'s `sortCamps()`, shared with the camp reminder email.
- **Star/dismiss is inline, not tabbed**: every bucket shows one list; starred camps float to the top, dismissed camps are held out via a per-bucket "Show N dismissed items" reveal row. Swipe and a tappable star icon are both live at once.
- **Structured options/prep_items** (JSONB, not free text): `CampOptionLine` has real per-field `start_time`/`end_time`/`price`/`age_min`/`age_max` plus a `note` escape hatch — rendered as a real 4-column table (`OptionsTable`), sorted most-to-least expensive at render time. Member self-service posting stays simple: one free-text `options_note`/`prep_note` field, never the structured multi-row editor (those fields aren't settable via member `POST`/`PATCH`, only by seed scripts — except via universal editing, see below).
- **Time formatting house style** (`web/src/camps/format.ts`'s `timeLabel`, also applied to `events/format.ts`): omit `:00` minutes, lowercase `am`/`pm` no periods, "noon"/"midnight" instead of 12pm/12am, a shared meridiem shown once when both ends of a range match.
- **Booking status**: `camps.booking_status`, seed-only (not member-editable via the create form — universal editing does allow it), shown as a color-coded `IonBadge`. A point-in-time snapshot, refreshed only when asked.
- **Address as a map link**: `web/src/camps/format.ts`'s `shortAddress()`/`mapUrl()` — displayed text drops trailing city/state/zip, the link itself uses the full untrimmed address.
- **Cross-listing "notes from this source"**: `GET /camps/:id/source-notes`, merged into one uniformly-styled list with regular Comments (`CommentsSection.tsx`) — a comment gets a small date-range badge/link only when it's from a *different* camp occurrence than the one being viewed.
- **Titles are just the provider/venue name** (e.g. "Lake View YMCA"), not "`<break name> <provider> Camp`".
- **Images**: `api/src/camps/image-enrichment.ts`'s `enrichCampSourceImage()`, keyed by *source* (not listing) — every camp at a venue shares that venue's one real photo, fetched once per provider. `ProviderSpec.imageSourceUrls: string[]` is tried in order (a list of candidate pages, not just one).
- **Provider seed data, hand-researched not scraped**: `api/src/camps/seed-2026-08-04-providers.ts` plus several standalone backfill scripts. ~9 active providers today (Lake View YMCA, ClimbZone Chicago, Fit City Kids, BitSpace [0 camps — nothing confirmed bookable], Chicago Park District [0 camps — no genuine single-day rate published, real availability lives in a JS-rendered search this codebase can't query], Family Room Chicago, Unicoi Art Studio, Ultimate Ninjas, Sky Zone [0 camps — no camp program at the nearest location]). `ProviderSpec` mechanisms for expressing real confirmed availability: `hasRecurringOffering: false` (nothing confirmed open at all), `earliestConfirmedDate` (narrows to on/after a confirmed opening date), `breakDateOverrides` (narrows one specific break's range for one provider whose real hours don't span the whole break).

## Sports & Clubs data model & sourcing
- Fourth tab, for recurring activities with a real weekly cadence (dance classes, Park District sports leagues, martial arts, music/art lessons, school clubs) — distinct from Events' single/simple-recurring occurrences and Camps' school-break date ranges. **Deliberately fresh, non-shared clone**: own tables (`sports_clubs`, `sports_club_occurrences`, `sports_club_sources`, `sports_club_interests`, `sports_club_comments`), own routes, no cross-imports. Feature folders: `api/src/sports-clubs/`, `web/src/sports-clubs/`.
- **`schedule_type`: `'fixed_session' | 'ongoing'`** drives sort/hide logic (`api/src/sports-clubs/sorting.ts`, unit-tested): a `fixed_session` (a real cohort with a first/last day) sorts by `first_date` and hides once started (a "Show N already-started listings" reveal row); an `ongoing` listing (join-anytime) sorts by its next real occurrence and never hides for being "started." A listing with no upcoming occurrence at all is excluded from the fetch entirely.
- **`sports_club_occurrences`**: individual real meeting dates, generated for a bounded window (through a real season's end, or a rolling 12-week window for `ongoing` listings). `web/src/sports-clubs/format.ts`'s `nextOccurrenceDayTimeLabel()` derives the list-row preview from the real next occurrence, falling back to `cadence_note` when no occurrence data exists.
- **Structured `options`** (`SportsClubOptionLine` — label/start_time/end_time/price/price_unit/age_min/age_max/note), directly modeled on Camps' `CampOptionLine`.
- **Standardized weekly price**: `price_per_week` (hand-computed, always prefixed "~", rounded to the nearest whole dollar) is the one primary figure shown; the real published rate stays visible verbatim via `originalPriceLabel` as a transparency footnote.
- **Category-accordion browsing**: `CATEGORY_OPTIONS` (Dance, Sports & Athletics, Martial Arts, Music, Art & Creative, Academic & Clubs, Other), each with a small representative emoji via `format.ts`'s `categoryLabel()`.
- **Topic/Day/Time filters**: three independent chips (`SportsClubFilterChips.tsx`, own copy of Events' chip-opens-sheet pattern), each opening a real `IonModal` sheet wrapped in `IonContent` for genuine scroll. Pure client-side filtering (`web/src/sports-clubs/filters.ts`, unit-tested) — a listing with no occurrence data is never excluded by an active Day/Time filter.
- **Standing per-listing research checklist** — run through this for every new or re-researched listing (full incident detail on the Dance on Broadway/multi-provider under-research failures is in `CLAUDE_HISTORY.md`): (1) find the real class/schedule page, not just the homepage or a program-description blurb; (2) ask explicitly whether a wide age range or plural language ("classes," "levels") signals several distinct classes rather than one; (3) verify a grid/schedule page's real structure (raw HTML, positional PDF extraction, a rendered crop) rather than trusting a one-shot AI summary of it; (4) after image enrichment, open the actual uploaded file and confirm it's a real, on-topic, usable photo; (5) price/schedule must be the provider's own genuinely published number for *that specific class* — never inferred, blended across sibling classes, or copied from a different program, and honestly disclosed as unpublished (in `price_note`/`cadence_note`) only after a real attempt to find it.

## Universal editing & edit history
- **Any logged-in member can edit any event/camp/sports-club listing, in place, with full version history**. **Deletion stays creator-only, plus an admin override** (feedback #164, 2026-09-14) — a materially more destructive action than an edit, which is always visible/attributed/reversible via the history mechanism, so it's still scoped tighter than editing for everyone but Ben. `canEditX(currentUser, entity)` in each feature's `permissions.ts` is a trivial `return true`; a sibling `canDeleteX` returns true for the submitter or for `currentUser.roles.includes('admin')`. Serialization gained `can_delete` alongside the existing `can_edit`.
- **Editing is inline and WYSIWYG, not a separate form screen**: each entity's shared presentational "Body" component (`EventBody.tsx`, `CampBody.tsx`, `SportsClubBody.tsx`) takes `editing`/`draft`/`onFieldChange`/`highlightFields` props, rendering each fact line as either normal read-mode text or an inline input in the exact same DOM position, via the shared primitive `web/src/edit-history/InlineField.tsx` (`InlineField` wrapper + `InlineText/Textarea/Date/Time/Number/Select/CheckboxInput` atoms, all real Ionic components). Toggling `editing` never swaps the component tree — that's what keeps scroll position stable. A session-level Save/Cancel (not per-field autosave) is deliberate — one coherent history entry per editing pass, and a real Cancel. `InlineImageEditor` replaces the static photo with a small pencil-icon overlay in edit mode. The "create a new listing" flow (`EventForm.tsx`/`CampForm.tsx`/`SportsClubForm.tsx`) is unchanged — this rework is scoped to editing an *existing* listing.
- **"All the fields" includes what used to be seed-only**: Camps' `options`/`prep_items`/`price_is_estimated`/`booking_status` and Sports & Clubs' `options`/`signup_status` (plus `price_per_week` and `location_name`) are now genuinely member-editable. The structured `options`/`prep_items` arrays get real inline table/list editors (`EditableOptionsTable`/`EditablePrepList`), same column shape as the read-mode tables, with add/remove-row affordances.
- **One shared, generic history table, `entity_edits`** (migration `0047`) — `entity_type` (`'event'/'camp'/'sports_club'`) + `entity_id` discriminate rather than three parallel tables. `before`/`after` are full snapshots (snake_case), restricted to a fixed per-entity-type allow-list (`api/src/edit-history/service.ts`'s `EDITABLE_FIELDS` — internal workflow columns like `status`/`pipelineReviewedAt` excluded). `actor_user_id` (nullable FK) + `actor_label` (e.g. `'system:image-enrichment'`). `recordEdit()` no-ops (no insert) when nothing actually changed.
- **The one shared write path per entity, `applyXEdit()`** (`api/src/{events,camps,sports-clubs}/edit.ts`) — used by both that entity's `PATCH` route and the restore endpoint below, so restoring an old version isn't a second parallel implementation.
- **"System edits" scope = the ongoing pipeline only**, not one-off historical backfill/fix scripts. `events/image-enrichment.ts`'s `enrichEventImage()` gained `recordHistory`/`actor` options (default `true`/`'system:image-enrichment'`) — the batch `enrichEventImages()` used during initial ingestion passes `recordHistory: false`.
- **Pipeline Review unified into the same mechanism**: `editKeptCandidate()`/`retryEventImageForKeptItem()` record into the same `entity_edits` table, attributed to the acting admin (a real user, not a `system:` label).
- **History UI**: a low-key `timeOutline` icon in each detail page's toolbar, present in both read mode and edit mode (viewable by any member — the whole point of visible history is transparency now that anyone can edit anything). Opens `/events/:id/history` (and the Camps/Sports & Clubs equivalents) — `web/src/edit-history/EditHistoryListPage.tsx`, newest-first, each row showing the actor and a `changed_fields` teaser. Tapping a row opens `.../:id/history/:editId` (`EditHistoryVersionPage.tsx`) — renders that entry's `after` snapshot through the *same* Body component (read-only), `highlightFields` drawing a red left-border accent on changed fact lines. "Restore This Version" calls `POST /edit-history/:id/restore`, replaying the `after` snapshot through the same `applyXEdit()` — a restore is always a new forward edit, never a rewrite of history.
- **Toolbar decluttered into an overflow menu**: read-mode History/Edit/Delete collapsed into one `ellipsisVerticalOutline` `IonActionSheet` (mounted unconditionally, not inside an `editing`/`!editing` branch, to avoid the stale-`isOpen` reopen bug — see Feedback tab above). Star stays directly visible.
- **One deliberate, disclosed scope boundary**: Sports & Clubs' `sports_club_occurrences` stay read-only in every mode — treated as generated/related data, not one of "the fields" a listing owns, same posture as comments.
- Verified against real WebKit, not just Chromium — see `CLAUDE_HISTORY.md` for the number-input-spinner-overlap bug this surfaced (`InlineNumberInput` uses `type="text"` + `inputmode="decimal"`, not `type="number"`).

## Newsletter
- A weekly email digest of that week's approved, upcoming events. Feature folder `api/src/newsletter/` (no frontend component — email is the whole surface).
- **Sending**: Resend (`resend` npm package, `RESEND_API_KEY`/`RESEND_FROM_EMAIL` env vars).
- **Content window**: Monday–Sunday, computed by `getUpcomingWeekRange()` (`newsletter/week.ts`) against Chicago's calendar day (`todayInChicago()`, `api/src/dates.ts`). Sent Sunday night.
- **Query**: `newsletter/query.ts`'s `getWeeklyEvents()` is a deliberate parallel implementation of `GET /events` (same next-occurrence-collapse/interest-count CTE techniques, scoped to a date range) — kept separate to avoid risking the live endpoint.
- **Prioritization**: `newsletter/prioritize.ts`'s `prioritizeNewsletterEvents()` — non-recurring events first (chronological), then recurring events (sorted by interest count) fill remaining slots, capped at `MAX_NEWSLETTER_EVENTS` (10). "Recurring" = more than one approved, non-deleted occurrence anywhere in the whole table.
- **Template**: `newsletter/template.ts`, table-based HTML with inline styles, the whole event row is one clickable link. Subject/heading: "This week near Nettelhorst". CTA: "See more".
- **Kept in sync with the app, not just duplicated**: `newsletter/format.ts` and `newsletter/theme.ts` are byte-identical to `web/src/events/format.ts` and `theme.ts`, enforced by `scripts/check-format-parity.mjs` (CI job + local pre-push hook).
- **Unsubscribe**: `users.newsletter_subscribed` (boolean) + `GET /newsletter/unsubscribe?token=...` signed with the same `signJson`/`verifyJson` HMAC helpers WebAuthn uses (`api/src/auth/tokens.ts`), reusing `SESSION_SECRET`, no expiry. Logic in `newsletter/service.ts`.
- **Delivery**: `newsletter/send-weekly.ts`, a standalone script triggered by a dedicated Railway cron service. Parallel sends (`Promise.allSettled`) so one bad address doesn't block everyone. One `events_log` entry per run (`newsletter_sent`).
- **Absolute URLs**: `PUBLIC_API_URL`/`PUBLIC_WEB_URL` env vars required even in local dev — `mailer.ts` throws at module load if `RESEND_API_KEY`/`RESEND_FROM_EMAIL` is unset.
- **Admin test-send**: `POST /admin/newsletter/test-send`, surfaced at `/admin/dev-tools`.
- **Sending domain**: `RESEND_FROM_EMAIL` verifies against the platform apex `bulbord.com` (one verification covers every future institution). Display name/local-part is institution-prefixed: `Nettelhorst <nettelhorst.newsletter@bulbord.com>`.
- **Sender icon (BIMI)**: `web/public/bimi-logo.svg` served at `bulbord.com/bimi-logo.svg`. DNS records (`_dmarc.bulbord.com`, `default._bimi.bulbord.com`) still need adding manually in Cloudflare — not reachable via Claude's tools (see the DNS reference memory).

## Camp reminder email
- A second scheduled email, distinct from the weekly newsletter: fires ~4 weeks before a CPS day off, listing real available camps. Feature folder `api/src/camp-reminders/` (`window.ts` pure due-date logic, `query.ts` DB reads, `template.ts` render, `service.ts` admin test-send, `send-due.ts` cron entrypoint).
- **Trigger**: `window.ts`'s `isReminderDue(today, startDate, remindedAt)` fires once `today >= startDate - 28 days`, for any non-`split_weekly` `school_breaks` row not yet reminded and not fully passed. `schoolBreaks.remindedAt` is the dedup guard — self-healing (a missed cron run is still caught by the next one).
- One email per continuous block — `school_breaks` is already stored as block ranges.
- Only sends if the break has real camps listed: `query.ts`'s `getCampsForDateRange()`. A break with zero matches is skipped for that run (`remindedAt` stays null, re-checked every subsequent run).
- Recipients: same audience/unsubscribe as the newsletter.
- Content mirrors the in-app compact camp row: `api/src/camps/format.ts` (byte-identical mirror of `web/src/camps/format.ts`, parity-checked). Embeds small stacked avatars for "N interested" (capped at 5). Subject/heading use the app's abbreviated date format via `formatDateRange('detailed')`.
- Sort order shared with the live Camps tab: `camps/format.ts`'s `sortCamps()` (computed per recipient, since "starred by the viewer" varies).
- **Delivery**: `send-due.ts`, daily (12:00 UTC / ~7am Chicago) via a second dedicated Railway cron service (`camp-reminder-cron`). One `events_log` entry per break actually sent (`camp_reminder_sent`).
- **Admin test-send**: `POST /admin/camp-reminders/test-send` — ignores the real due-date gate and never touches `remindedAt` (a preview send must never suppress the later real send).

## Images & object storage
- A single Railway object storage bucket (`uploads`, S3-compatible) holds every image. Feature folder: `api/src/uploads/` (`storage.ts`, `routes.ts`), mirrored by `web/src/uploads/` (upload API client, `ImageLightbox`).
- Private bucket, no public-URL mode — every image is served through `GET /uploads/*`, a backend proxy with content-addressed (uuid) object keys and a long, immutable `Cache-Control`.
- Every upload gets two variants: a full image + a 400px JPEG thumbnail, generated server-side with `sharp` at upload time.
- `POST /uploads` (auth required) is the generic entry point for user-attached images (feedback screenshots via paste/file picker). Event/camp images are populated directly by the ingestion pipeline (no HTTP request to attach a file to).
- **Extraction priority order** (`api/src/events/image-enrichment.ts` + `api/src/uploads/extract-page-image.ts`'s `extractPageImageCandidates()`): `og:image`/`twitter:image` → schema.org JSON-LD `image` (`Event`/`Article` types only) → WordPress featured image → largest `<img>` within `<article>`/`<main>` → **Wikimedia Commons stock search** → **broader real-web-search tier** (see below) → site logo — the logo tier is tried dead last, after both web-search tiers, not before (a legacy ordering bug let a mediocre logo always beat a possibly-better web-search photo — see `CLAUDE_HISTORY.md`).
- **Broader real-web-search tier** (feedback #169, 2026-09-16): Wikimedia Commons' own keyless stock-photo search (`api/src/uploads/web-image-search.ts`'s `searchWebImageQueryTiers()`) only ever holds generic stock photos of a general subject — thin for anything hyper-local (a specific school's event, a specific neighborhood festival), which was the real cause of a recent sourcing run's "unacceptable image quality" (most candidates for local events had nothing to try beyond Commons and a site logo). `findBroaderImageSearchPages()` (same file) reuses the Anthropic `web_search` tool already paid for/exercised elsewhere in this codebase (`description-extraction.ts`, `photo-extraction.ts`, `resourcing.ts`) to find real candidate *pages* (news coverage, the host's own site, a community calendar) — deliberately page URLs, not image URLs a model might name from memory without them actually resolving — then runs each one through the exact same `extractPageImageCandidates()`/download/quality/relevance pipeline `source_url` itself already goes through. Tried after Commons, before the last-resort logo tier. No new API key/provider needed.
- **`events.image_url`/`thumbnail_url` and `camps.image_url`/`thumbnail_url` are `NOT NULL`** — a real Postgres constraint (migration `0025`). If no real candidate passes the quality gate, `api/src/uploads/placeholder.ts`'s `generatePlaceholderImage()` (deterministic solid-color card, title initial, palette color by title hash) is used instead. Every insert path computes a real value before insert. There's no `is_placeholder` flag to distinguish a generated placeholder from a real found photo on a given row.
- **Image quality gate**: `api/src/uploads/image-quality.ts`'s `isLowQualityImage()` downloads and checks real pixel dimensions/aspect ratio (rejects <200px on either side, or >3:1 aspect ratio) — a looser bar for `isLogo` candidates. `enrichEventImage()` walks every candidate (override → content candidates, scored → web search, scored → site logo, unscored) until one passes, rather than accepting the first found.
- **Content-relevance scoring**: `api/src/uploads/image-relevance.ts`'s `scoreImageRelevance()` — see Events section above. Skipped for `isLogo` candidates. Fails open.
- **Movie-poster lookup**: `api/src/events/movie-poster-lookup.ts`'s `lookupMoviePoster()` — Wikipedia's public keyless API, for recurring sources where the `source_url` can't distinguish occurrences but each occurrence is an identifiable real-world subject (a specific film). **Triggered by real judgment, not a title pattern** (feedback #169 follow-up, 2026-09-16): `identifyFilmScreening()` (same file) reads an event's title+description and decides whether it's genuinely a screening of one specific, named film, returning that film's canonical title — replacing an earlier `/^Movie Night: /` regex that broke every time a source used different phrasing (`fix-2026-09-05-petes-dragon-poster.ts`'s "Indoor Kids: Pete's Dragon" was the first casualty; "Film Screening: <film>" was the second). Called from `image-enrichment.ts`'s own `findImageCandidate()` — tried before both web-search tiers, for every entry point (ingestion, a member's own post, an edit, an admin retry), not just the original ingestion path the regex was scoped to.
- **Duplicate-image protections**: `isSharedListingPage(sourceUrl, eventId, title)` skips page-extraction when another *differently-titled* event already shares the exact `source_url` (a genuine same-titled recurring series is exempted). `events.sourceImageUrl` (migration `0043`) records the actual external URL a past enrichment used; `isAlreadyClaimedImage(url, eventId, title)` checks it before trusting any candidate, same different-title scoping. Both only compare against other currently-live events.
- **Full per-candidate debuggability**: `events_ingested` `events_log` rows carry `filteredOut`, `duplicateSkips`, and `imageTraces` (every image candidate + outcome: `shared_listing_page_skipped`/`already_claimed`/`download_failed`/`low_quality`/`rejected_relevance`/`chosen`) — queryable via plain SQL. **`events.imageSearchTrace`** (jsonb, migration `0049`, feedback #169) additionally persists that same per-candidate trace directly onto the event row itself — every `enrichEventImage()` call writes it, chosen or not, regardless of entry point (ingestion, a member's own post, an explicit admin retry), so one event's own search history is queryable without knowing which ingestion batch/events_log row touched it. Overwritten on each attempt; enrichEventImage is only ever re-invoked when the event still lacks a real image or someone explicitly retries, never as a redundant re-check of an already-successful search.
- **Standing rule**: never settle for a generated placeholder without exhausting real, genuinely distinct sources first (the org's own site, press coverage, a different aggregator, a specific non-generic Commons query, the broader web-search tier above).
- **Descriptive `User-Agent` on every outbound image/page fetch** (`api/src/uploads/fetch-with-timeout.ts`, feedback #169, 2026-09-16): found while investigating the same "unacceptable image quality" report that ~80% of Wikimedia Commons candidate downloads were failing in production (logged as `download_failed` with no status code kept to explain why), though the exact same URLs fetched fine from outside that environment — Node's `fetch` sends no `User-Agent` by default, and Wikimedia's stated policy (and plenty of other sites) treats anonymous-looking traffic from datacenter IP ranges with more suspicion than a request that identifies itself. Every caller of `fetchWithTimeout` (image downloads, page-text extraction, movie-poster lookup, resourcing) now sends one.
- `api/src/events/image-health.ts`'s `checkImageHealth()` calls the exact same `getImageObject()` the real proxy route uses, to verify every live event's stored image is actually servable — runs automatically on every Dev Tools page load (`GET /admin/events/image-health`).
- **Production incident lesson**: any one-off image fix must go through the live deployed API (mint a real session, call `POST /uploads`), never write to the bucket from a local script — a real, repeatable propagation gap exists between a local write and what the deployed proxy reads.
- Local dev shares the same production bucket, namespaced under `UPLOADS_KEY_PREFIX` (`dev/`). Bucket credentials: `railway bucket credentials --bucket uploads --environment production --json`.

## Testing (must run headless — no manual QA step required)
- Unit/component: Vitest + React Testing Library (`web/`), Vitest (`api/`). Ionic's web components don't map to standard ARIA roles in jsdom — tests click the underlying custom element directly. `web/src/test-setup.ts` stubs `window.matchMedia` and auto-cleans up. `IonModal`'s `present()`/`dismiss()` are async — wrap assertions against it in `waitFor`.
- E2E: Playwright (`web/playwright.config.ts`), headless, Pixel 7 mobile-viewport emulation. Passkey registration/login is driven end-to-end using Chrome DevTools Protocol's WebAuthn virtual-authenticator support (`web/e2e/passkey-auth.spec.ts`), not mocked. Run locally with `ROOT_INVITE_SECRET=<value from api/.env> npx playwright test` against a real local dev server — the spec skips itself silently if unset.
- **Real-WebKit cross-browser coverage is standard practice**, not an emergency-only technique, for any UI/interaction-touching change involving layout timing, canvas/image processing, file/photo attachment, or DOM APIs known to diverge across engines. `web/e2e/webkit-onboarding.spec.ts` + shared `web/e2e/helpers.ts`. Since CDP WebAuthn is Chromium-only, the spec launches a throwaway Chromium to register/get a session token, then hands the token to a real WebKit browser via `addInitScript`. Requires `npx playwright install --with-deps chromium webkit`.
- Component previews: Storybook (`web/.storybook/`, Vite builder). `.storybook/preview.tsx` mirrors `main.tsx`'s real bootstrap and wraps stories in the real `MemoryRouter`/`AuthProvider`. `msw`/`msw-storybook-addon` mocks only the fetch calls a story's `play` function exercises. Stories run for real via `@storybook/addon-vitest` in headless Chromium (not jsdom), folded into `npm test`. A disabled `ion-button`'s shadow content isn't in the browser's accessibility tree; `ion-input` uses closed shadow DOM — story `play` functions dispatch custom events directly on the custom elements rather than using role/label queries.
- **Visual regression**: Chromatic was tried, then removed for low ROI (see `CLAUDE_HISTORY.md`). Standing practice instead: Claude does local build-and-screenshot visual QA as part of finishing any UI-touching change.
- Types: TypeScript strict mode everywhere — treat `tsc` errors as test failures.
- Every push runs lint + typecheck + unit (api and web, parallel) + e2e in CI (`.github/workflows/ci.yml`) — must pass before merge. A local pre-push hook (`scripts/pre-push.sh`) runs lint + typecheck + both unit suites + `scripts/check-format-parity.mjs`, installed automatically via the root `package.json`'s `prepare` script (`ln -sf ../../scripts/pre-push.sh .git/hooks/pre-push` on `npm install`) — not a manual one-time step.
- A schema-level test (`api/src/db/schema.test.ts`) asserts the `NOT NULL` image columns stay declared `.notNull()` in the Drizzle schema, so a future accidental revert fails immediately rather than needing to reach production to be noticed.
- Coverage is targeted, not blanket: near-100% required on business logic (bookings, auth, data mutations); light coverage is acceptable on trivial UI glue.

## Introspectability
- No separate admin tool (no pgAdmin/Supabase Studio/etc.). All DB browsing, logs, and analytics live in an in-app `/admin` section gated to Ben's account specifically. `/admin/users` (`web/src/admin/UsersPage.tsx`, `GET /admin/users`) lists every member with who invited them and when they joined.
- **Developer Tools** (`/admin/dev-tools`, `web/src/admin/DevToolsPage.tsx`): newsletter test-send tool, link to All members, a sign-up flow preview (`/admin/invite-preview` → `/admin/profile-setup-preview` → `/admin/friends-preview`, reusing the real `InviteAcceptCard`/`ProfileSetupWizard(preview)`/`ChooseFriendsScreen(preview)` components — every field/button is genuinely interactive; only the final network-mutating call is skipped), "Re-run event sourcing" (calls `resourceActiveEventSources()`, admin sampling knobs `max_sources`/`max_candidates`), "Manage event sources"/"Manage camp sources" links (`AdminRoute`-gated `SourcesPage.tsx`/`CampSourcesPage.tsx`), "Test email-based event ingestion" (pasted-in from/subject/body form running the real extraction/ingestion pass), "Image health" (`GET /admin/events/image-health`, runs automatically on page load).
- Entry point: tapping your own avatar goes to `/account`; an admin taps the "Administrator" row (not the avatar/name row) to reach `/admin/dev-tools`.
- **Impersonation/demo sign-in links**: a per-member button on `/admin/users` generates a real ~1hr-TTL session via the same `?signInToken=` mechanism, shown as a QR code + Copy Link (`ImpersonateModal.tsx`, reusing `ShareButton.tsx`'s QR pattern via the extracted `web/src/sharing/useQrDataUrl.ts` hook). `api/src/admin/impersonation.ts`'s `impersonateUser()` writes its own `user_impersonated` `events_log` entry. `POST /admin/users/:id/impersonate`.
- **Member deletion**: `DELETE /admin/users/:id` (`api/src/admin/memberDeletion.ts`'s `deleteMember()`) soft-deletes (never hard-deletes) + writes a `user_deleted` `events_log` entry. No cascade to the member's other rows. An admin can't delete their own account.
- Logs are structured domain events (`events_log`: actor, action, metadata JSON, timestamp), not verbose request logs. Exception: production error/crash monitoring uses an external tool (Sentry or similar) rather than being built in-house.

## Analytics
- Admin-only (`/admin/analytics`, linked from Developer Tools). Backend: `api/src/analytics/` (`service.ts`, `routes.ts`) — a generic `POST /analytics/track` endpoint, validated against a fixed 4-item action enum (`app_opened`, `event_viewed`, `camp_viewed`, `share_opened`).
- **Daily active**: `app_opened` deduped to once per member per Chicago calendar day at insert time, fired once per app session from `AuthContext`'s boot effect.
- **"Who's viewing/sharing"**: `event_viewed`/`camp_viewed` fire once per detail-page mount; `share_opened` fires on Share modal open. Surfaced as aggregate 7-day stat tiles (distinct-actor counts).
- **Recent activity log**: an *exclusion* list (`EXCLUDED_LOG_ACTIONS`), not an allowlist — every real `events_log` action shows by default; only one-off backfill/seed/correction scripts opt out.
- Chart: a small hand-rolled SVG bar chart (`web/src/admin/DauChart.tsx`), no charting dependency, tap-to-reveal exact count, plus a `<details>`-collapsed data table.
- **Person filter**: `getAnalyticsSummary()` takes an optional `{actorId, mode: 'include' | 'exclude'}`, scoped only to the recent-log query — `GET /admin/analytics/summary?actor_id=...&actor_mode=...`. The person `IonSelect` uses `interface="action-sheet"`, not `"popover"` — popover positioning math breaks on this app's centered desktop "phone frame" layout (see Code hygiene's Ionic coverage check, which now bans `interface="popover"` outright).

## Code hygiene (anti-sprawl)
- Knip (`knip.json` in `api/`, default config in `web/`) runs in CI on every push, flagging unused exports/files/dependencies. Both scripts set `KNIP_DISABLE_RAW_TRANSFER=1` (sidesteps an oxc-parser memory issue under tight limits).
- oxlint (`web/`) and `tsc`'s `noUnusedLocals`/`noUnusedParameters` (both packages) enforce unused-imports/vars rules at write time.
- Feature-based file organization makes a whole dead feature visible as one unused folder.
- Run the `/simplify` skill as a standard step before merging non-trivial work.
- **Ionic coverage check** (`scripts/check-ionic-coverage.mjs`, run in its own CI job and the local pre-push hook): scans `web/src/**/*.tsx` for a hand-rolled clickable element or a raw HTML primitive Ionic doesn't cover (`<input type="file">`/`"checkbox"`/`"radio"`, `<canvas>`, `<button>`, `<select>`), fails the build unless marked with an `ionic-exception: <reason>` comment within 8 lines above. Also bans `interface="popover"` on any Ionic overlay (a real off-screen-rendering bug on this app's desktop layout — see Analytics above and `CLAUDE_HISTORY.md`).
